# Виртуальная файловая система

Статус: готов  
Назначение: определить единое пространство имён файлов профиля, идентичность и состояния
файла, семантику чтения и записи, доступ за пределы VFS и к чужим файлам.

Связанные документы: [blob store и материализация](./04-blobs-and-materialization.md),
[модель состояния](./01-state-model.md), [база данных приложения](./02-database.md),
[мусор и квоты](./05-garbage-and-quotas.md),
[базовый стек](../02-architecture/06-base-stack.md),
[обмен файлами между пользователями](../07-federation/02-sharing.md).

## Что это такое

VFS — единое платформонезависимое пространство имён, **одинаковое на всех нодах профиля**.
Физически это не общий POSIX-каталог: одинаково выглядит дерево, а не размещение
содержимого. На каждом устройстве есть каталог, который система синхронизирует, но
приложение работает не с ним, а с деревом профиля.

Разделение, определяющее всю модель:

```text
метаданные      реплицируются на все ноды: дерево, имена, атрибуты, ссылки на содержимое
содержимое      материализуется по политике: физически присутствует не везде
```

Отсюда главное следствие для приложений: **видеть файл и иметь его содержимое — разные
вещи**.

## Дерево

```text
/user/                       дом пользователя: документы, заметки, проекты, медиа
/app/<package-id>/           всё, что принадлежит пакету
        code/                артефакты пакета, только чтение
        replicated/          app.data.replicated
        files/               app.files — файлы приложения
        local/               app.data.local, своё на каждой ноде
        cache/               app.cache, вытесняемо в любой момент
        tmp/                 app.tmp, очищается при перезапуске ноды
/sys/                        состояние профиля: реестр пакетов, настройки, grants
        trash/               корзина профиля
        versions/            прежние версии содержимого
        volumes/             описания volume
/node/<node-id>/             пространство конкретной ноды: конфигурация, логи, диагностика
/mnt/<mount-id>/             внешние монтирования за пределами VFS
/shared/<peer-id>/           файлы, к которым доступ открыл другой пользователь
```

Дерево сгруппировано **по владельцу, а не по классу данных**: всё, что принадлежит пакету,
лежит в одном поддереве `/app/<pkg>/`, включая кэш и временные файлы. Уборка после пакета
становится одной операцией над одним путём, а не обходом нескольких корней, см.
[мусор и квоты](./05-garbage-and-quotas.md). Класс данных выражается вторым сегментом и
одинаков у всех пакетов, поэтому политику можно выразить правилом по маске пути.

Приложение по умолчанию видит только своё поддерево `/app/<own-package-id>/`. Всё остальное
требует отдельной capability, а `/user/` и `/mnt/` — ещё и действия пользователя.

| Поддерево | Владелец | Реплицируется | Переживает удаление пакета |
|---|---|---|---|
| `/user/` | пользователь | да | да |
| `/app/<pkg>/code/` | система | метаданные да, содержимое по размещению | нет |
| `/app/<pkg>/replicated/`, `files/` | пакет | да | нет, уходит в корзину |
| `/app/<pkg>/local/`, `cache/`, `tmp/` | пакет на этой ноде | нет | нет |
| `/sys/` | система | да | — |
| `/node/<node-id>/` | конкретная нода | нет | — |
| `/mnt/<mount-id>/` | хостовая ОС | нет, только факт монтирования | да |
| `/shared/<peer-id>/` | другой пользователь | нет, доступ по сети | да |

Владелец в этой таблице — не пояснение, а свойство каждой записи дерева: данных без
владельца в VFS не существует, и на этом построена уборка.

## Правила путей

Пути платформонезависимы, поэтому ограничения — объединение ограничений всех целевых
платформ:

- разделитель `/`, пути абсолютные;
- кодировка UTF-8 в нормализации NFC;
- регистр значим и сохраняется, но два имени в одном каталоге, различающиеся только
  регистром, запрещены — иначе дерево разойдётся между Linux и Windows;
- запрещены управляющие символы и `\ / : * ? " < > |`;
- запрещены зарезервированные имена Windows: `CON`, `PRN`, `AUX`, `NUL`, `COM1..9`,
  `LPT1..9`;
- запрещены завершающие точка и пробел;
- ограничение длины компонента имени и общей длины пути объявляется в контракте.

Проверка выполняется **при записи**, а не при чтении: недопустимое имя не должно попадать в
реплицируемые метаданные. Файл, пришедший из внешнего монтирования с недопустимым именем,
получает при импорте нормализованное имя, а исходное сохраняется в атрибутах.

## Идентичность файла

Файл имеет стабильный идентификатор, не зависящий от пути. Имя и родительский каталог —
атрибуты. Переименование и перемещение — операции над метаданными, а не удаление с
созданием: открытый handle и ссылки остаются валидными, история и конфликты сохраняются.

Практическое следствие: приложение хранит в своих данных **идентификатор файла**, а не
путь. Путь, сохранённый как ссылка, перестанет быть верным, как только пользователь
переименует каталог на другом устройстве.

## Состояния файла

Полное дерево видно на любой ноде, содержимое присутствует не везде:

| Состояние | Значение |
|---|---|
| `materialized` | содержимое доступно локально |
| `metadata-only` | известны только метаданные |
| `fetching` | содержимое загружается |
| `partial` | доступна часть содержимого |
| `evicted` | содержимое было локально и вытеснено |
| `conflicted` | существуют параллельные версии |
| `unavailable` | ни одна доступная нода не содержит содержимого |
| `index-not-local` | каталог является volume в режиме `members-only`, индекс не загружен |

Это часть публичного API. `unavailable` не означает потерю: чаще всего файл есть на
выключенном ноутбуке. Интерфейс обязан сообщать, где содержимое есть, а не показывать
ошибку чтения.

## Чтение

Режим доступа задаётся явно при открытии:

| Режим | Поведение |
|---|---|
| `auto` | при отсутствии содержимого запускает материализацию и ждёт в пределах deadline; при недостижимости источника возвращает `unavailable` |
| `require-local` | немедленная ошибка, если файл не материализован |
| `stream` | чтение диапазонов без полной материализации |

Дополнительно доступны `prefetch` и `pin`. `pin` закрепляет путь или поддерево на
конкретной ноде и защищает содержимое от вытеснения в пределах квоты.

Режим по умолчанию — `auto`. **Скрытая блокирующая загрузка без deadline не допускается ни
в одном режиме**: это правило существует потому, что иначе интерфейс приложения зависает на
файле, лежащем на выключенном устройстве.

## Запись

- запись идёт через `writer` с завершающим `commit`; **частично записанный файл не
  наблюдаем** ни локально, ни в репликации;
- `commit` опирается на сброс данных на носитель и атомарное переименование платформы;
- отменённая запись (`abort`) не оставляет следов в дереве;
- запись создаёт новую версию содержимого; предыдущее содержимое остаётся достижимым, пока
  на него есть ссылки, что делает возможными история версий и разрешение конфликтов;
- одновременная запись в один файл с двух устройств не блокируется и не отклоняется: обе
  версии сохраняются, файл переходит в `conflicted`.

## Наблюдение за изменениями

`watch(path, recursive)` даёт поток изменений: создание, изменение содержимого,
переименование, удаление, изменение состояния материализации, появление конфликта.

Свойства: события приходят и от локальных операций, и от репликации; поток может сообщить
о переполнении, после чего приложение обязано перечитать состояние поддерева; наблюдение
за большими поддеревьями квотируется.

Отдельно отмечается смена состояния материализации: для интерфейса «файл появился локально»
— такое же событие, как «файл изменился».

## Удаление

Удаление — операция над метаданными, распространяющаяся на все ноды. Чтобы ошибочное
удаление на одном устройстве не уничтожало данные повсюду:

- удалённые записи попадают в корзину профиля `/sys/trash/` на объявленный срок и
  восстанавливаются оттуда с прежним идентификатором. Корзина — видимый каталог, а не
  скрытое состояние: невидимая корзина является невидимым мусором;
- содержимое физически удаляется сборщиком мусора только когда на него не ссылается ни
  одна живая версия и истёк срок хранения корзины;
- удаление поддерева выполняется как одна операция, чтобы промежуточное состояние не
  расходилось по нодам.

## Политика материализации

Метаданные приходят на все ноды. Содержимое хранится по политике, которая задаётся двумя
уровнями: **дефолт по классу ноды** и **явные исключения**.

| Класс ноды | Дефолт для `/user/` | Дефолт для `/app/*/files/` |
|---|---|---|
| десктоп, ноутбук | полное зеркало | полное зеркало |
| телефон, планшет | полное зеркало в пределах квоты, дальше вытеснение по давности | по потребности компонента |
| `cloud` | полное зеркало | полное зеркало |
| `appliance`, `relay` | ничего: ключей данных нет | ничего |

**Дом пользователя по умолчанию материализован целиком на каждой ноде, владеющей ключами
данных.** Это дефолт политики, а не инвариант, и разница существенна: устройство с малым
хранилищем физически не может держать дом на два терабайта. Инвариант, который система не
способна выдержать, приводит либо к отказу записи на телефоне, либо к молчаливому
вытеснению — то есть к нарушению собственного обещания.

Поэтому обещание о сохранности формулируется иначе и является инвариантом:

> Содержимое, отнесённое к реплицируемым классам, присутствует не менее чем на
> `min-replicas` нодах профиля. Значение по умолчанию — 2, и хотя бы одна из них
> постоянно доступна, если такая нода в профиле есть.

Следствия, обязательные к реализации:

- запись, после которой содержимое существует в одном экземпляре, **разрешена**, но запись
  помечена недостаточной избыточностью до появления второй копии, и это видно в интерфейсе;
- вытеснение никогда не уменьшает число реплик ниже `min-replicas`: последняя копия не
  вытесняется, а запись, которой не хватает места, возвращает `quota-exceeded`;
- нода, которой не хватает места на полное зеркало, показывает дефицит числом — «до полного
  зеркала не хватает 40 ГБ» — вместо того, чтобы молча уходить в режим вытеснения;
- профиль из одного устройства не может удовлетворить `min-replicas`, и это состояние
  показывается как незакрытый риск, а не считается нормой.

Явные исключения из дефолта:

- `pin` пути или поддерева закрепляет содержимое на ноде и защищает от вытеснения;
- декларация потребности в манифесте компонента;
- **volume** — поддерево с собственным списком нод, см. ниже;
- квота профиля на этой ноде и давность обращения — для всего, что не закреплено.

Вытеснение не удаляет файл: запись переходит в `evicted` и восстанавливается при
доступности источника. Пользователь видит, сколько места занято и что будет вытеснено
следующим.

## Volumes

Большие коллекции — фотографии, видео, архивы — не должны лежать в доме пользователя, если
дом реплицируется целиком: они раздувают каждое устройство. Для них существует **volume** —
поддерево с собственным списком нод-участников.

```text
volume "Photos"   path /user/Photos   members {desktop, cloud, nas}   index full
volume "Video"    path /user/Video    members {nas}                   index members-only
```

Свойства:

- volume — **не второй механизм синхронизации**. Это то же дерево, те же blobs, та же модель
  конфликтов и та же корзина. Отличается только множество нод, хранящих содержимое, и то,
  что автоматические политики материализации к нему не применяются;
- содержимое материализуется только на нодах-участниках. Нода вне списка видит дерево и
  может вытянуть отдельный файл по запросу — этим модель отличается от отдельной программы
  синхронизации, где на неучаствующем устройстве поддерева просто не существует;
- `min-replicas` действует и внутри volume: volume с единственным участником инварианту не
  удовлетворяет, и это показывается как риск потери, а не как выбранная конфигурация;
- volume не вкладываются друг в друга: путь принадлежит ровно одному volume;
- описания volume лежат в `/sys/volumes/` и реплицируются как обычное состояние профиля;
- удаление ноды из списка участников не удаляет содержимое немедленно: оно переходит в
  разряд вытесняемого и убирается сборщиком, когда инвариант реплик уже выполнен другими.

### Режим индекса

| Режим | Метаданные | Что видит нода вне списка |
|---|---|---|
| `full` | реплицируются везде | полное дерево поддерева, содержимое по запросу |
| `members-only` | только на участниках | узел в состоянии `index-not-local` с числом файлов и объёмом |

`full` — режим по умолчанию, потому что метаданные дёшевы: порядка сотен байт на файл, то
есть десятки мегабайт на сотню тысяч фотографий. `members-only` существует для коллекций в
миллионы записей, где заметным становится сам индекс. Индекс такого volume загружается по
требованию, и это обычная операция, а не восстановление после сбоя.

Это единственное допустимое расхождение дерева между нодами, и оно **наблюдаемо**:
поддерево видно как узел с явным состоянием, а не отсутствует молча.

## Доступ за пределы VFS

Доступ к хостовой файловой системе возможен только через явное внешнее монтирование:

- монтирование создаётся **действием пользователя**: системный picker каталога или
  настройка. Приложение не может создать его скрытно;
- каждое монтирование получает идентификатор и собственные права
  `files.external.<mount-id>.read|write`, выданные **тому приложению**, которое доступ
  запросило. Другой пакет этим монтированием не воспользуется;
- содержимое внешних монтирований не реплицируется. Между нодами передаётся только факт
  существования монтирования и его описание, чтобы пользователь понимал, где лежат данные;
- каждое монтирование принадлежит конкретной ноде. Обращение к нему с другого устройства
  маршрутизируется по сети к владеющей ноде и требует её доступности: это удалённый доступ
  к чужому диску, а не синхронизация;
- платформа может отозвать доступ в любой момент, что возвращается как `revoked`, а не
  `io`, и является нормальным состоянием;
- на Android внешний доступ выражается идентификаторами SAF, а не путями, и adapter обязан
  представлять это ограничение явно, не имитируя POSIX-семантику.

Копирование из внешнего монтирования в VFS — обычная операция чтения и записи, и именно она
превращает внешний файл в файл профиля, который дальше синхронизируется.

## Чужие файлы

`/shared/<peer-id>/` содержит то, к чему открыл доступ другой пользователь. Это не копия:

- чтение маршрутизируется в сеть владельца, и при её недоступности возвращается
  `unreachable`;
- владелец может закрыть доступ в любой момент, после чего поддерево исчезает;
- явное копирование к себе — отдельное действие пользователя, а не следствие открытия;
- содержимое из `/shared/` не реплицируется между нодами получателя без такого действия.

Модель и границы обещаний — в [обмене файлами](../07-federation/02-sharing.md).

## Квоты

| Ограничение | Поведение |
|---|---|
| объём профиля на ноде | вытесняется `tmp`, затем `cache`, затем незакреплённое содержимое |
| объём приложения | запись возвращает `quota-exceeded` |
| число файлов в каталоге | предупреждение, затем отказ записи |
| закреплённое содержимое | `pin` сверх квоты возвращает `quota-exceeded`, а не вытесняет чужое |
| последняя реплика содержимого | не вытесняется ни при каком давлении на место |

Учёт занятого места по владельцу, классу и ноде и правила уборки — в
[мусоре и квотах](./05-garbage-and-quotas.md).

## Проверяемые критерии

- дерево одинаково на всех нодах профиля, за единственным исключением: поддерево volume в
  режиме `members-only` представлено на неучаствующей ноде узлом в состоянии
  `index-not-local`. Иных расхождений дерева не существует;
- содержимое реплицируемых классов присутствует не менее чем на `min-replicas` нодах, и
  запись, нарушающая это условие, наблюдаема как недостаточная избыточность;
- вытеснение не уменьшает число реплик ниже `min-replicas`;
- у каждой записи дерева есть ровно один владелец: пользователь, пакет или система;
- файл имеет идентичность, не зависящую от пути;
- нематериализованное содержимое — нормальное состояние, выражаемое в API;
- ни один режим чтения не блокирует вызывающего без deadline;
- частично записанный файл не наблюдаем;
- недопустимое имя не попадает в реплицируемые метаданные;
- внешнее монтирование не реплицируется и доступно с других нод только по сети;
