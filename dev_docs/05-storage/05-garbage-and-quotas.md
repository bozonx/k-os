# Мусор, владение данными и уборка

Статус: готов  
Назначение: определить, кому принадлежит каждый байт хранилища, что происходит с данными при
удалении пакета, как устроены сроки хранения, учёт занятого места и сборка мусора.

Связанные документы: [VFS](./03-vfs.md), [модель состояния](./01-state-model.md),
[база данных приложения](./02-database.md),
[blob store](./04-blobs-and-materialization.md),
[распространение приложений](../03-apps/07-distribution.md),
[системная оболочка](../09-clients/05-system-shell.md).

## Задача

Персональная среда живёт годами и переживает десятки установленных и удалённых приложений.
Если каждое из них оставляет после себя данные, которые никому не принадлежат, через год
пользователь не может ответить на вопрос «что занимает место» и не может это вычистить.
В реплицируемой среде проблема хуже, чем на одном устройстве: мусор копируется на все ноды и
занимает место везде.

Решение строится на одном свойстве, которое обязано выполняться с самого начала, потому что
добавить его задним числом к уже накопленным данным невозможно.

## Владелец есть у каждого байта

> Каждая единица хранения — запись VFS, объект базы, blob, секрет, запись журнала —
> принадлежит **ровно одному владельцу**. Данных без владельца не существует.

| Владелец | Обозначение | Что это |
|---|---|---|
| пользователь | `user` | `/user/`, а также файлы, созданные приложениями по его действию |
| пакет | `pkg:<package-id>` | всё в `/app/<pkg>/`, коллекции его базы, его секреты |
| система | `system` | `/sys/`, `/node/<id>/`, реестры, control log, логи |

Из этого правила следует всё остальное: уборка перестаёт быть эвристикой и становится
запросом «покажи всё, что принадлежит вот этому владельцу». Реализация обязана хранить
владельца рядом с данными, а не выводить его из пути: путь меняется, владелец — нет.

### Файлы, созданные приложением в доме пользователя

Отдельный случай, который иначе порождает сирот. Приложение с правом `files.user.write`
записывает файл в `/user/`. Правило:

- владельцем становится **пользователь**, а не пакет: иначе удаление читалки уничтожило бы
  сохранённые ею книги;
- запись получает атрибут `created-by: <package-id>`, сохраняемый в метаданных навсегда;
- после удаления пакета оболочка может показать: «приложение X оставило 240 файлов в
  `/user/`, объём 12 ГБ» — и предложить их просмотреть;
- **автоматически такие файлы не удаляются никогда**, даже с подтверждением в диалоге
  удаления пакета: пользователь принимает это решение отдельно, глядя на список.

Причина запрета: атрибут `created-by` описывает происхождение, а не принадлежность.
Отредактированный пользователем документ не перестаёт быть его документом оттого, что первым
его записал редактор.

## Удаление пакета — это две разные операции

Самая опасная ошибка в этой области — одно слово «удалить» для двух разных действий.
Пользователь освобождает место на телефоне и теряет данные на десктопе.

| Операция | Область | Что происходит |
|---|---|---|
| **убрать с этого устройства** | одна нода | удаляются `code`, `local`, `cache`, `tmp`, производные индексы; реплицируемые данные не трогаются |
| **удалить из профиля** | весь профиль | пакет исключается из реестра, его реплицируемые данные и файлы уходят в корзину на всех нодах |

Первая — операция [размещения](../03-apps/08-placement-and-execution.md), обратимая
установкой обратно: данные при ней не теряются нигде и приходят снова. Вторая — операция над
реплицируемым состоянием профиля.

Требования к интерфейсу, а не только к реализации:

- операции называются разными словами и не объединяются в один пункт меню;
- «удалить из профиля» показывает, сколько данных будет удалено и на скольких нодах;
- «убрать с этого устройства» показывает, сколько места освободится **здесь**, и явно
  сообщает, что данные останутся в профиле.

### Три уровня при удалении из профиля

Один диалог, три группы с разной судьбой:

| Уровень | Что | Возврат |
|---|---|---|
| немедленно | `cache`, `tmp`, `local`, производные индексы, артефакты `code` | нет и не требуется: восстанавливается пересчётом или загрузкой |
| в корзину | `replicated`, `files`, коллекции базы, секреты пакета | да, в пределах срока хранения |
| никогда | файлы пользователя с `created-by`, данные, экспортированные в другие пакеты | не удаляются, только показываются списком |

Данные второго уровня переносятся в `/sys/trash/packages/<package-id>/` и остаются
восстановимыми вместе с пакетом: повторная установка в пределах срока хранения возвращает
состояние, а не начинает с пустого места. Это прямо влияет на поведение пользователя —
удалить приложение, чтобы освободить место, перестаёт быть необратимым решением.

## Сроки хранения

Значения по умолчанию с записанными причинами; каждое настраивается в профиле.

| Что | Дефолт | Причина |
|---|---|---|
| корзина файлов | 30 дней | покрывает типичный интервал «заметил пропажу» и переживает отпуск |
| корзина данных удалённого пакета | 30 дней | тот же интервал, чтобы правило было одно |
| прежние версии содержимого | 30 дней либо 10 версий, что наступит раньше | ограничение по обоим измерениям: один большой файл иначе съедает бюджет истории |
| tombstones и горизонт компактизации | 90 дней | нода, не выходившая на связь дольше, синхронизируется полным переносом, см. [репликацию](../06-network/07-replication.md) |
| `tmp` | до перезапуска ноды | не требует бюджета и учёта |
| `cache` | без срока, вытесняется по давлению на место | по определению класса |
| логи ноды | по объёму, ротация | время здесь бесполезно: важен объём, а не возраст |

Срок хранения корзины **не является гарантией**: при нехватке места корзина очищается
раньше, начиная с самых старых записей, и пользователь об этом уведомляется. Обещание
«30 дней при наличии места» честнее, чем невыполнимое «30 дней всегда».

## Учёт занятого места

Без учёта уборка невозможна: пользователь не может убрать то, о существовании чего не знает.
Поэтому учёт — часть публичного контракта, а не диагностика.

Разрезы, которые система обязана уметь показать:

```text
по владельцу      сколько занимает каждый пакет, пользователь, система
по классу         replicated / local / cache / tmp / files / корзина / версии
по ноде           здесь и на каждой другой ноде профиля
по состоянию      материализовано / вытеснено / только метаданные
по возвратности   освободится сразу / после истечения срока / только по решению пользователя
```

Существенные свойства:

- учёт ведётся **по логическому размеру и по занимаемому месту раздельно**: дедупликация
  чанков делает сумму по владельцам больше физического объёма, и интерфейс обязан показывать
  обе величины, а не выдавать одну за другую;
- сведения о других нодах приходят из реплицируемого состояния и сопровождаются отметкой
  давности, как и любое состояние ноды;
- приложение видит **только собственное потребление** — это не привилегированная информация,
  но и не повод раскрывать пакету размеры чужих данных.

## Сборка мусора

Работает постоянно и без участия пользователя:

| Что собирается | Условие |
|---|---|
| чанки blob | нет ссылки ни из одной живой версии и истёк срок корзины |
| прежние версии содержимого | превышен лимит по числу или по возрасту |
| tombstones | достигнута причинная стабильность либо пройден горизонт |
| записи корзины | истёк срок хранения |
| `tmp` | перезапуск ноды |

Сборка мусора **никогда не удаляет данные класса `replicated` и `user`, срок хранения
которых не истёк**. Освобождение места под давлением идёт строго в объявленном порядке:
`tmp` → `cache` → незакреплённое содержимое по давности → старейшие записи корзины. Ниже
этого система не опускается: она возвращает `quota-exceeded` вызывающему, а не удаляет то,
чего пользователь не разрешал.

### Проверка на сирот

Отдельная периодическая задача, потому что сирота — это всегда следствие ошибки или сбоя, а
не штатного пути. Она не удаляет молча, а **докладывает**, и предлагает действие:

- данные пакета, отсутствующего в реестре профиля;
- blob, на которые нет ссылок, но которые не были собраны;
- ссылки на blob, содержимого которых нет ни на одной известной ноде;
- монтирования, указывающие на исчезнувший каталог;
- volume, у которых не осталось нод-участников;
- grants, выданные пакету, которого больше нет.

Отчёт показывается в разделе диагностики оболочки. Автоматическое удаление разрешено только
для первых двух категорий и только по истечении срока корзины: остальные могут быть
следствием временной недоступности ноды, а не мусором.

## Что система не делает молча

Правило, ради которого написан весь документ:

- не удаляет данные пользователя;
- не удаляет `replicated`-данные установленного пакета;
- не очищает корзину раньше срока, не сообщив об этом;
- не удаляет файлы, созданные приложением в `/user/`, при удалении приложения;
- не уменьшает число реплик содержимого ниже `min-replicas`.

Всё остальное — `cache`, `tmp`, производные данные, артефакты, вытесняемое содержимое —
система вправе удалить в любой момент, и приложение обязано это выдерживать.

## Проверяемые критерии

- у каждой единицы хранения есть ровно один владелец, и он хранится рядом с данными;
- файл, записанный приложением в `/user/`, принадлежит пользователю и несёт `created-by`;
- удаление пакета из профиля и удаление с ноды — различимые операции с разными
  последствиями, и ни одна из них не выполняется под именем другой;
- повторная установка пакета в пределах срока хранения возвращает его данные;
- сумма учёта по владельцам покрывает всё занятое профилем место: неучтённого остатка нет;
- при нехватке места порядок освобождения соблюдается, и запись отклоняется раньше, чем
  удаляются данные пользователя;
- сирота обнаруживается и докладывается, а не удаляется молча;
- полностью удалённый пакет не оставляет данных, кроме файлов пользователя с `created-by`.

## Открытые вопросы

- **Экспорт данных между пакетами.** Пока [межпакетный обмен](../01-overview/05-open-questions.md)
  не спроектирован, третий уровень уборки содержит категорию, механизма у которой нет. Когда
  обмен появится, переданные данные обязаны получить владельца по тем же правилам.
- **Бюджет истории версий на профиль**, а не только на файл: сейчас лимит по числу и возрасту
  версий не ограничивает суммарный объём истории.
