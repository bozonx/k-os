## Namespaces

Приложение работает с логическими namespaces, а не с внутренней структурой каталогов:

```text
app.data.local        не реплицируется, принадлежит этому node
app.data.replicated   реплицируется между nodes профиля
app.cache             не реплицируется, вытесняемо в любой момент
app.tmp               не реплицируется, очищается при перезапуске node
app.secrets           секреты приложения
app.files             файлы приложения в VFS
user.files            пользовательские файлы в VFS
```

Соответствие namespace, пути VFS и capability однозначно и фиксируется таблицей:

| Namespace | Путь VFS | Capability |
|---|---|---|
| `app.data.local` | `/app/<pkg>/local/` | `storage.local.read-write` |
| `app.data.replicated` | `/app/<pkg>/replicated/` | `storage.replicated.read-write` |
| `app.cache` | `/app/<pkg>/cache/` | `storage.cache.read-write` |
| `app.tmp` | `/app/<pkg>/tmp/` | `storage.tmp.read-write` |
| `app.files` | `/app/<pkg>/files/` | `files.app.read-write` |
| `app.secrets` | — | `secrets.read-write` |
| `user.files` | `/user/` | `files.user.read`, `files.user.write` |

Секреты не имеют пути в VFS: они хранятся отдельно и не адресуются как файлы.

`app.tmp` отделён от `app.cache` намеренно, хотя оба не реплицируются. Разница в контракте
восстановления: `cache` заполняется данными, которые дорого получить заново, поэтому он
вытесняется по давлению на место и учитывается в квоте; `tmp` — рабочая область одного
исполнения, и она исчезает при перезапуске node без учёта и без вопросов. Без отдельного
`tmp` промежуточные файлы неизбежно оказываются в `cache` и вытесняют оттуда полезное.

Логи не являются namespace приложения: [журналирование](../04-capabilities/02-catalog/01-common-types.md)
пишется в системный приёмник, физически расположенный в `/node/<node-id>/logs/`. Логи
принадлежат системе, никогда не реплицируются — иначе поток диагностики заполнил бы op log —
и ротируются по объёму.

## Классы состояния

| Класс | Реплицируется | Назначение | Пример |
|---|---|---|---|
| `ephemeral` | нет | состояние процесса | открытое соединение |
| `device-local` | нет | данные конкретного устройства | раскладка панели, выбранное аудиоустройство |
| `replicated` | да | синхронизируемые данные | настройки, документы |
| `derived` | нет | восстанавливаемые данные | индекс поиска, thumbnails |
| `temporary` | нет | рабочая область одного исполнения | распаковываемый архив, промежуточный файл |
| `log` | нет, никогда | диагностика | журнал ноды и записи приложений в нём |
| `secret` | да, в зашифрованном виде | переносимые секреты | API token |
| `device-bound-secret` | нет, никогда | секрет конкретного устройства | приватный ключ node |
| `file` | метаданные да, содержимое по политике | файлы | документы и медиа |

`derived` реплицировать не следует: восстановить дешевле, чем синхронизировать. Приложение обязано уметь пересобрать этот класс с нуля.

## Инварианты

**У каждой единицы хранения ровно один владелец** — пользователь, пакет или система. Это условие делает возможной уборку и учёт занятого места; правила владения и последствия удаления пакета — в [мусоре и квотах](./05-garbage-and-quotas.md).

**Реплицируется операция, а не файл базы данных.** Файлы локального движка хранения никогда не синхронизируются побайтово между nodes. Это относится и к базам приложений, и к базам самой системы.

**Подтверждённая replicated mutation атомарна.** Локальное изменение и durable запись для будущей репликации сохраняются в одной транзакции. Реализация не имеет права сначала изменить базу, а затем ненадёжно уведомить sync service.

**Публичный storage API не сводится к одному CRUD.** Приложение выбирает семантику данных — документ, множество, счётчик, журнал, координируемая запись — и consistency profile, но не алгоритм репликации.

Физическое хранение является деталью реализации storage service и может измениться без изменения API приложений.

`localStorage`, IndexedDB и browser cache:

- считаются локальными и несинхронизируемыми;
- не должны использоваться для основного состояния;
- могут очищаться вместе с данными контейнера;
- допускаются для временной оптимизации UI.

Основным способом хранения является асинхронное K-OS storage API.
