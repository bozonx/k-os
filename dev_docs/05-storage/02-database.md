# База данных приложения

Статус: готов  
Назначение: определить, как приложение работает с базой данных, как система обеспечивает её
синхронизацию между нодами профиля и какие ограничения из этого следуют.

Связанные документы: [модель состояния](./01-state-model.md),
[репликация](../06-network/07-replication.md), [VFS](./03-vfs.md),
[данные приложения](../03-apps/06-app-data-api.md),
[каталог capabilities](../04-capabilities/02-catalog/00-index.md).

## Разграничение ролей

**Базой управляет система, приложение читает и пишет данные.** Приложение не открывает файл
базы, не выбирает движок, не управляет соединениями и не выполняет репликацию. Оно работает
с типизированным API поверх слоя синхронизации.

```text
Приложение          коллекции, объекты, запросы, подписки
      ↓ capability API
storage-service     схема, типы данных, транзакция, подписки, квоты
      ↓
replication layer   op log, причинность, слияние, эпохи ключей
      ↓
локальный движок    materialized state + outbox в одной транзакции
```

Причина такого разделения: синхронизация, разрешение конфликтов и шифрование не могут быть
корректно реализованы в каждом приложении отдельно, а именно они определяют, будет ли
пользователь терять данные.

## Что синхронизируется

**Реплицируется операция, а не файл базы данных.** Побайтовая синхронизация файла SQLite
или другого движка между нодами запрещена: при параллельной записи это гарантированное
повреждение. Локальный движок — деталь реализации ноды и не является частью контракта.

Локальный движок — SQLite: он даёт транзакции, надёжность и присутствует на всех целевых
платформах. Существенно, что он используется как **локальное материализованное
представление**, а не как единица синхронизации.

Движок **один и тот же на всех платформах, включая мобильные**. Модель допускает разные
движки на разных нодах, но система ими не пользуется: отдельный мобильный движок удваивает
матрицу тестов и создаёт класс дефектов, воспроизводимых только на устройстве. Если
платформа когда-либо потребует другого движка, это изменение реализации, а не контракта.

### Атомарность подтверждённой записи

Подтверждённая запись атомарно обновляет две вещи в одной транзакции локального движка:

```text
BEGIN
  применить изменение к materialized state
  записать операцию в durable replication outbox
COMMIT
```

Синхронизация не восстанавливает пропущенные изменения, наблюдая за базой постфактум:
триггеры и сравнение снимков дают потерю операций при сбое между записью и наблюдением.
Нарушение этого правила невозможно исправить позднее без потери данных, поэтому оно входит
в [критерии корректности](../11-development/03-correctness-criteria.md).

## Модель данных

Приложение выбирает **семантику данных**, а не алгоритм репликации. Это позволяет менять
реализацию слияния без изменения публичного API.

| Тип | Семантика слияния | Когда применять |
|---|---|---|
| `document` | map с LWW по полям | записи приложения, настройки, карточки объектов |
| `set` | observed-remove set | коллекции ссылок, теги, членство |
| `counter` | grow-only или PN | счётчики, статистика |
| `log` | append-only, причинный порядок | история, события, сообщения |
| `blob-ref` | ссылка на неизменяемое содержимое | вложения, медиа, большие файлы |
| `coordinated` | запись только под lease | то, что нельзя разрешить слиянием |

Данные приложения группируются в **коллекции**: именованные множества объектов одного типа
с объявленной схемой. Коллекция принадлежит одному namespace и наследует его класс
(`replicated`, `local`, `cache`).

```text
collection  "tracks"     type document  namespace app.data.replicated
collection  "playlists"  type document  namespace app.data.replicated
collection  "index"      type document  namespace app.data.local     (derived)
```

### Что нельзя выразить

Модель честно ограничена, и границы фиксируются, чтобы приложение не проектировалось вокруг
несуществующих гарантий:

- **нет глобальных ограничений целостности.** Уникальность значения поля по всей коллекции
  не может быть гарантирована при параллельной записи на двух устройствах. Уникальность
  достижима только через `coordinated` с lease или через ключ, вычисляемый из содержимого;
- **нет внешних ключей с каскадами.** Ссылка на удалённый объект — нормальное промежуточное
  состояние при слиянии; приложение обязано его допускать;
- **нет распределённых транзакций.** Транзакция атомарна локально и в пределах одного
  namespace;
- **нет единого порядка записей между объектами.** Гарантируется причинный порядок, а не
  общий; см. [модель времени](../06-network/05-time.md);
- **нет совместного редактирования текста** как встроенного типа: это отдельный тип
  последовательности, не входящий в v0.

## Запросы

В v0 приложению даётся **декларативный запрос по объявленным полям**, а не произвольный SQL:

```wit
interface query {
  record filter { field: string, op: compare-op, value: value }
  record order  { field: string, descending: bool }

  record request {
    collection: string,
    filters: list<filter>,
    order-by: list<order>,
    limit: u32,
    cursor: option<string>,
  }

  run:   func(req: request) -> result<page, error>;
  count: func(req: request) -> result<u64, error>;
  watch: func(req: request) -> result<change-feed, error>;
}
```

Причина отказа от произвольного SQL в публичном API: SQL-запрос выражает предположения о
физической схеме и о единой согласованной базе, а данные приложения — набор сливаемых
объектов, физическое представление которых является деталью реализации. Кроме того,
произвольный запрос от недоверенного кода — источник неограниченной нагрузки.

Каждый запрос обязан опираться на объявленный индекс либо на ключ объекта; запрос, для
которого нет индекса, отклоняется явной ошибкой на этапе установки пакета, а не деградирует
в полное сканирование во время работы.

Локальное read-only SQL-представление сверх декларативных запросов **не вводится**: оно
возвращает в публичный API предположения о физической схеме, ради обхода которых запрос и
сделан декларативным, а стоимость произвольного запроса от недоверенного кода не
ограничивается иначе как таймаутом. Задачи, ради которых его просят, решаются объявленным
индексом и постраничным чтением.

Стоимость запроса ограничивается тремя способами сразу: обязательным индексом, `limit` на
странице и лимитом просмотренных записей. Запрос, превысивший лимит просмотра, возвращает
`quota-exceeded` и не деградирует в долгое сканирование.

### Индексы и производные данные

Индексы объявляются в манифесте и относятся к классу `derived`: они не реплицируются, а
строятся на каждой ноде локально и могут быть перестроены в любой момент. Это следует из
того, что производные данные дешевле пересчитать, чем синхронизировать, и их рассогласование
не должно быть наблюдаемым.

Приложение может объявлять собственные индексы; создавать их во время работы динамически —
нет, потому что построение индекса на слабом устройстве является заметной нагрузкой и должно
быть учтено при установке.

## Транзакции

```wit
interface transaction {
  resource tx {
    put:    func(collection: string, id: string, patch: value) -> result<_, error>;
    delete: func(collection: string, id: string) -> result<_, error>;
    commit: func() -> result<_, error>;
    abort:  func();
  }
  begin: func(namespace: string) -> result<tx, error>;
}
```

Свойства:

- транзакция атомарна **локально**: либо все изменения попали в materialized state и outbox,
  либо ни одного;
- транзакция не блокирует другие ноды и не является распределённой: параллельная запись на
  другом устройстве не отклоняется, а сливается по правилам типа;
- транзакция ограничена по числу операций и объёму; превышение возвращает `quota-exceeded`;
- транзакция над `coordinated`-объектом требует действующего lease, и при его отсутствии
  `commit` возвращает `precondition-failed`, а не выполняется «как получится».

## Конфликты

Для большинства типов конфликт разрешается слиянием и приложением не наблюдается. Наблюдаемые
случаи:

| Ситуация | Поведение |
|---|---|
| параллельная правка разных полей `document` | сливается автоматически |
| параллельная правка одного поля | побеждает запись с большим HLC, проигравшая доступна в истории версий объекта |
| удаление против правки | удаление побеждает; приложение может отследить это подпиской |
| параллельная запись `coordinated` | невозможна: запись требует lease |
| конфликт содержимого файла по `blob-ref` | обе версии сохраняются, файл переходит в `conflicted` |

Приложение может запросить у объекта список конкурирующих версий, если ему нужно показать
выбор пользователю. Автоматическая потеря версии без возможности её увидеть запрещена.

## Подписки

Подписка на изменения — основной способ построения интерфейса; опрос базы в цикле является
антипаттерном и квотируется как обычные запросы.

```text
watch(request) → change-feed
   changed(id, version)      объект изменён локально или пришёл с другой ноды
   removed(id)
   reset                     произошёл полный state transfer, нужно перечитать
```

Событие `reset` обязательно к обработке: нода, долго не выходившая на связь,
синхронизируется полным переносом состояния, а не историей операций, и в этот момент
инкрементальные события неприменимы.

## Схема и миграции

Схема коллекций объявляется в манифесте пакета и версионируется. Каждая операция несёт
версию схемы.

Правила совместимости в профиле, где ноды обновляются не одновременно:

1. **Неизвестные поля сохраняются.** Нода со старой версией пакета, получив операцию с
   новыми полями, обязана сохранить их и передать дальше без потери. Иначе обновление на
   одном устройстве уничтожало бы данные при синхронизации со вторым.
2. **Совместимые изменения не требуют миграции**: добавление поля со значением по
   умолчанию, добавление коллекции, добавление индекса.
3. **Несовместимое изменение объявляется миграцией** с новой версией схемы. Миграция
   выполняется локально на каждой ноде при первом запуске новой версии пакета.
4. **Операции с версией схемы выше поддерживаемой не применяются**, а помещаются в
   карантин: нода сохраняет их для последующего применения и показывает пользователю, что
   приложение нужно обновить на этом устройстве. Отбрасывание таких операций запрещено.
5. **Понижение версии не поддерживается.** Откат пакета возможен, но данные, записанные
   новой схемой, могут оказаться недоступны старой версии; это состояние показывается явно.

## Частичная репликация

Устройство с малым хранилищем не обязано держать все коллекции профиля. Единицей
частичной репликации является **коллекция целиком**, а не подмножество объектов по фильтру:
нода подписана на набор коллекций, объявленный приложением в манифесте как разделение на
обязательные и необязательные.

Произвольный фильтр репликации не вводится. Он превращает членство объекта в реплике в
функцию его содержимого: правка поля перемещает объект между нодами, а изменение фильтра
требует пересчёта членства по всей истории. Коллекция как единица даёт то же сокращение
объёма без этого класса задач.

Требование к [механизму репликации](../06-network/07-replication.md): mutation log ведётся
**отдельным потоком на коллекцию** с самого начала, даже пока все ноды подписаны на всё.
Иначе включение частичной репликации потребует переписывания формата журнала, а не
добавления подписки.

Первичное наполнение базы на новой ноде выражается **сводным состоянием namespace** —
тем же `status()`, что описан в [данных приложения](../03-apps/06-app-data-api.md).
Отдельного API прогресса нет.

## Квоты и объём

| Ограничение | Поведение при исчерпании |
|---|---|
| объём данных приложения в профиле | запись возвращает `quota-exceeded`, чтение работает |
| объём на конкретной ноде | вытесняется `cache`, затем нематериализованное содержимое blob |
| число объектов в коллекции | предупреждение в диагностике, затем отказ записи |
| частота записи | сглаживание, затем `quota-exceeded` с `retry-after` |

Данные класса `cache` вытесняются без предупреждения по определению; данные `replicated`
никогда не удаляются системой молча.
