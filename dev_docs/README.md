# Проектная документация K-OS

Набор design documents K-OS. Документы описывают проектируемую систему, а не текущее
состояние кода: реализация следует за документом, а не наоборот.

## Как читать

Порядок для первого знакомства:

1. [Видение](./01-overview/01-vision.md) — что такое K-OS и какое обещание она даёт пользователю.
2. [Словарь](./01-overview/02-glossary.md) — термины, используемые во всех документах.
3. [Принципы](./01-overview/03-principles.md) — сквозные правила, которым подчинены все подсистемы.
4. [Слои системы](./02-architecture/01-layers.md) — вертикаль от host adapters до приложений.
5. [Базовый стек](./02-architecture/06-base-stack.md) — эта вертикаль на примере HTTP, WebSocket и файлов.
6. Дальше — по интересующей области: приложения, права, хранилище, сеть, клиенты.

Быстрые входы по ролям:

| Интерес | Начинать с |
|---|---|
| пишу приложение | [модель приложения](./03-apps/01-app-model.md) → [данные приложения](./03-apps/06-app-data-api.md) → [каталог capabilities](./04-capabilities/02-catalog/00-index.md) |
| реализую ядро | [слои](./02-architecture/01-layers.md) → [host adapters](./02-architecture/03-host-adapters.md) → [drivers](./02-architecture/04-drivers.md) → [базовый стек](./02-architecture/06-base-stack.md) |
| занимаюсь сетью | [сеть пользователя](./06-network/01-overview.md) → [создание сети](./06-network/09-network-lifecycle.md) → [NAT](./06-network/10-nat-and-reachability.md) |
| занимаюсь интерфейсом | [системная оболочка](./09-clients/05-system-shell.md) → [frontend приложения](./03-apps/04-frontend.md) → [десктоп](./09-clients/02-desktop.md) |

## Статусы документов

Статус указан в шапке каждого документа и **только там** — карта его не дублирует, чтобы
два места не расходились. Сводка по всем документам:

```sh
grep -r --include='*.md' -m1 '^Статус:' . | sort
```

| Статус | Значение |
|---|---|
| `готов` | документ отражает принятое решение |
| `перенесено из прежних документов` | содержимое перенесено, требует ревизии и согласования формулировок |
| `направление развития` | направление за пределами основной поставки |

## Правила ведения документов

1. **Один факт живёт в одном документе.** Остальные ссылаются на него. Дублирование
   формулировок приводит к расхождению при правках.
2. **Каталог capabilities — источник истины по публичному API.** При расхождении
   с любым другим документом верен [каталог](./04-capabilities/02-catalog/00-index.md).
3. **Контракт и механизм разделены.** Разделы 03–05 описывают, что видит приложение;
   раздел 06 — как это работает между устройствами. Документ, описывающий контракт для
   разработчика приложения, живёт в разделе 03, даже если реализован сетевым слоем.
4. **Проверяемые критерии и открытые вопросы живут у владельца темы** — в разделе
   «Проверяемые критерии» или «Открытые вопросы» самого документа. Сводные списки в
   разделах 01 и 11 содержат только то, у чего нет одного владельца.
5. **Статус документа хранится в его шапке** и нигде больше.
6. **Ссылка — по имени файла, а не по номеру раздела.** Формулировки вида «см. раздел 7»
   запрещены: нумерация меняется, а такая ссылка молча становится ложной.
7. **Изменение начинается с документа**, затем меняются контракты, затем код.
8. Документ в статусе `готов` меняется осознанно: правка формулировки контракта равнозначна
   правке кода.

## Что осталось доработать

Структура, ссылки и границы документов согласованы. Незакрытым остаётся содержание документов
в статусе `перенесено из прежних документов`: их формулировки не пересматривались с момента
переноса и могут расходиться с документами в статусе `готов`. Список получается командой из
раздела «Статусы документов»; порядок ревизии — по мере того, как соответствующая подсистема
доходит до реализации.
