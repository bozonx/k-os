# Критерии корректности архитектуры

Статус: готов  
Назначение: собрать в одном месте проверяемые условия, которым обязано удовлетворять архитектурное решение, чтобы их можно было превратить в тесты.

Связанные документы: [принципы](../01-overview/03-principles.md), [детерминированная симуляция](./02-determinism-and-simulation.md), [распределение ответственности](../02-architecture/01-layers.md).


Список ниже — сквозной, системного уровня. Критерии, относящиеся к одной подсистеме, живут
в её собственном документе в разделе «Проверяемые критерии» и здесь не повторяются.
Каждый пункт формулируется так, чтобы его можно было проверить прогоном в
[симуляции](./02-determinism-and-simulation.md) или сборкой, а не обсуждением.

Архитектурное решение считается совместимым, если:

- приложение не может обойти capability API;
- package может быть установлен в profile без требования исполнять каждый component на каждом node;
- несовместимый или недоступный component получает явное placement state;
- UI можно закрыть без обязательной остановки разрешённой фоновой задачи;
- host adapter можно заменить другой платформенной реализацией без изменения service API;
- данные явно относятся к local, replicated, derived или secret классу;
- выполнение имеет явный scope относительно устройств пользователя;
- обновление package не расширяет права без подтверждения;
- добавление backend не требует отдельной установки service пользователем;
- ядро собирается и проходит тесты без `tauri` и без системной оболочки;
- любое обращение к внешнему миру проходит через host adapter, имеющий mock-реализацию;
- несколько экземпляров ядра запускаются в одном процессе и синхронизируются через симулированную сеть;
- отсутствие capability на устройстве выражается явным `unavailable`, а не деградацией поведения;
- внешний инструмент вызывается через типизированный контракт, не зависящий от способа его исполнения.
