# Архитектура K-OS

Статус: design document  
Назначение: зафиксировать базовые сущности, границы слоёв, публичные контракты и правила исполнения приложений K-OS.

## 1. Цель системы

K-OS — персональная распределённая среда приложений, работающая на устройствах пользователя. Установленные приложения и разрешённое для синхронизации состояние доступны на desktop- и mobile-устройствах. При этом каждое устройство сохраняет собственные локальные ресурсы, возможности и ограничения платформы.

Продуктовое обещание системы: с какого бы своего устройства пользователь ни начал работу, он попадает в одну и ту же среду — те же установленные приложения, те же данные, то же состояние. Способ достижения — репликация состояния, а не удалённый доступ к чужому экрану.

K-OS не пытается заменить ядро операционной системы. Это прикладная среда поверх Tauri и системных API, которая предоставляет:

- установку и управление пакетами приложений;
- единое capability API для frontend- и backend-компонентов;
- изоляцию данных и прав приложений;
- локальное и распределённое исполнение;
- синхронизацию пользовательского состояния между устройствами;
- доступ к сети, файлам, мультимедиа и оборудованию через контролируемые системные слои.

Механизмы identity, доверия между устройствами, транспорта, репликации и разрешения конфликтов описаны в [network-and-replication.md](./network-and-replication.md). Этот документ определяет публичные контракты и границы слоёв, внутри которых эти механизмы используются.

Разделение между документами: здесь — **что видит приложение**; там — **как это работает между устройствами**.

## 2. Основные принципы

1. **Пакет является единицей установки.** Пользователь устанавливает приложение целиком, а не отдельно UI и его фоновые сервисы.
2. **Компонент является единицей исполнения.** Один пакет может содержать Web UI, workers и команды с разными жизненными циклами.
3. **Frontend не имеет прямого доступа к Tauri-командам, ОС и host adapters.** Он обращается только к публичному capability API K-OS.
4. **Пользовательский код считается недоверенным.** Права выдаются пакету явно и проверяются при каждом обращении к защищённой возможности.
5. **Состояние прозрачно, исполнение и ресурсы — нет.** Данные и установленные приложения выглядят одинаково на всех устройствах пользователя. Окна, соединения, процессы и оборудование всегда принадлежат конкретному устройству, поэтому API учитывает задержки, отсутствие устройства, отмену операций и конфликты состояния.
6. **Локальное и синхронизируемое состояние разделены семантически.** Приложение выбирает класс данных, а не физический каталог.
7. **Host adapter реализует механизм, driver управляет ресурсом, service реализует функцию.** Эти роли не смешиваются.
8. **Фоновая работа преимущественно событийная.** Постоянные пользовательские процессы являются исключением и требуют отдельного разрешения.
9. **Установка и исполнение разделены.** Приложение может быть установлено в профиле пользователя, но отдельный компонент исполняется только на совместимом и выбранном runtime узле.
10. **Неоднородность узлов является частью модели.** Наличие UI, фонового исполнения, оборудования и локальных данных на конкретном устройстве не предполагается автоматически.
11. **Контракты важнее реализаций.** Публичные capability interfaces, форматы package и логические классы состояния не зависят от конкретного WebView, WASM runtime, database engine или network transport.
12. **Детерминированная тестируемость является архитектурным требованием.** Всё, что обращается к внешнему миру — время, случайность, файловая система, сеть, процессы — доступно только через host adapters с mock-реализациями. Ядро должно запускаться как несколько нод в одном процессе поверх симулированной среды.
13. **Ядро не зависит от UI.** Kernel собирается и работает headless, без Tauri и WebView. Наличие окна — свойство конкретного node, а не условие работы системы.
14. **Одно окно на устройство.** K-OS не строится вокруг оконного менеджера: системная оболочка и UI приложений сосуществуют в одном окне. Изоляция обеспечивается origin и capability gateway, а не отдельными окнами ОС.

## 3. Общая схема

```text
┌─────────────────────────────────────────────────────┐
│                       Web UI                        │
│ React / Vue / Svelte / vanilla JS / Canvas / WebGL │
└─────────────────────────┬───────────────────────────┘
                          │ capability API / RPC
┌─────────────────────────▼───────────────────────────┐
│                Application Runtime                  │
│ Web UI components │ workers │ commands │ lifecycle │
└─────────────────────────┬───────────────────────────┘
                          │ service calls
┌─────────────────────────▼───────────────────────────┐
│                  System Services                    │
│ storage │ sync │ scheduler │ media │ notifications │
└─────────────────────────┬───────────────────────────┘
                          │ capability handles
┌─────────────────────────▼───────────────────────────┐
│            Drivers / Resource Brokers               │
│ ownership │ multiplexing │ retry │ quotas │ metrics │
└─────────────────────────┬───────────────────────────┘
                          │ typed adapter contracts
┌─────────────────────────▼───────────────────────────┐
│                   Host Adapters                     │
│ files │ sockets │ BLE │ key store │ clock │ system │
└─────────────────────────┬───────────────────────────┘
                          │
               OS / network / hardware
```

Схема описывает **направление зависимостей**, а не строгие уровни: service может использовать другой service, driver — другой driver. Запрещены только обратные зависимости, то есть обращение нижнего слоя к верхнему.

Отдельно от этой вертикали существует **control plane** — набор компонентов, от которых зависит сама проверка прав и потому не может быть capability-gated:

```text
Control plane
├── Node identity и key storage
├── Profile control log (состав профиля, роли, grants)
├── Capability registry и permission evaluation
├── Package registry
└── Logging и crash reporting
```

Control plane поднимается раньше остальных services и не вызывает их. Feature services — storage, media, notifications, scheduler — используют control plane, но не наоборот.

Через все слои проходят сквозные механизмы:

- идентификация вызывающего компонента;
- permissions и capability handles;
- lifecycle и cancellation;
- журналирование, трассировка и метрики;
- управление локальным и replicated state;
- обнаружение устройств;
- установка, обновление и удаление пакетов.

### 3.1. Граница Rust, TypeScript и WebAssembly

K-OS использует гибридную архитектуру. Доверенное ядро и системный control plane работают вне WebView на Rust. WebView является клиентом системы и не владеет системным состоянием, соединениями или планировщиком.

| Область | Основная реализация |
|---|---|
| Host adapters | Rust |
| Drivers / resource brokers | Rust |
| Permissions и capability handles | Rust |
| Package manager и application runtime | Rust |
| Storage, synchronization и distributed coordination | Rust |
| Scheduler и lifecycle | Rust |
| Tauri/WebView bridge | Rust и сгенерированный TypeScript SDK |
| Системный UI | TypeScript |
| UI приложений | Любая web-технология |
| Backend приложений | Изолированный WebAssembly worker |
| Native-интеграции ОС | Rust/Tauri plugins |

Граница доверия выглядит следующим образом:

```text
Недоверенная зона
├── Web UI приложения
└── WebAssembly worker приложения
             │
             │ capability API / IPC
             ▼
Доверенная зона
├── Application Runtime
├── System Services
├── Control Plane
├── Drivers / Resource Brokers
└── Host Adapters
```

TypeScript SDK является удобной типизированной оболочкой над capability API, но не реализует безопасность. Все permissions, identity вызывающего компонента, quotas и ограничения ресурсов проверяются на стороне Rust.

Система не должна исполняться внутри browser runtime по следующим причинам:

- жизненный цикл WebView связан с окном и управляется платформой;
- JavaScript-контекст может быть перезагружен, приостановлен или выгружен;
- системные соединения и синхронизация должны жить независимо от UI;
- системные ключи и привилегированные API нельзя помещать в недоверенную среду;
- mobile и desktop предоставляют разные гарантии фонового исполнения.

Открытое desktop-окно может использоваться для оптимизации, но не является архитектурной гарантией доступности процесса.

### 3.2. Поддерживаемые платформы

Основными целевыми платформами являются:

- Linux — desktop и headless;
- Windows — desktop;
- Android — mobile.

Отдельной целью сборки является **headless Linux node** без Tauri, WebView и системного UI. Это форма запуска cloud node. Требование фиксируется на уровне зависимостей: crate `kernel` и все services не зависят от `tauri`, интеграция с окном локализована в `tauri-host`.

Архитектурные контракты не должны без необходимости зависеть от особенностей этих трёх платформ, однако текущая реализация и MVP не обязаны поддерживать Apple platforms. macOS и iOS могут быть добавлены в будущем как отдельные platform ports после проверки ограничений исполнения, распространения пакетов и фоновой работы.

Для будущей переносимости достаточно соблюдать следующие правила:

- platform-specific код находится за host adapter contracts;
- manifest позволяет объявить совместимость component с платформой и архитектурой;
- service API не содержит Linux-, Windows- или Android-specific типов;
- отсутствие capability на платформе является нормальным состоянием;
- runtime не предполагает наличие process spawning, постоянного background execution или общей POSIX filesystem.

Не требуется заранее реализовывать Apple adapters, альтернативный mobile runtime или специальные ограничения App Store. Возможность будущего port обеспечивается границами контрактов, а не неиспользуемым кодом.

### 3.3. Модель окна и размещение UI

K-OS использует **одно окно на устройство**. Мультиоконность не входит в модель: она различна на desktop и Android, усложняет lifecycle и не нужна для целевого продукта.

```text
Единственное окно устройства
├── System shell        доверенный UI: панель, launcher, переключатель, диалоги прав
└── App view            UI активного приложения, изолированный контейнер
```

Требования к контейнеру приложения:

- собственный origin на пакет, недостижимый из origin системной оболочки;
- строгий CSP, запрет загрузки удалённого исполняемого кода;
- запрет произвольной навигации и открытия внешних URL без разрешения;
- отсутствие доступа к DOM и глобальным объектам системной оболочки;
- отдельная сессия capability bridge, привязанная к origin;
- при перезагрузке или смене документа создаётся новая сессия, старые handles отзываются.

Рассматриваются два способа реализации контейнера:

| Вариант | Плюсы | Риски |
|---|---|---|
| `iframe` с отдельным origin | один WebView, одинаковое поведение на всех платформах | изоляция зависит от корректности origin-разделения внутри движка; идентификация вызывающего frame на стороне Rust требует проверки |
| Встроенный дочерний WebView | более сильная изоляция, отдельное хранилище | поддержка на Android ограничена, разное поведение платформ |

Выбор делается по результатам спайка на Android. До этого публичные контракты не должны зависеть от способа размещения: приложение работает с абстракцией `view`, а не с окном или frame.

Независимо от выбранного варианта действует правило: **container является дополнительной границей изоляции, но не основной**. Основная граница — capability gateway в Rust.

Диалоги выдачи прав, ввод учётных данных, picker файлов и подтверждение enrollment рисует только системная оболочка. Приложение не может отобразить собственный интерфейс, выглядящий как системный запрос.

## 4. Термины

### 4.1. Package

Package — подписываемая и версионируемая единица установки. Пакет содержит manifest, статические ресурсы и один или несколько исполняемых компонентов.

Пакет может содержать:

- `web-ui` — пользовательский интерфейс;
- `worker` — изолированный backend-компонент;
- `command` — короткая операция, запускаемая по запросу;
- декларации обработчиков событий;
- миграции данных;
- локализованные название, описание и иконки.

Пакет с пользовательской функцией или UI называется приложением. Пользователь устанавливает пакет один раз независимо от количества его компонентов.

### 4.2. Component

Component — единица запуска внутри package. У компонентов одного пакета могут быть разные точки входа, условия активации, ограничения ресурсов и жизненные циклы. Все они наследуют идентичность пакета, но получают только необходимые им permissions.

### 4.3. Profile, Node, Installation и Placement

`Profile` представляет персональную среду пользователя: набор установленных packages, grants, replicated namespaces и доверенных устройств.

`Node` — конкретная установка K-OS на устройстве. Node имеет собственную криптографическую identity, роль, набор доступных capabilities, platform constraints, локальное состояние и статус доступности.

Роли nodes:

| Роль | UI приложений | Исполнение workers | Ключи профиля |
|---|---|---|---|
| `device` | да | да | да |
| `cloud` | нет | да | да |
| `relay` | нет | нет | нет |

`cloud` — headless-узел для хранения, синхронизации и фонового исполнения. Он намеренно **не запускает UI приложений**: удалённый доступ к интерфейсу не нужен, потому что приложение и его состояние реплицированы и запускаются локально на том устройстве, которое пользователь взял в руки.

Подробное описание ролей, доверия и enrollment — в [network-and-replication.md](./network-and-replication.md).

`Package installation` — desired state профиля: пользователь считает package установленным в своей среде. Это не означает, что все его артефакты обязаны быть загружены и все components способны исполняться на каждом node.

`Placement` — решение о том, где может и должен исполняться component. Для component различаются состояния:

```text
available     package известен профилю
materialized  необходимые артефакты присутствуют на node
compatible    node удовлетворяет требованиям component
placed        runtime выбрал node для исполнения
running       существует конкретный execution
```

UI приложения может быть доступен на Android и desktop, а hardware worker — только на Linux node с требуемым устройством. Runtime обязан представлять такую ситуацию явно, а не имитировать локальную доступность компонента.

### 4.4. Host Adapter

Host adapter — нижний платформозависимый слой, реализующий примитив ОС или устройства.

Термин `host adapter` является единственным для этой роли. Название `platform provider` считается устаревшим и в новом коде и документации не используется. Соглашение об именовании типов: `<Domain>Adapter`, например `FileSystemAdapter`, реализации — `<Platform><Domain>Adapter`.

Набор контрактов:

| Adapter | Назначение |
|---|---|
| `FileSystemAdapter` | доступ к хранилищу устройства и внешним монтированиям |
| `SocketAdapter` | TCP/UDP/TLS-примитивы |
| `SecureKeyStoreAdapter` | платформенное хранилище ключей |
| `ClockAdapter` | wall clock, monotonic clock, таймеры |
| `RandomAdapter` | криптографическая и обычная случайность |
| `BackgroundSchedulerAdapter` | платформенные возможности фонового запуска |
| `BluetoothLeAdapter` | BLE-канал и discovery |
| `ProcessAdapter` | запуск программ хостовой ОС |
| `SystemAdapter` | сведения о системе и управление питанием |
| `NotificationAdapter` | системные уведомления |
| `MediaCaptureAdapter` | захват и воспроизведение |
| `GpioAdapter` | линии GPIO, если платформа их предоставляет |
| `SerialAdapter` | последовательные порты |

`ClockAdapter` и `RandomAdapter` выделены явно: без них невозможна детерминированная симуляция, а прямое обращение к системным часам и генератору случайных чисел из ядра запрещено.

У разных видов adapters нет общего универсального API. Общим является контракт между реализациями одного вида:

```text
FileSystemAdapter
├── LinuxFileSystemAdapter
├── WindowsFileSystemAdapter
├── AndroidFileSystemAdapter
└── MockFileSystemAdapter
```

Наличие mock-реализации для каждого контракта обязательно и является частью определения adapter, а не тестовой инфраструктурой.

Host adapter:

- выполняет низкоуровневую операцию;
- скрывает различия ОС и платформ;
- не знает о приложениях и пользователях;
- не определяет permissions и квоты;
- не управляет распределением ресурса между потребителями;
- не отвечает за синхронизацию пользовательского состояния.

Adapter также сообщает runtime свои возможности и ограничения: availability, поддерживаемые режимы, лимиты payload и streaming, background guarantees и стоимость использования ресурса, если она известна.

HTTP, WebSocket и MQTT являются переносимыми protocol engines или системными services поверх network primitives. Они не относятся к host adapters только потому, что используют платформенные API. Внешние инструменты вроде FFmpeg и Git не являются host adapters: это capability с несколькими взаимозаменяемыми backends, см. раздел о внешних инструментах.

В первой версии adapters являются встроенными Rust-компонентами ядра.

#### 4.4.1. SystemAdapter

`SystemAdapter` предоставляет сведения о хосте и ограниченный набор управляющих действий. Он разделён на две части с разным уровнем доверия.

Чтение — `system.info`:

```text
os, версия, архитектура, тип устройства
hostname и локальное имя устройства
uptime
CPU: число ядер, загрузка
память: объём, доступно
хранилище: объём, свободно по томам
питание: наличие сети, уровень батареи, режим экономии
сеть: тип подключения, metered/unmetered
locale, timezone
экран: размер, плотность, ориентация
```

Данные разделены на низкочувствительный и чувствительный поднаборы. Низкочувствительный доступен приложениям с базовым разрешением, потому что от него зависит адаптация UI и решение о тяжёлых операциях. Чувствительный — hostname, серийные номера, список сетевых интерфейсов, полный список томов — требует отдельного разрешения, поскольку служит для фингерпринтинга.

Управление — `system.power`:

```text
reboot
shutdown
suspend
отмена запланированного действия
```

Это высокодоверенная capability. Она не выдаётся обычным приложениям, требует явного подтверждения пользователя, может требовать эскалации прав в ОС и на Android недоступна. Отсутствие capability — нормальное состояние, обрабатываемое явно.

Сводка `system.info` каждого node публикуется в node capability descriptor и используется для placement, поэтому она доступна другим nodes профиля даже когда устройство офлайн — с пометкой давности.

#### 4.4.2. GpioAdapter и оборудование

Оборудование доступно не везде, и это нормальное состояние модели.

Способы поставки:

1. **Сборочная feature платформенного crate.** `host-linux` собирается с включённым `gpio`, где это имеет смысл. Сборки для платформ без поддержки просто не содержат этот код.
2. **Platform extension package.** Отдельный подписанный нативный пакет, устанавливаемый пользователем явно, с отдельным уровнем доверия. Это не обычное приложение и не WASM worker; см. раздел о расширяемости.

Для приложения оба способа выглядят одинаково: capability либо доступна на этом node, либо возвращает `unavailable`. Приложение не определяет способ поставки.

Типовой сценарий использования — удалённый: UI на телефоне управляет GPIO на Linux-ноде через delegation capability. Поэтому отсутствие оборудования на текущем устройстве не означает недоступность функции для пользователя.

### 4.5. Driver / Resource Broker

Driver, или resource broker, превращает host adapter в управляемый системный ресурс.

Driver отвечает за:

- создание и переиспользование соединений;
- владение ресурсами и их освобождение;
- multiplexing между потребителями;
- очереди, backpressure и rate limits;
- reconnect, retry и timeout policy;
- сбор метрик и статистики;
- проверку валидности, scope и ownership выданных capability handles;
- выдачу ограниченных capability handles;
- платформенные ограничения времени жизни ресурса.

Например, socket host adapter открывает низкоуровневое соединение. Network broker управляет соединением и backpressure, а MQTT service маршрутизирует подписки и реализует семантику протокола.

Приложение не получает прямую ссылку на driver. Оно получает непрозрачный handle:

```rust
let connection = ctx
    .capabilities()
    .mqtt()
    .connect(options)
    .await?;
```

Handle связан с package ID, component ID, permissions и временем жизни владельца. Освобождение владельца закрывает или возвращает ресурс в управляемый pool.

Решение о выдаче права принимает централизованный authorization/capability service на входе в системный API. Driver не интерпретирует manifest и пользовательские grants самостоятельно. Повторная проверка ограничений handle в driver является defense-in-depth и защитой конкретного ресурса.

В первой версии drivers являются встроенными. Устанавливаемые native drivers откладываются до появления подтверждённых сценариев нового оборудования или протоколов.

### 4.6. Service

Service — высокоуровневая системная функция, построенная поверх drivers и других services.

Services делятся на две группы с разными правилами запуска и зависимостей.

**Control plane** — то, от чего зависит проверка прав. Эти компоненты не могут быть capability-gated и не вызывают feature services:

- node identity и key storage;
- profile control log: состав профиля, роли nodes, grants;
- capability registry и permission evaluation;
- package registry;
- logging и crash reporting.

**Feature services** — системные функции, доступные компонентам через capability API:

- application runtime;
- package manager;
- storage и VFS;
- synchronization;
- secrets;
- scheduler;
- notifications;
- media;
- внешние инструменты: transcode, vcs;
- telemetry.

Различие существенно: попытка проверить право на запись в лог через сервис, который сам пишет лог, даёт цикл. Порядок запуска в разделе о загрузке системы следует из этого разделения.

Service является runtime-ролью, но не отдельной обязательной единицей установки для пользователя. Пользовательский backend входит в package приложения как worker.

Системные services запускаются ядром в определённом порядке и могут иметь расширенные внутренние права. Пользовательский worker не становится системным service и не получает системных прав из-за фонового режима работы.

### 4.7. Worker

Worker — backend-компонент пользовательского package. Он предназначен для сложной логики, фоновой обработки, интеграций и реакций на события.

Рекомендуемый формат worker — WebAssembly Component с явно импортированными capability interfaces. Rust является основным рекомендуемым языком, но контракт не должен зависеть от Rust ABI и в дальнейшем может поддерживать другие компилируемые в WebAssembly языки.

Worker:

- не имеет прямого доступа к ОС;
- использует только объявленные capabilities;
- может запускаться без открытого окна;
- должен поддерживать cancellation и ограничение времени работы;
- сохраняет checkpoint для возобновления длительных задач;
- не предполагает, что процесс будет жить постоянно.

## 5. Компоненты приложения

### 5.1. Web UI

Web UI загружается в изолированный контейнер внутри единственного окна устройства и живёт, пока существует связанный с ним view. Разработчик может использовать любую web-технологию, включая WebGL и Canvas.

Web UI получает K-OS API через контролируемый bridge. Прямой произвольный вызов Tauri commands запрещён. Идентичность вызывающего package и component runtime определяет из сессии контейнера, а не из переданных приложением данных, поэтому приложение не может выдать себя за другое.

Web UI не является обязательным компонентом: на cloud node он не запускается вовсе, и приложение обязано это допускать.

Web UI предназначен для:

- отображения интерфейса;
- обработки пользовательского ввода;
- подписки на события;
- вызова команд и services;
- работы с изолированными данными через K-OS API.

### 5.2. Worker

Обычный worker запускается событием или запросом, выполняет работу и завершается. Возможные причины активации:

- запуск приложения;
- пользовательская команда;
- изменение данных;
- сетевое событие;
- системное уведомление;
- расписание;
- открытие файла или URL;
- запрос другого разрешённого компонента.

### 5.3. Background worker

Background worker может продолжить работу после закрытия UI, пока существует разрешённая задача или выданный runtime lease.

Lease ограничивает:

- максимальную продолжительность;
- CPU и память;
- сетевую активность;
- частоту пробуждений;
- условия работы от батареи;
- поведение при переходе устройства в sleep.

Гарантии зависят от платформы. Код не должен предполагать, что desktop- и mobile-устройства дают одинаковое время фонового исполнения.
Lease выражает разрешение и запрошенный runtime budget, но не обещание запуска в точное время или непрерывного исполнения. Android host adapter отображает системные background opportunities в общую модель scheduler.

### 5.4. Отказ от пользовательских daemons

Daemon не входит в публичную модель компонентов приложения. K-OS не обещает пользовательскому коду постоянно живущий процесс, потому что такая гарантия несовместима с жизненным циклом мобильных ОС.

Сценарии, обычно требующие daemon, реализуются через:

- event-driven workers;
- durable jobs;
- периодические задания scheduler;
- подписки на системные события;
- ограниченные background leases;
- checkpoints и восстановление работы;
- платформенные push/background events.

Постоянные соединения принадлежат системным drivers и services, а не пользовательским workers. Например, системный MQTT service поддерживает соединение и сохраняет входящие события, после чего scheduler активирует подписанный на них worker приложения. При остановке процесса соединения и события восстанавливаются согласно системной политике.

Внутренние долгоживущие системные services допустимы, но они не являются устанавливаемыми пользовательскими daemons.

### 5.5. Command

Command — короткая stateless или ограниченная по времени операция. Она может вызываться из UI, другим компонентом или системой. Command подходит для операций, которым не нужен собственный долгоживущий lifecycle.

## 6. Жизненный цикл

| Компонент | Жизненный цикл |
|---|---|
| `web-ui` | Пока существует view приложения в окне устройства |
| `worker` | От события до завершения обработчика |
| `background-worker` | Пока активна задача и runtime lease |
| `command` | Один запрос — одно ограниченное выполнение |
| `system-service` | Управляется ядром |

Пример фонового исполнения:

```text
Событие
   ↓
Runtime проверяет manifest и permissions
   ↓
Запускает worker
   ↓
Worker запрашивает background lease при необходимости
   ↓
Выполняет работу и сохраняет checkpoint
   ↓
Завершается или возобновляется по следующему событию
```

Каждое выполнение получает deadline и cancellation token. Принудительная остановка компонента не должна повреждать подтверждённое состояние.

## 7. Manifest пакета

Предварительный концептуальный пример:

Права и placement объявляются **внутри** описания компонента, а не отдельными таблицами верхнего уровня: разнесение приводит к рассинхронизации при редактировании и упрощает случайное расширение прав.

```toml
[package]
id = "com.example.music"
version = "1.0.0"

[package.compatibility]
platforms = ["linux", "windows", "android"]

[[components]]
id = "main-ui"
type = "web-ui"
entry = "ui/index.html"

  [[components.capabilities]]
  name = "storage.replicated.read-write"
  version = "^1"

  [[components.capabilities]]
  name = "events.subscribe"
  version = "^1"

  [[components.capabilities]]
  name = "command.invoke"
  version = "^1"
  scope = ["scan-library"]

[[components]]
id = "library-indexer"
type = "worker"
entry = "workers/indexer.wasm"
activation = ["app-start", "files-changed"]

  [components.placement]
  scope = "per-user"
  requires = ["compute.background"]
  prefers = ["power.ac", "network.unmetered"]
  remote = "allowed"

  [[components.capabilities]]
  name = "storage.replicated.read-write"
  version = "^1"

  [[components.capabilities]]
  name = "files.user.read"
  version = "^1"
  optional = false

  [[components.capabilities]]
  name = "media.probe"
  version = "^1"
  optional = true
  reason = "чтение тегов и длительности аудиофайлов"

[[components]]
id = "scan-library"
type = "command"
entry = "workers/indexer.wasm#scan"
```

Свойства модели manifest:

- глобально уникальный package ID и стабильные component IDs;
- capabilities объявляются на уровне компонента с **версией контракта** и, где применимо, со `scope`, ограничивающим область действия;
- `optional = true` означает, что компонент обязан работать при отказе в этом праве. Обязательные права, в которых отказано, переводят компонент в состояние `not-permitted`, а не запускают его с урезанной функциональностью;
- `reason` — человекочитаемое обоснование, показываемое в диалоге выдачи прав. Для чувствительных capabilities обязательно;
- декларативные activation events;
- декларация поддерживаемых платформ и platform-specific варианты артефактов при сохранении общего component contract;
- `placement` для каждого компонента: требования, предпочтения, допустимость удалённого исполнения;
- поведение при отсутствии совместимого runtime;
- декларация миграций данных;
- декларация потребности в материализации данных, влияющая на selective sync;
- криптографическая подпись пакета.

Точный формат manifest фиксируется отдельным документом вместе с каталогом capabilities.

## 8. Capability API и permissions

Capability — ограниченное право выполнить класс операций. Permissions из manifest описывают запрашиваемые права, а runtime policy определяет, какие из них реально выданы на конкретном устройстве.

### 8.1. Пространство имён capabilities

Имена capabilities строятся как `<домен>.<область>.<операция>`. Для данных действует однозначное соответствие «namespace — путь VFS — capability», зафиксированное таблицей в разделе о хранилищах. Расхождение между этой таблицей и любым другим местом документа считается дефектом.

```text
storage.local.read-write
storage.replicated.read-write
storage.cache.read-write
secrets.read-write

files.app.read-write
files.user.read
files.user.write
files.external.<mount-id>.read
files.external.<mount-id>.write

net.http:api.example.com
net.ws:example.com
net.socket.tcp
mqtt.connect

events.subscribe
events.publish
command.invoke

media.probe
media.transcode
media.capture

vcs.git

system.info
system.info.detailed
system.power

process.exec:<program>
process.shell

notifications.show
background.run
device.location
gpio.line
serial.port

remote.delegate
```

Разделены две ортогональные оси, которые ранее смешивались в имени `storage.private`:

- **scope** — реплицируются ли данные: `local` или `replicated`;
- **visibility** — видны ли данные другим пакетам: по умолчанию все namespaces приватны для пакета, доступ другому пакету выдаётся отдельной capability.

Каждая capability имеет версию контракта. Полный каталог с сигнатурами интерфейсов, таксономией ошибок, правилами версионирования и таблицей доступности по платформам находится в [capabilities.md](./capabilities.md). Этот каталог является источником истины: из него выводятся WIT, TypeScript SDK, имена прав в manifest и contract tests. При расхождении верен каталог.

### 8.2. Контекст вызова

Каждый защищённый вызов содержит или восстанавливает следующий контекст:

```text
profile ID
node ID
package ID
component ID
execution ID
granted capabilities
trace ID
deadline
cancellation token
```

Проверка производится на границе системного API и не полагается только на скрытие методов во frontend SDK.

Capability handle должен быть:

- непрозрачным для приложения;
- ограниченным конкретным ресурсом и операциями;
- отзывным;
- привязанным к владельцу;
- автоматически освобождаемым;
- непригодным для передачи другому package без явного системного механизма.

Модель различает:

- permission, запрошенный package в manifest;
- grant, подтверждённый пользователем или system policy на конкретном node;
- runtime capability, выданную конкретному execution;
- resource handle, ограниченный конкретным объектом и операциями;
- delegation capability для явно разрешённого локального или удалённого вызова.

Право компонента на локальный ресурс не становится правом удалённого node автоматически. Delegation всегда ограничивает получателя, операции, scope, deadline и возможность дальнейшей передачи.

## 9. Взаимодействие services и компонентов

Компоненты находят services через service registry и типизированные контракты. Они не получают произвольные Rust-объекты и не обращаются напрямую к внутренним менеджерам.

Концептуальный локальный API:

```rust
let media = ctx.services().require::<MediaService>(">=1.2")?;
let result = media.transcode(request).await?;
```

Контракт не должен зависеть от нестабильного Rust ABI. Для разных границ могут использоваться:

- WIT и WebAssembly Component Model для workers;
- сериализуемые versioned messages для IPC/RPC;
- Protobuf, CBOR или MessagePack со схемой;
- generated TypeScript API для Web UI.

Локальный и удалённый вызов могут иметь одинаковые типы запроса и ответа, но API обязан сохранять сетевую семантику: timeout, cancellation, недоступность узла, повтор и idempotency.

## 10. Состояние и хранилища

### 10.1. Namespaces

Приложение работает с логическими namespaces, а не с внутренней структурой каталогов:

```text
app.data.local        не реплицируется, принадлежит этому node
app.data.replicated   реплицируется между nodes профиля
app.cache             не реплицируется, вытесняемо в любой момент
app.secrets           секреты приложения
app.files             файлы приложения в VFS
user.files            пользовательские файлы в VFS
```

Соответствие namespace, пути VFS и capability однозначно и фиксируется таблицей:

| Namespace | Путь VFS | Capability |
|---|---|---|
| `app.data.local` | `/data/<pkg>/local/` | `storage.local.read-write` |
| `app.data.replicated` | `/data/<pkg>/replicated/` | `storage.replicated.read-write` |
| `app.cache` | `/data/<pkg>/cache/` | `storage.cache.read-write` |
| `app.files` | `/data/<pkg>/files/` | `files.app.read-write` |
| `app.secrets` | — | `secrets.read-write` |
| `user.files` | `/user/` | `files.user.read`, `files.user.write` |

Секреты не имеют пути в VFS: они хранятся отдельно и не адресуются как файлы.

### 10.2. Классы состояния

| Класс | Реплицируется | Назначение | Пример |
|---|---|---|---|
| `ephemeral` | нет | состояние процесса | открытое соединение |
| `device-local` | нет | данные конкретного устройства | раскладка панели, выбранное аудиоустройство |
| `replicated` | да | синхронизируемые данные | настройки, документы |
| `derived` | нет | восстанавливаемые данные | индекс поиска, thumbnails |
| `secret` | да, в зашифрованном виде | переносимые секреты | API token |
| `device-bound-secret` | нет, никогда | секрет конкретного устройства | приватный ключ node |
| `file` | метаданные да, содержимое по политике | файлы | документы и медиа |

`derived` реплицировать не следует: восстановить дешевле, чем синхронизировать. Приложение обязано уметь пересобрать этот класс с нуля.

### 10.3. Инварианты

**Реплицируется операция, а не файл базы данных.** Файлы локального движка хранения никогда не синхронизируются побайтово между nodes. Это относится и к базам приложений, и к базам самой системы.

**Подтверждённая replicated mutation атомарна.** Локальное изменение и durable запись для будущей репликации сохраняются в одной транзакции. Реализация не имеет права сначала изменить базу, а затем ненадёжно уведомить sync service.

**Публичный storage API не сводится к одному CRUD.** Приложение выбирает семантику данных — документ, множество, счётчик, журнал, координируемая запись — и consistency profile, но не алгоритм репликации.

Физическое хранение является деталью реализации storage service и может измениться без изменения API приложений.

`localStorage`, IndexedDB и browser cache:

- считаются локальными и несинхронизируемыми;
- не должны использоваться для основного состояния;
- могут очищаться вместе с данными контейнера;
- допускаются для временной оптимизации UI.

Основным способом хранения является асинхронное K-OS storage API.

### 10.4. Виртуальная файловая система

VFS — единое платформонезависимое пространство имён, одинаковое на всех nodes профиля. Это не общий POSIX-каталог: одинаково выглядит дерево, а не физическое размещение содержимого.

```text
/apps/<package-id>/            артефакты пакета, только чтение, реплицируются
/data/<package-id>/
        replicated/            app.data.replicated
        local/                 app.data.local, своё на каждом node
        cache/                 app.cache, вытесняемо
        files/                 app.files
/user/                         пользовательские файлы: документы, медиа
/profile/                      состояние профиля: реестр пакетов, настройки, grants
/nodes/<node-id>/              локальные пространства конкретных nodes
/mnt/<mount-id>/               внешние монтирования за пределами VFS
```

Приложение по умолчанию видит только своё поддерево в `/data/<own-package-id>/`. Всё остальное требует отдельной capability.

#### Правила путей

Пути платформонезависимы, поэтому ограничения являются объединением ограничений всех целевых платформ:

- разделитель `/`, абсолютные пути;
- кодировка UTF-8 в нормализации NFC;
- регистр значим и сохраняется, но два имени в одном каталоге, различающиеся только регистром, запрещены — иначе дерево разойдётся между Linux и Windows;
- запрещены управляющие символы и `\ / : * ? " < > |`;
- запрещены зарезервированные имена Windows: `CON`, `PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9`;
- запрещены завершающие точка и пробел;
- ограничение длины компонента имени и общей длины пути объявляется в контракте.

Проверка выполняется при записи, а не при чтении: недопустимое имя не должно попадать в реплицируемые метаданные.

#### Идентичность файла

Файл имеет стабильный идентификатор, не зависящий от пути. Имя и родительский каталог являются атрибутами. Переименование и перемещение — операции над метаданными, а не удаление с созданием: открытый handle и ссылки остаются валидными.

#### Состояния файла

Полное дерево видно на любом node, но содержимое присутствует не везде:

| Состояние | Значение |
|---|---|
| `materialized` | содержимое доступно локально |
| `metadata-only` | известны только метаданные |
| `fetching` | содержимое загружается |
| `partial` | доступна часть содержимого |
| `evicted` | содержимое было локально и вытеснено |
| `conflicted` | существуют параллельные версии |
| `unavailable` | ни один доступный node не содержит содержимого |

Это состояние является частью публичного API. Приложение обязано его обрабатывать, а не считать, что чтение всегда мгновенно.

#### Семантика чтения

Режим доступа задаётся явно при открытии:

| Режим | Поведение |
|---|---|
| `auto` | при отсутствии содержимого запускает материализацию и ожидает в пределах deadline; при недостижимости источника возвращает `unavailable` |
| `require-local` | немедленная ошибка, если файл не материализован |
| `stream` | чтение диапазонов без полной материализации |

Дополнительно доступны `prefetch` и `pin`. Pin закрепляет путь или поддерево на конкретном node и защищает его от вытеснения в пределах квоты.

Режим по умолчанию — `auto`. Скрытая блокирующая загрузка без deadline не допускается ни в одном режиме.

#### Доступ за пределы VFS

Доступ к хостовой файловой системе возможен только через явное внешнее монтирование:

- монтирование создаётся действием пользователя: системный picker каталога или настройка;
- каждое монтирование получает собственный идентификатор и собственные capabilities `files.external.<mount-id>.read|write`;
- содержимое внешних монтирований не реплицируется; между nodes передаётся только сам факт существования монтирования, чтобы пользователь понимал, где лежат данные;
- платформа может отозвать доступ в любой момент, что является нормальным состоянием, а не ошибкой;
- на Android внешний доступ выражается идентификаторами SAF, а не путями, и adapter обязан представлять это ограничение явно, не имитируя POSIX-семантику.

Механизм репликации метаданных, blob store, selective sync и разрешение конфликтов описаны в [network-and-replication.md](./network-and-replication.md).

## 11. Распределённое исполнение

Состояние приложения может быть общим между устройствами, но процессы, views, соединения и аппаратные ресурсы всегда принадлежат конкретному устройству.

Cloud node участвует в исполнении наравне с остальными, но никогда не выбирается для компонентов типа `web-ui`. Компонент, требующий UI, размещается только на `device` node.

Для jobs и workers manifest или scheduler задаёт execution scope. Scope описывает требуемую кардинальность, а placement отдельно выбирает подходящий node:

| Scope | Семантика |
|---|---|
| `per-view` | Отдельно для каждого открытого view приложения |
| `per-node` | Один экземпляр на устройстве |
| `per-user` | Логически один экземпляр пользователя |
| `cluster-singleton` | Одно активное выполнение среди устройств |
| `leader-elected` | Выполнение на выбранном устройстве-лидере |

Placement учитывает обязательные `requires`, необязательные `prefers`, platform compatibility, локальность необходимых данных и разрешение на remote execution. Отсутствие подходящего node возвращает явное состояние `not-placed`, а не запускает component с урезанными неоговорёнными возможностями.

Распределённый scheduler должен учитывать:

- доступность устройства;
- необходимые capabilities и оборудование;
- online/offline состояние;
- питание и батарею;
- idempotency задачи;
- lease и потерю лидера;
- checkpoint и повтор выполнения.

Распределённая операция не получает гарантию exactly-once по умолчанию. Обработчики должны проектироваться как idempotent либо использовать системные механизмы дедупликации.

### 11.1. Время

Планирование и координация опираются на явную модель времени, описанную в [network-and-replication.md](./network-and-replication.md). Существенные для прикладного API следствия:

- порядок событий определяется причинностью и hybrid logical clock, а не системными часами устройства;
- таймауты и leases измеряются монотонными часами измеряющего узла; сравнение локальных настенных часов с удалёнными запрещено;
- безопасность единственного владельца обеспечивает fencing token, а не истечение lease;
- пользовательские расписания хранятся в гражданском времени с timezone и вычисляются на исполняющем узле;
- задача scope `per-user` дедуплицируется по ключу срабатывания, иначе выполнится на каждом устройстве;
- время доступно коду только через `ClockAdapter`.

### 11.2. Размещение распределённой координации

Распределённая инфраструктура реализуется системными Rust services и работает независимо от WebView и приложений:

```text
Distributed Runtime
├── Node Identity
├── Profile Control Log
├── Peer Discovery
├── Secure Transport
├── Replication
├── Blob Transfer
├── Lease Service
├── Distributed Scheduler
└── Event Delivery
```

Выбор Rust связан не с тем, что распределённые алгоритмы невозможно реализовать на TypeScript, а с требованиями к жизненному циклу, владению ключами и соединениями, устойчивому локальному хранилищу и восстановлению после аварии.

Не следует вводить строгий consensus для каждой функции. Механизм выбирается по требуемой семантике:

- CRDT или version vectors — для части replicated state;
- lease с fencing token — для временного единственного владельца;
- leader election — когда работу должно координировать одно устройство;
- строгий consensus — только для данных, которым действительно необходим единый порядок изменений.

Lease, защищающий внешний side effect, используется вместе с fencing token, который проверяет владелец ресурса. Само по себе истечение lease не способно остановить старого лидера после network partition.

Предварительные границы network layer и replication вынесены в [network-and-replication.md](./network-and-replication.md).

Удалённые jobs должны быть idempotent или использовать ключи дедупликации. Потеря устройства либо lease рассматривается как нормальная ситуация, а не исключительное завершение всей системы.

## 12. Расширяемость, внешние инструменты и команды хоста

### 12.1. Модель расширяемости

Rust dynamic libraries (`.so`, `.dll`, `.dylib`) не являются основным форматом пользовательских расширений, потому что:

- Rust ABI не гарантирует стабильность между версиями компилятора;
- библиотека исполняется внутри процесса и может завершить всё приложение;
- сложно обеспечить sandbox и контроль ресурсов;
- нужны отдельные сборки под платформы и архитектуры;
- обновление загруженного кода усложняет lifecycle;
- мобильные платформы ограничивают загрузку нового исполняемого кода.

Принята следующая модель расширяемости:

| Механизм | Назначение | Доверие |
|---|---|---|
| Встроенный Rust crate | host adapters, drivers, системные services | часть ядра |
| WebAssembly Component | пользовательские workers и безопасные расширения | недоверенное |
| Platform extension package | оборудование и протоколы, не вошедшие в сборку | высокое, отдельная подпись |
| Sidecar process | тяжёлые native-инструменты там, где платформа это позволяет | ограниченное, деталь реализации capability |
| Dynamic library со стабильным C ABI | только доверенные платформенные расширения в будущем | высокое |

**Platform extension package** — отдельный подписанный нативный пакет, добавляющий host adapter или driver: например, поддержку конкретной шины или промышленного протокола. Он устанавливается явным действием пользователя с отдельным подтверждением, распространяется по платформам отдельно и не является обычным приложением. Такое расширение не получает автоматически прав основного процесса K-OS и объявляет, какие capabilities оно предоставляет.

Sidecar в этой таблице — не самостоятельный механизм расширяемости для приложений, а один из возможных backends системной capability. Приложение никогда не получает право «запустить sidecar» как таковое.

### 12.2. Внешние инструменты: FFmpeg, Git и подобные

Ранняя формулировка относила FFmpeg и Git к sidecar-процессам. Это противоречит требованию платформонезависимости: на Android запуск произвольных процессов недоступен, а оба инструмента объявлены базовыми возможностями системы.

Принятая модель: **внешний инструмент — это capability с несколькими взаимозаменяемыми backends**.

```text
capability: media.transcode / media.probe / vcs.git
        │
        ├── in-process library      предпочтительный backend
        ├── bundled sidecar         desktop, где библиотека неполна
        └── remote execution        исполнение на другом node профиля
```

| Capability | Desktop | Android | Fallback |
|---|---|---|---|
| `media.probe`, `media.transcode` | связанная библиотека или поставляемый бинарь | связанная библиотека сборки для мобильной платформы | удалённое исполнение на capable node |
| `vcs.git` | библиотечная реализация в процессе | та же библиотечная реализация | удалённое исполнение |

Правила:

1. **Публичный API — типизированное описание задачи, а не строка аргументов.** Транскодирование описывается входом, выходом, контейнером, кодеками и структурированными параметрами; операция Git — типом операции, ссылками и путями. Только так один и тот же вызов работает на всех backends.
2. **Сырые аргументы — отдельная capability.** Escape hatch вида «передать произвольные аргументы FFmpeg» существует, но требует отдельного разрешения, и компонент, использующий его, обязан объявить платформы, на которых он работает. Переносимость таких вызовов не гарантируется.
3. **Выбор backend делает runtime, а не приложение.** Приложение может узнать доступные возможности и ограничения, но не выбирает способ исполнения.
4. **Недоступность backend — явное состояние.** Если ни локального, ни удалённого backend нет, вызов возвращает `unavailable`, а не деградирует молча.

Тот же принцип применяется к любому будущему тяжёлому инструменту: сначала capability и типизированный контракт, только потом вопрос, чем он реализован на конкретной платформе.

### 12.3. Исполнение команд хостовой ОС

Запуск программ хоста нужен для системных задач и для приложений-инструментов, но это самая опасная возможность в системе. Модель строится вокруг `ProcessAdapter`.

#### Контракт запуска

```text
program            имя или путь исполняемого файла
args               массив аргументов, отдельными элементами
env                явный allowlist переменных окружения
cwd                путь VFS или внешнего монтирования
stdin/stdout/stderr потоки с backpressure
timeout            обязателен
cancellation       завершение процесса при отмене
```

Правила:

1. **Аргументы передаются массивом, а не строкой.** Отсутствие промежуточной оболочки исключает инъекцию через аргументы. Это поведение по умолчанию и единственное переносимое.
2. **Окружение не наследуется.** Передаются только явно перечисленные переменные, чтобы токены и настройки хоста не утекали в дочерний процесс.
3. **Рабочий каталог ограничен.** `cwd` должен находиться внутри доступного компоненту поддерева VFS или внутри разрешённого внешнего монтирования.
4. **Таймаут обязателен**, а отмена завершает процесс и его группу.

#### Разрешения

```text
process.exec:<program>   запуск конкретной программы
process.exec:*           запуск произвольных программ, класс «администрирование»
process.shell            исполнение строки через оболочку хоста
```

`process.exec` не выдаётся приложениям по умолчанию ни в каком виде. `process.exec:*` и `process.shell` относятся к классу администрирования, требуют отдельного явного подтверждения и не могут быть получены обновлением пакета без согласия пользователя.

`process.shell` выделен намеренно: исполнение строки через оболочку является платформозависимым и подверженным инъекциям. Оболочка выбирается adapter по платформе — `sh` на Linux, `cmd` или PowerShell на Windows — и различие **не скрывается**: компонент, использующий `process.shell`, обязан объявить поддерживаемые платформы. Приложениям, которым нужна переносимость, следует использовать `process.exec` с массивом аргументов.

#### Платформенные ограничения

На Android `process.exec` недоступен для произвольных программ. Это нормальное состояние: capability возвращает `unavailable`, и приложение обязано это обработать. Внешние инструменты вроде FFmpeg и Git на Android доступны не через `process.exec`, а через собственные capabilities из предыдущего раздела.

#### Удалённое исполнение команд

Команда может быть выполнена на другом node профиля через delegation capability. Это основной способ для сценария «телефон просит домашний Linux-узел выполнить операцию».

Разрешение проверяется дважды: у инициатора должно быть право делегировать, у целевого node — собственное правило, разрешающее этому пакету исполнять эту программу здесь. Односторонней проверки недостаточно: иначе компрометация одного устройства даёт исполнение кода на всех остальных.

#### Системный терминал

Терминал K-OS является системным приложением с capability класса администрирования. Он не служит обходным путём для обычных приложений: наличие терминала в системе не означает, что приложение может запустить команду через него.

## 13. Изоляция и безопасность

Минимальные границы безопасности:

- каждый package имеет отдельный namespace данных;
- Web UI работает с ограниченным bridge;
- workers исполняются в WebAssembly sandbox;
- системные capabilities запрещены по умолчанию;
- доступ к пользовательским файлам выдаётся через picker, scope или permission;
- credentials передаются через secrets service, а не хранятся в manifest;
- сетевые права могут ограничиваться доменами и протоколами;
- фоновые права выдаются отдельно;
- межпакетные вызовы разрешаются обеими сторонами и системой;
- удалённые вызовы аутентифицируют node и проверяются политикой обеих сторон;
- запуск программ хоста и доступ за пределы VFS относятся к отдельному классу прав;
- package update не может незаметно расширить permissions.

### 13.1. Изоляция Web UI

Система использует одно окно на устройство, поэтому изоляция достигается не разделением окон, а разделением origin и сессий внутри окна.

Каждое приложение загружается в собственный контейнер с уникальным origin, выделяемым системой на основании package ID. К контейнеру применяются:

- строгий Content Security Policy, формируемый доверенным runtime;
- запрет произвольных Tauri commands;
- ограничение навигации и открытия внешних URL;
- отдельная сессия capability bridge;
- отсутствие доступа к DOM и глобальному контексту системной оболочки;
- получение package ID и component ID из доверенного runtime-контекста.

**Идентификация вызывающего.** Frontend не передаёт собственный package ID для доступа к ресурсам. Публичный вызов имеет форму `storage.read(path)`, а namespace определяется Rust runtime по сессии контейнера. Переданный приложением идентификатор не является доказательством его личности.

Требование к реализации bridge: Rust-сторона должна устанавливать соответствие «канал → package» способом, который приложение не может подделать. Допустимые механизмы — секрет сессии, внедряемый доверенным runtime при загрузке документа и не доступный другим origin, либо проверяемый источник запроса на стороне custom protocol. Механизм фиксируется по результатам спайка вместе с выбором способа размещения контейнера.

**Контейнер не является основной границей безопасности.** Размещение WebView и iframe по процессам ОС зависит от платформы и версии движка, поэтому изоляция контейнера считается защитой в глубину. Основной security boundary — capability gateway в Rust: даже при полной компрометации frontend-кода приложение получает только выданные ему capabilities.

Для пользовательских UI используется один минимальный K-OS bridge entry point вместо набора произвольных Tauri commands. Tauri capabilities применяются как внешний статический слой защиты системного окна, а динамические package permissions и caller identity принадлежат runtime K-OS.

Загрузка remote executable scripts, произвольная навигация и наследование системного origin запрещены. После навигации или перезагрузки создаётся новая сессия, а старые handles отзываются.

**Разделение экранных ролей.** Диалоги выдачи прав, ввод учётных данных, picker файлов и подтверждение добавления устройства рисует исключительно системная оболочка, вне контейнера приложения. Приложение не может отобразить интерфейс, неотличимый от системного запроса.

### 13.2. Изоляция workers

Основным execution backend приложения является WebAssembly Component. Worker получает только явно импортированные K-OS interfaces и по умолчанию не получает полного доступа WASI к сети, процессам или файловой системе.

Runtime ограничивает:

- память и объём вычислений;
- длительность и количество одновременных запусков;
- сетевые направления;
- доступный объём хранилища;
- частоту активации;
- набор импортированных capabilities.

Язык реализации worker не является частью security model. Rust рекомендуется первым, но в будущем может поддерживаться любой язык, способный собрать совместимый WebAssembly Component.

Публичный component contract не зависит от конкретного WASM engine. Runtime в будущем может использовать совместимый локальный engine, встроенную доверенную реализацию или remote execution proxy. Это позволяет добавлять новые platform ports без изменения package и service contracts; реализовывать такие backends заранее не требуется.

Permissions определяют доступ, а quotas — объём использования разрешённого доступа. Это разные механизмы и оба применяются runtime.

## 14. Ошибки, отмена и наблюдаемость

Все асинхронные контракты должны поддерживать:

- типизированные ошибки;
- deadline;
- cancellation;
- backpressure для потоков;
- ограниченную retry policy;
- trace ID;
- безопасное журналирование без утечки секретов.

Driver собирает технические метрики ресурса, service — метрики операций, application runtime — метрики жизненного цикла. Приложению доступна только разрешённая ему часть диагностических данных.

## 15. Тестируемость

Требования этого раздела являются архитектурными ограничениями, а не рекомендациями по тестированию. Детерминированную симуляцию распределённой системы невозможно добавить позднее без переписывания ядра, поэтому ограничения фиксируются до начала реализации.

### 15.1. Запреты в коде ядра

В `kernel`, services, drivers и app-runtime запрещены:

- прямое обращение к системным часам вместо `ClockAdapter`;
- прямое использование генератора случайных чисел вместо `RandomAdapter`;
- прямые вызовы файловой системы, сокетов, процессов и платформенных API в обход host adapters;
- глобальное изменяемое состояние и синглтоны, препятствующие запуску нескольких экземпляров ядра в одном процессе;
- скрытые фоновые задачи, не привязанные к явному scheduler и не останавливаемые при остановке экземпляра.

Соблюдение проверяется автоматически в CI, а не только на code review.

### 15.2. Уровни проверки

| Уровень | Что проверяет |
|---|---|
| Contract tests | общий набор тестов для всех реализаций одного host adapter, включая mock |
| Компонентные тесты | service или driver поверх mock adapters |
| Симуляция кластера | несколько нод в одном процессе на симулированных сети и времени |
| Платформенные тесты | реальные adapters на целевых ОС |
| End-to-end | системная оболочка, установка пакета, запуск компонентов |

Contract tests существенны: они гарантируют, что Linux-, Windows-, Android- и mock-реализации ведут себя одинаково там, где контракт это обещает, и явно расходятся там, где различие объявлено.

### 15.3. Симуляция

Симуляционный харнесс запускает N нод в одном процессе и управляет:

- виртуальным временем и таймерами;
- задержкой, потерей, дублированием и переупорядочиванием сообщений;
- разделением сети и восстановлением связи;
- падением и перезапуском node в произвольный момент;
- расхождением часов между нодами;
- заполнением диска и ошибками записи;
- повреждением blob и обрывом передачи.

Прогон детерминирован по seed. Найденный сбой воспроизводится по номеру seed, что делает отладку распределённых дефектов возможной.

### 15.4. Проверяемые инварианты

- сходимость реплик после восстановления связи;
- отсутствие потери подтверждённой mutation при падении в любой точке;
- отсутствие двойного внешнего side effect без корректного fencing token;
- невозможность обойти capability gateway ни из UI, ни из worker;
- невозможность получить admin-полномочия без валидной цепочки подписей;
- невозможность материализовать файл с содержимым, не соответствующим хешу;
- освобождение всех capability handles при завершении владельца.

## 16. Загрузка системы

Порядок запуска следует из разделения на control plane и feature services:

1. platform runtime и конфигурация устройства;
2. logging и crash reporting;
3. node identity и key storage;
4. profile control log: состав профиля, роли, grants;
5. permissions и capability registry;
6. host adapters;
7. drivers/resource brokers;
8. storage, VFS и blob store;
9. package registry и application runtime;
10. network layer, synchronization и координация nodes;
11. scheduler и activation manager;
12. системная оболочка и пользовательские компоненты.

Пункты 1–5 составляют control plane и не зависят от последующих. Пункт 12 отсутствует на cloud node: ядро обязано завершать загрузку и работать без него.

Каждый этап объявляет зависимости явно. Циклические зависимости между services запрещены либо разрываются через события и отложенную активацию.

## 17. Решения для первой версии

В MVP входят:

- Tauri shell с одним окном: системная оболочка и контейнер приложения;
- Linux, Windows и Android platform ports, а также headless-сборка Linux;
- встроенные Rust host adapters, включая `ClockAdapter`, `RandomAdapter`, `SystemAdapter` и `ProcessAdapter`;
- встроенные drivers/resource brokers;
- control plane: node identity, control log, capability registry;
- package manifest и базовый package manager;
- Web UI components и capability bridge;
- WebAssembly workers;
- lifecycle и event activation;
- namespaces `local`, `replicated`, `cache`, `secrets`, `files`;
- VFS с метаданными, blob store и материализацией по запросу;
- permissions, grants и capability handles;
- симуляционный харнесс и contract tests с первого дня.

В MVP не входят:

- устанавливаемые platform extension packages;
- пользовательские Rust dynamic libraries;
- пользовательские постоянно работающие daemons;
- полностью прозрачный distributed RPC;
- универсальный интерфейс для всех видов host adapters;
- мультиоконность;
- обещание одинаковых фоновых гарантий на desktop и mobile;
- macOS и iOS platform ports и связанный с ними код;
- одинаковое размещение всех components на всех nodes;
- совместное редактирование текста как тип реплицируемых данных.

## 18. Рекомендуемая структура Rust workspace

Предварительная структура, не являющаяся окончательным разбиением crates:

```text
crates/
├── kernel/                 # запуск и координация; не зависит от tauri
├── contracts/              # IDL, DTO, версии публичных контрактов
├── capabilities/           # permissions, grants, handles, caller context
├── host-adapters/          # traits контрактов + общие типы
├── host-mock/              # mock-реализации всех контрактов
├── host-linux/             # Linux implementations
├── host-windows/           # Windows implementations
├── host-android/           # Android implementations
├── drivers/                # resource brokers
├── services/               # системные services
├── storage/                # namespaces, mutation log, persistence
├── vfs/                    # дерево, метаданные, материализация
├── blobs/                  # content-addressed store и chunking
├── net/                    # link adapters, сессии, транспорт
├── sync/                   # репликация и control log
├── app-runtime/            # package/component lifecycle
├── wasm-runtime/           # запуск workers
├── sim/                    # симуляция кластера и fault injection
├── tauri-host/             # интеграция с Tauri и bridge
└── kos-headless/           # точка входа cloud node
```

Ключевое ограничение структуры: `kernel` и всё, что ниже него, не зависят от `tauri`. Зависимость от `tauri` допустима только в `tauri-host`. Это проверяется в CI, потому что нарушение обнаруживается иначе только при попытке собрать headless-вариант.

`host-mock` и `sim` не являются тестовой инфраструктурой в обычном смысле: они входят в состав системы и поддерживаются наравне с платформенными реализациями.

Не следует сразу создавать crate для каждого небольшого типа. Границы crates вводятся там, где нужны отдельные зависимости, платформенная компиляция, стабильный контракт или изоляция тестирования.

## 19. Критерии корректности архитектуры

Архитектурное решение считается совместимым с этим документом, если:

- приложение не может обойти capability API;
- package может быть установлен в profile без требования исполнять каждый component на каждом node;
- несовместимый или недоступный component получает явное placement state;
- UI можно закрыть без обязательной остановки разрешённой фоновой задачи;
- worker можно остановить и позже возобновить из checkpoint;
- host adapter можно заменить другой платформенной реализацией без изменения service API;
- один ресурс можно безопасно разделить между несколькими приложениями через driver;
- данные явно относятся к local, replicated, derived или secret классу;
- выполнение имеет явный scope относительно устройств пользователя;
- обновление package не расширяет права без подтверждения;
- приложение без собственного backend может полноценно работать через стандартное API;
- добавление backend не требует отдельной установки service пользователем;
- ядро собирается и проходит тесты без `tauri` и без системной оболочки;
- любое обращение к внешнему миру проходит через host adapter, имеющий mock-реализацию;
- несколько экземпляров ядра запускаются в одном процессе и синхронизируются через симулированную сеть;
- отсутствие capability на устройстве выражается явным `unavailable`, а не деградацией поведения;
- внешний инструмент вызывается через типизированный контракт, не зависящий от способа его исполнения;
- файл имеет стабильную идентичность, не зависящую от пути;
- нематериализованное содержимое файла является нормальным состоянием, обрабатываемым API.

## 20. Открытые вопросы

Следующие темы требуют отдельных документов. Порядок соответствует очерёдности принятия решений.

Блокирующие начало реализации соответствующих подсистем:

1. ~~каталог capabilities~~ — зафиксирован в [capabilities.md](./capabilities.md), версия `0.1`;
2. формат control log: записи, правила авторизации, слияние ветвей;
3. key hierarchy, enrollment и revocation в деталях;
4. storage engine, формат mutation log и набор реплицируемых типов;
5. формат package, подпись и repository;
6. схема chunking и адресация blobs.

Отложенные до стабилизации перечисленного выше:

- модель миграций replicated state в распределённом профиле;
- distributed scheduler, leader election и leases;
- модель межпакетного обмена данными;
- обновление и rollback packages в масштабе профиля;
- резервное копирование и восстановление профиля;
- политика UI разрешения конфликтов;
- threat model и уровни доверия platform extensions;
- выбор WebAssembly runtime и поддерживаемая версия WASI;
- будущие macOS/iOS platform ports, если будет принято решение об их поддержке.

Требуют экспериментальной проверки, а не проектного решения:

- способ размещения контейнера приложения на Android: iframe с отдельным origin или встроенный WebView;
- механизм неподделываемой привязки канала bridge к package;
- работоспособность и стоимость выбранного WASM runtime на Android.

## 21. Краткое распределение ответственности

```text
Host adapter       — как выполнить платформенную операцию.
Driver             — как безопасно владеть и делить ресурс.
Control plane      — кто входит в профиль и что кому разрешено.
Service            — какую системную функцию предоставить.
Package            — что устанавливает пользователь.
Web UI             — что работает во view внутри единственного окна.
Worker             — backend приложения, активируемый runtime.
Capability API     — единственный путь к защищённым возможностям.
Storage namespace  — семантическое место хранения состояния.
VFS                — единое имя данных на всех устройствах профиля.
Placement          — где допустимо и предпочтительно исполнять component.
Node role          — что устройство вообще способно и обязано делать.
```

Главное следствие этой модели: frontend и backend могут принадлежать одному приложению, но имеют независимый жизненный цикл. Backend оформляется как worker внутри package, а не как отдельно устанавливаемый пользовательский service. Системные services остаются частью доверенной платформы K-OS.
