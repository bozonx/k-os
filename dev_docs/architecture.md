# Архитектура K-OS

Статус: первоначальный дизайн  
Назначение: зафиксировать базовые сущности, границы слоёв и правила исполнения приложений K-OS.

## 1. Цель системы

K-OS — персональная распределённая среда приложений, работающая на устройствах пользователя. Установленные приложения и разрешённое для синхронизации состояние доступны на desktop- и mobile-устройствах. При этом каждое устройство сохраняет собственные локальные ресурсы, возможности и ограничения платформы.

K-OS не пытается заменить ядро операционной системы. Это прикладная среда поверх Tauri и системных API, которая предоставляет:

- установку и управление пакетами приложений;
- единое capability API для frontend- и backend-компонентов;
- изоляцию данных и прав приложений;
- локальное и распределённое исполнение;
- синхронизацию пользовательского состояния между устройствами;
- доступ к сети, файлам, мультимедиа и оборудованию через контролируемые системные слои.

Синхронизация, репликация данных и разрешение конфликтов проектируются отдельно. Этот документ определяет границы, внутри которых эти механизмы будут использоваться.

## 2. Основные принципы

1. **Пакет является единицей установки.** Пользователь устанавливает приложение целиком, а не отдельно UI и его фоновые сервисы.
2. **Компонент является единицей исполнения.** Один пакет может содержать Web UI, workers и команды с разными жизненными циклами.
3. **Frontend не имеет прямого доступа к Tauri-командам, ОС и platform providers.** Он обращается только к публичному capability API K-OS.
4. **Пользовательский код считается недоверенным.** Права выдаются пакету явно и проверяются при каждом обращении к защищённой возможности.
5. **Распределённость не должна быть полностью прозрачной.** API учитывает задержки, отсутствие устройства, отмену операций и конфликты состояния.
6. **Локальное и синхронизируемое состояние разделены семантически.** Приложение выбирает класс данных, а не физический каталог.
7. **Platform provider реализует механизм, driver управляет ресурсом, service реализует функцию.** Эти роли не смешиваются.
8. **Фоновая работа преимущественно событийная.** Постоянные пользовательские процессы являются исключением и требуют отдельного разрешения.

## 3. Общая схема

```text
┌─────────────────────────────────────────────────────┐
│                       Web UI                        │
│ React / Vue / Svelte / vanilla JS / Canvas / WebGL │
└─────────────────────────┬───────────────────────────┘
                          │ capability API / RPC
┌─────────────────────────▼───────────────────────────┐
│                Application Runtime                  │
│ Web UI components │ workers │ commands │ lifecycle │
└─────────────────────────┬───────────────────────────┘
                          │ service calls
┌─────────────────────────▼───────────────────────────┐
│                      Services                       │
│ storage │ sync │ scheduler │ media │ notifications │
└─────────────────────────┬───────────────────────────┘
                          │ capability handles
┌─────────────────────────▼───────────────────────────┐
│            Drivers / Resource Brokers               │
│ ownership │ multiplexing │ retry │ quotas │ metrics │
└─────────────────────────┬───────────────────────────┘
                          │ typed provider contracts
┌─────────────────────────▼───────────────────────────┐
│                Platform Providers                   │
│ HTTP │ WebSocket │ files │ MQTT │ GPIO │ Git │ media│
└─────────────────────────┬───────────────────────────┘
                          │
               OS / network / hardware
```

Через все слои проходят системные механизмы:

- идентификация вызывающего компонента;
- permissions и capability handles;
- lifecycle и cancellation;
- журналирование, трассировка и метрики;
- управление локальным и replicated state;
- обнаружение устройств;
- установка, обновление и удаление пакетов.

### 3.1. Граница Rust, TypeScript и WebAssembly

K-OS использует гибридную архитектуру. Доверенное ядро и системный control plane работают вне WebView на Rust. WebView является клиентом системы и не владеет системным состоянием, соединениями или планировщиком.

| Область | Основная реализация |
|---|---|
| Platform providers | Rust |
| Drivers / resource brokers | Rust |
| Permissions и capability handles | Rust |
| Package manager и application runtime | Rust |
| Storage, synchronization и distributed coordination | Rust |
| Scheduler и lifecycle | Rust |
| Tauri/WebView bridge | Rust и сгенерированный TypeScript SDK |
| Системный UI | TypeScript |
| UI приложений | Любая web-технология |
| Backend приложений | Изолированный WebAssembly worker |
| Native-интеграции ОС | Rust/Tauri plugins |

Граница доверия выглядит следующим образом:

```text
Недоверенная зона
├── Web UI приложения
└── WebAssembly worker приложения
             │
             │ capability API / IPC
             ▼
Доверенная зона
├── Application Runtime
├── System Services
├── Drivers / Resource Brokers
└── Platform Providers
```

TypeScript SDK является удобной типизированной оболочкой над capability API, но не реализует безопасность. Все permissions, identity вызывающего компонента, quotas и ограничения ресурсов проверяются на стороне Rust.

Система не должна исполняться внутри browser runtime по следующим причинам:

- жизненный цикл WebView связан с окном и управляется платформой;
- JavaScript-контекст может быть перезагружен, приостановлен или выгружен;
- системные соединения и синхронизация должны жить независимо от UI;
- системные ключи и привилегированные API нельзя помещать в недоверенную среду;
- mobile и desktop предоставляют разные гарантии фонового исполнения.

Открытое desktop-окно может использоваться для оптимизации, но не является архитектурной гарантией доступности процесса.

## 4. Термины

### 4.1. Package

Package — подписываемая и версионируемая единица установки. Пакет содержит manifest, статические ресурсы и один или несколько исполняемых компонентов.

Пакет может содержать:

- `web-ui` — пользовательский интерфейс;
- `worker` — изолированный backend-компонент;
- `command` — короткая операция, запускаемая по запросу;
- декларации обработчиков событий;
- миграции данных;
- локализованные название, описание и иконки.

Пакет с пользовательской функцией или UI называется приложением. Пользователь устанавливает пакет один раз независимо от количества его компонентов.

### 4.2. Component

Component — единица запуска внутри package. У компонентов одного пакета могут быть разные точки входа, условия активации, ограничения ресурсов и жизненные циклы. Все они наследуют идентичность пакета, но получают только необходимые им permissions.

### 4.3. Platform Provider

Platform provider — нижний платформозависимый слой, реализующий конкретный технический механизм.

Примеры контрактов:

- `HttpProvider`;
- `WebSocketProvider`;
- `FileSystemProvider`;
- `MqttProvider`;
- `GpioProvider`;
- `ProcessProvider`;
- `MediaProvider`;
- `GitProvider`.

У разных видов providers нет общего универсального API. Общим является контракт между реализациями одного вида provider:

```text
HttpProvider
├── DesktopHttpProvider
├── MobileHttpProvider
└── MockHttpProvider
```

Platform provider:

- выполняет низкоуровневую операцию;
- скрывает различия ОС и платформ;
- не знает о приложениях и пользователях;
- не определяет permissions и квоты;
- не управляет распределением ресурса между потребителями;
- не отвечает за синхронизацию пользовательского состояния.

В первой версии providers являются встроенными Rust-компонентами ядра.

### 4.4. Driver / Resource Broker

Driver, или resource broker, превращает platform provider в управляемый системный ресурс.

Driver отвечает за:

- создание и переиспользование соединений;
- владение ресурсами и их освобождение;
- multiplexing между потребителями;
- очереди, backpressure и rate limits;
- reconnect, retry и timeout policy;
- сбор метрик и статистики;
- проверку permissions;
- выдачу ограниченных capability handles;
- платформенные ограничения времени жизни ресурса.

Например, `MqttProvider` открывает соединение и передаёт пакеты. `MqttDriver` переиспользует соединения, маршрутизирует подписки, восстанавливает связь и ведёт учёт потребителей.

Приложение не получает прямую ссылку на driver. Оно получает непрозрачный handle:

```rust
let connection = ctx
    .capabilities()
    .mqtt()
    .connect(options)
    .await?;
```

Handle связан с package ID, component ID, permissions и временем жизни владельца. Освобождение владельца закрывает или возвращает ресурс в управляемый pool.

В первой версии drivers являются встроенными. Устанавливаемые native drivers откладываются до появления подтверждённых сценариев нового оборудования или протоколов.

### 4.5. Service

Service — высокоуровневая системная функция, построенная поверх drivers и других services.

Примеры системных services:

- package manager;
- application runtime;
- storage и database;
- synchronization;
- identity и device registry;
- secrets;
- permissions;
- scheduler;
- notifications;
- media;
- logging и telemetry.

Service является runtime-ролью, но не отдельной обязательной единицей установки для пользователя. Пользовательский backend входит в package приложения как worker.

Системные services запускаются ядром в определённом порядке и могут иметь расширенные внутренние права. Пользовательский worker не становится системным service и не получает системных прав из-за фонового режима работы.

### 4.6. Worker

Worker — backend-компонент пользовательского package. Он предназначен для сложной логики, фоновой обработки, интеграций и реакций на события.

Рекомендуемый формат worker — WebAssembly Component с явно импортированными capability interfaces. Rust является основным рекомендуемым языком, но контракт не должен зависеть от Rust ABI и в дальнейшем может поддерживать другие компилируемые в WebAssembly языки.

Worker:

- не имеет прямого доступа к ОС;
- использует только объявленные capabilities;
- может запускаться без открытого окна;
- должен поддерживать cancellation и ограничение времени работы;
- сохраняет checkpoint для возобновления длительных задач;
- не предполагает, что процесс будет жить постоянно.

## 5. Компоненты приложения

### 5.1. Web UI

Web UI загружается в WebView Tauri и живёт, пока открыто связанное с ним окно. Разработчик может использовать любую web-технологию, включая WebGL и Canvas.

Web UI получает K-OS API через контролируемый bridge. Прямой произвольный вызов Tauri commands запрещён. Bridge передаёт runtime контекст вызывающего package и component, поэтому приложение не может выдать себя за другое приложение.

Web UI предназначен для:

- отображения интерфейса;
- обработки пользовательского ввода;
- подписки на события;
- вызова команд и services;
- работы с изолированными данными через K-OS API.

### 5.2. Worker

Обычный worker запускается событием или запросом, выполняет работу и завершается. Возможные причины активации:

- запуск приложения;
- пользовательская команда;
- изменение данных;
- сетевое событие;
- системное уведомление;
- расписание;
- открытие файла или URL;
- запрос другого разрешённого компонента.

### 5.3. Background worker

Background worker может продолжить работу после закрытия UI, пока существует разрешённая задача или выданный runtime lease.

Lease ограничивает:

- максимальную продолжительность;
- CPU и память;
- сетевую активность;
- частоту пробуждений;
- условия работы от батареи;
- поведение при переходе устройства в sleep.

Гарантии зависят от платформы. Код не должен предполагать, что desktop- и mobile-устройства дают одинаковое время фонового исполнения.

### 5.4. Отказ от пользовательских daemons

Daemon не входит в публичную модель компонентов приложения. K-OS не обещает пользовательскому коду постоянно живущий процесс, потому что такая гарантия несовместима с жизненным циклом мобильных ОС.

Сценарии, обычно требующие daemon, реализуются через:

- event-driven workers;
- durable jobs;
- периодические задания scheduler;
- подписки на системные события;
- ограниченные background leases;
- checkpoints и восстановление работы;
- платформенные push/background events.

Постоянные соединения принадлежат системным drivers и services, а не пользовательским workers. Например, системный MQTT service поддерживает соединение и сохраняет входящие события, после чего scheduler активирует подписанный на них worker приложения. При остановке процесса соединения и события восстанавливаются согласно системной политике.

Внутренние долгоживущие системные services допустимы, но они не являются устанавливаемыми пользовательскими daemons.

### 5.5. Command

Command — короткая stateless или ограниченная по времени операция. Она может вызываться из UI, другим компонентом или системой. Command подходит для операций, которым не нужен собственный долгоживущий lifecycle.

## 6. Жизненный цикл

| Компонент | Жизненный цикл |
|---|---|
| `web-ui` | Пока существует окно или view |
| `worker` | От события до завершения обработчика |
| `background-worker` | Пока активна задача и runtime lease |
| `command` | Один запрос — одно ограниченное выполнение |
| `system-service` | Управляется ядром |

Пример фонового исполнения:

```text
Событие
   ↓
Runtime проверяет manifest и permissions
   ↓
Запускает worker
   ↓
Worker запрашивает background lease при необходимости
   ↓
Выполняет работу и сохраняет checkpoint
   ↓
Завершается или возобновляется по следующему событию
```

Каждое выполнение получает deadline и cancellation token. Принудительная остановка компонента не должна повреждать подтверждённое состояние.

## 7. Manifest пакета

Предварительный концептуальный пример:

```toml
[package]
id = "com.example.music"
version = "1.0.0"

[[components]]
id = "main-ui"
type = "web-ui"
entry = "ui/index.html"

[[components]]
id = "library-indexer"
type = "worker"
entry = "workers/indexer.wasm"
activation = ["app-start", "files-changed"]

[[components]]
id = "scan-library"
type = "command"
entry = "workers/indexer.wasm#scan"

[permissions.main-ui]
capabilities = [
  "storage.private.read-write",
  "events.subscribe",
  "command.scan-library.invoke"
]

[permissions.library-indexer]
capabilities = [
  "storage.private.read-write",
  "files.user.read",
  "media.metadata"
]
```

Точный формат manifest будет определён отдельно. Важные свойства модели:

- глобально уникальный package ID;
- стабильные component IDs;
- отдельные permissions для компонентов;
- декларативные activation events;
- версии capability contracts;
- декларация поддерживаемых платформ;
- декларация миграций данных;
- криптографическая подпись пакета.

## 8. Capability API и permissions

Capability — ограниченное право выполнить класс операций. Permissions из manifest описывают запрашиваемые права, а runtime policy определяет, какие из них реально выданы на конкретном устройстве.

Примеры capabilities:

```text
storage.private.read-write
storage.replicated.read-write
files.user.read
files.user.write
network.http:api.example.com
mqtt.connect
media.transcode
notifications.show
background.run
device.location
```

Каждый защищённый вызов содержит или восстанавливает следующий контекст:

```text
user ID
device ID
package ID
component ID
execution ID
granted capabilities
trace ID
deadline
cancellation token
```

Проверка производится на границе системного API и не полагается только на скрытие методов во frontend SDK.

Capability handle должен быть:

- непрозрачным для приложения;
- ограниченным конкретным ресурсом и операциями;
- отзывным;
- привязанным к владельцу;
- автоматически освобождаемым;
- непригодным для передачи другому package без явного системного механизма.

## 9. Взаимодействие services и компонентов

Компоненты находят services через service registry и типизированные контракты. Они не получают произвольные Rust-объекты и не обращаются напрямую к внутренним менеджерам.

Концептуальный локальный API:

```rust
let media = ctx.services().require::<MediaService>(">=1.2")?;
let result = media.transcode(request).await?;
```

Контракт не должен зависеть от нестабильного Rust ABI. Для разных границ могут использоваться:

- WIT и WebAssembly Component Model для workers;
- сериализуемые versioned messages для IPC/RPC;
- Protobuf, CBOR или MessagePack со схемой;
- generated TypeScript API для Web UI.

Локальный и удалённый вызов могут иметь одинаковые типы запроса и ответа, но API обязан сохранять сетевую семантику: timeout, cancellation, недоступность узла, повтор и idempotency.

## 10. Состояние и хранилища

Приложение работает с логическими namespaces, а не с внутренней структурой каталогов:

```text
app.storage.local
app.storage.replicated
app.storage.cache
app.storage.files
app.storage.secrets
```

Основные классы состояния:

| Класс | Назначение | Пример |
|---|---|---|
| `ephemeral` | Временное состояние процесса | открытое соединение |
| `device-local` | Данные конкретного устройства | положение окна |
| `replicated` | Синхронизируемые данные | настройки, документы |
| `derived` | Восстанавливаемые данные | индекс поиска, thumbnails |
| `secret` | Защищённые переносимые секреты | API token |
| `device-bound-secret` | Секрет конкретного устройства | device private key |
| `shared-file` | Пользовательские файлы | документы и медиа |

Физическое хранение является деталью реализации storage service. Оно может измениться без изменения API приложений.

`localStorage`, IndexedDB и browser cache:

- считаются локальными и несинхронизируемыми;
- не должны использоваться для основного состояния;
- могут очищаться вместе с данными WebView;
- допускаются для временной оптимизации UI.

Основным способом хранения является асинхронное K-OS storage API.

## 11. Распределённое исполнение

Состояние приложения может быть общим между устройствами, но процессы, окна, соединения и аппаратные ресурсы всегда принадлежат конкретному устройству.

Для jobs и workers manifest или scheduler задаёт execution scope:

| Scope | Семантика |
|---|---|
| `per-window` | Отдельно для каждого окна |
| `per-device` | Один экземпляр на устройстве |
| `per-user` | Логически один экземпляр пользователя |
| `cluster-singleton` | Одно активное выполнение среди устройств |
| `leader-elected` | Выполнение на выбранном устройстве-лидере |

Распределённый scheduler должен учитывать:

- доступность устройства;
- необходимые capabilities и оборудование;
- online/offline состояние;
- питание и батарею;
- idempotency задачи;
- lease и потерю лидера;
- checkpoint и повтор выполнения.

Распределённая операция не получает гарантию exactly-once по умолчанию. Обработчики должны проектироваться как idempotent либо использовать системные механизмы дедупликации.

### 11.1. Размещение распределённой координации

Распределённая инфраструктура реализуется системными Rust services и работает независимо от WebView и приложений:

```text
Distributed Runtime
├── Device Identity
├── Peer Discovery
├── Secure Transport
├── Replication
├── Membership
├── Lease Service
├── Distributed Scheduler
└── Event Delivery
```

Выбор Rust связан не с тем, что распределённые алгоритмы невозможно реализовать на TypeScript, а с требованиями к жизненному циклу, владению ключами и соединениями, устойчивому локальному хранилищу и восстановлению после аварии.

Не следует вводить строгий consensus для каждой функции. Механизм выбирается по требуемой семантике:

- CRDT или version vectors — для части replicated state;
- lease с fencing token — для временного единственного владельца;
- leader election — когда работу должно координировать одно устройство;
- строгий consensus — только для данных, которым действительно необходим единый порядок изменений.

Удалённые jobs должны быть idempotent или использовать ключи дедупликации. Потеря устройства либо lease рассматривается как нормальная ситуация, а не исключительное завершение всей системы.

## 12. Динамические расширения и Rust

Rust dynamic libraries (`.so`, `.dll`, `.dylib`) не являются основным форматом пользовательских расширений, потому что:

- Rust ABI не гарантирует стабильность между версиями компилятора;
- библиотека исполняется внутри процесса и может завершить всё приложение;
- сложно обеспечить sandbox и контроль ресурсов;
- нужны отдельные сборки под платформы и архитектуры;
- обновление загруженного кода усложняет lifecycle;
- мобильные платформы ограничивают загрузку нового исполняемого кода.

Принята следующая модель расширяемости:

| Механизм | Назначение |
|---|---|
| Встроенный Rust crate | platform providers, drivers, системные services |
| WebAssembly Component | пользовательские workers и безопасные расширения |
| Отдельный native process / sidecar | FFmpeg, Git и тяжёлые native-инструменты |
| Dynamic library со стабильным C ABI | только доверенные платформенные расширения в будущем |

Native extension требует отдельного уровня доверия, подписи, платформенного пакета и явного согласия пользователя. Оно не должно автоматически получать права основного процесса K-OS.

## 13. Изоляция и безопасность

Минимальные границы безопасности:

- каждый package имеет отдельный namespace данных;
- Web UI работает с ограниченным bridge;
- workers исполняются в WebAssembly sandbox;
- системные capabilities запрещены по умолчанию;
- доступ к пользовательским файлам выдаётся через picker, scope или permission;
- credentials передаются через secrets service, а не хранятся в manifest;
- сетевые права могут ограничиваться доменами и протоколами;
- фоновые права выдаются отдельно;
- межпакетные вызовы разрешаются обеими сторонами и системой;
- удалённые вызовы аутентифицируют пользователя и устройство;
- package update не может незаметно расширить permissions.

### 13.1. Изоляция Web UI

Каждое приложение должно загружаться в отдельный WebView с собственным origin и, где позволяет платформа, отдельным browser storage partition. Для WebView применяются:

- строгий Content Security Policy;
- запрет произвольных Tauri commands;
- ограничение навигации и открытия внешних URL;
- отдельная сессия capability bridge;
- отсутствие доступа к WebView системного UI;
- получение package ID и component ID из доверенного runtime-контекста.

Frontend не передаёт собственный package ID для доступа к ресурсам. Например, публичный вызов имеет форму `storage.read(path)`, а namespace приложения определяется Rust runtime из сессии WebView. Переданный приложением идентификатор нельзя считать доказательством его личности.

WebView является дополнительной границей изоляции, но не единственной security boundary. Даже при компрометации frontend-кода Rust bridge обязан разрешать только выданные capabilities.

### 13.2. Изоляция workers

Backend приложения исполняется как WebAssembly Component. Worker получает только явно импортированные K-OS interfaces и по умолчанию не получает полного доступа WASI к сети, процессам или файловой системе.

Runtime ограничивает:

- память и объём вычислений;
- длительность и количество одновременных запусков;
- сетевые направления;
- доступный объём хранилища;
- частоту активации;
- набор импортированных capabilities.

Язык реализации worker не является частью security model. Rust рекомендуется первым, но в будущем может поддерживаться любой язык, способный собрать совместимый WebAssembly Component.

Permissions определяют доступ, а quotas — объём использования разрешённого доступа. Это разные механизмы и оба применяются runtime.

## 14. Ошибки, отмена и наблюдаемость

Все асинхронные контракты должны поддерживать:

- типизированные ошибки;
- deadline;
- cancellation;
- backpressure для потоков;
- ограниченную retry policy;
- trace ID;
- безопасное журналирование без утечки секретов.

Driver собирает технические метрики ресурса, service — метрики операций, application runtime — метрики жизненного цикла. Приложению доступна только разрешённая ему часть диагностических данных.

## 15. Загрузка системы

Предварительный порядок запуска:

1. platform runtime и конфигурация устройства;
2. logging и crash reporting;
3. identity, key storage и device identity;
4. permissions и capability registry;
5. platform providers;
6. drivers/resource brokers;
7. storage и database services;
8. package manager и application runtime;
9. synchronization и device coordination;
10. scheduler и activation manager;
11. системный UI и пользовательские компоненты.

Каждый этап объявляет зависимости явно. Циклические зависимости между services запрещены либо разрываются через события и отложенную активацию.

## 16. Решения для первой версии

В MVP входят:

- Tauri shell;
- встроенные Rust platform providers;
- встроенные drivers/resource brokers;
- встроенные системные services;
- package manifest;
- Web UI components;
- capability bridge для WebView;
- WebAssembly workers;
- lifecycle и event activation;
- изолированные local, replicated, cache и secrets namespaces;
- permissions и capability handles;
- базовый package manager.

В MVP не входят:

- устанавливаемые platform providers;
- устанавливаемые native drivers;
- пользовательские Rust dynamic libraries;
- пользовательские постоянно работающие daemons;
- полностью прозрачный distributed RPC;
- универсальный интерфейс для всех видов providers;
- обещание одинаковых фоновых гарантий на desktop и mobile.

## 17. Рекомендуемая структура Rust workspace

Предварительная структура, не являющаяся окончательным разбиением crates:

```text
crates/
├── kernel/                 # запуск и координация системных компонентов
├── contracts/              # IDL, DTO, версии публичных контрактов
├── capabilities/           # permissions, handles, caller context
├── providers/              # provider traits
├── providers-desktop/      # desktop implementations
├── providers-mobile/       # mobile implementations
├── drivers/                # resource brokers
├── services/               # системные services
├── storage/                # namespaces и persistence
├── app-runtime/            # package/component lifecycle
├── wasm-runtime/           # запуск workers
├── sync/                   # синхронизация и replication
└── tauri-host/             # интеграция с Tauri и WebView bridge
```

Не следует сразу создавать crate для каждого небольшого типа. Границы crates вводятся там, где нужны отдельные зависимости, платформенная компиляция, стабильный контракт или изоляция тестирования.

## 18. Критерии корректности архитектуры

Архитектурное решение считается совместимым с этим документом, если:

- приложение не может обойти capability API;
- UI можно закрыть без обязательной остановки разрешённой фоновой задачи;
- worker можно остановить и позже возобновить из checkpoint;
- provider можно заменить платформенной реализацией без изменения service API;
- один ресурс можно безопасно разделить между несколькими приложениями через driver;
- данные явно относятся к local, replicated, derived или secret классу;
- выполнение имеет явный scope относительно устройств пользователя;
- обновление package не расширяет права без подтверждения;
- приложение без собственного backend может полноценно работать через стандартное API;
- добавление backend не требует отдельной установки service пользователем.

## 19. Открытые вопросы

Следующие темы требуют отдельных design documents:

- модель replicated database и разрешение конфликтов;
- идентификация пользователя и доверие между устройствами;
- формат package, подпись и repository;
- точный IDL публичных APIs;
- выбор WebAssembly runtime и поддерживаемая версия WASI;
- модель миграций replicated state;
- distributed scheduler, leader election и leases;
- обновление и rollback packages;
- резервное копирование и восстановление;
- модель межпакетного обмена данными;
- threat model и уровни доверия native extensions.

## 20. Краткое распределение ответственности

```text
Platform provider  — как выполнить платформенную операцию.
Driver             — как безопасно владеть и делить ресурс.
Service            — какую системную функцию предоставить.
Package            — что устанавливает пользователь.
Web UI             — что работает в окне.
Worker             — backend приложения, активируемый runtime.
Capability API     — единственный путь к защищённым возможностям.
Storage namespace  — семантическое место хранения состояния.
```

Главное следствие этой модели: frontend и backend могут принадлежать одному приложению, но имеют независимый жизненный цикл. Backend оформляется как worker внутри package, а не как отдельно устанавливаемый пользовательский service. Системные services остаются частью доверенной платформы K-OS.
