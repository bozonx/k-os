# Identity, ключи и доверие

Статус: готов  
Назначение: зафиксировать иерархию ключей, криптографические требования к enrollment и отзыв доверия.

Связанные документы: [создание и расширение сети](./09-network-lifecycle.md), [control log](./03-control-log.md).


## Иерархия ключей

```text
profile root key
├── admin authority (подмножество device nodes)
├── data key epochs: DEK[0], DEK[1], ...
│   └── производные ключи namespace / blob
└── node identity keys (по одному на node)
```

- **profile root key** создаётся при создании профиля, предъявляется пользователю как recovery phrase и хранится офлайн. Используется только для восстановления, когда потеряны все admin-устройства.
- **node identity key** генерируется на устройстве в платформенном secure storage и не покидает его. Класс состояния — `device-bound-secret`.
- **data key epoch** шифрует содержимое op log records и blobs. Новая эпоха создаётся при revocation node и при плановой ротации.

Данные шифруются на уровне записи и blob, а не только на уровне транспорта. Это условие существования ролей без ключей данных — `relay` и `appliance` — и защита хранилища на потерянном устройстве.

Ключи эпохи выдаются только нодам ролей `device` и `cloud`. Нода роли `appliance` имеет собственный node identity key и получает подтверждение членства, но ключей эпохи не получает никогда: отсюда следует, что её компрометация не раскрывает данные профиля, а её подключение не требует новой эпохи при отзыве других нод.

## Криптографические примитивы

| Назначение | Примитив |
|---|---|
| подписи: записи control log, ростеры, доказательства членства | Ed25519 |
| согласование ключей при установлении сессии и при enrollment | X25519 |
| деривация ключей namespace и blob из эпохи | HKDF-SHA-256 |
| шифрование записей и чанков | AEAD: ChaCha20-Poly1305 |
| хеширование содержимого и адресация | BLAKE3, см. [blob store](../05-storage/04-blobs-and-materialization.md) |

Выбор сделан досрочно и намеренно скучный: это общедоступные, проверенные примитивы с
реализациями на всех целевых платформах. Ничего оригинального здесь изобретать не нужно, а
отсутствие конкретики блокирует и формат control log, и симуляцию.

Каждый ключ и каждая подпись сопровождаются идентификатором алгоритма, поэтому замена
примитива — введение нового идентификатора и переходный период, а не смена формата.

Ротация эпохи не перешифровывает историю автоматически. Перешифрование прошлых данных является отдельной фоновой операцией с явной стоимостью; документ не обещает, что после revocation старые данные становятся недоступны отозванному устройству.

## Enrollment: требования

Пошаговый сценарий подключения, формат кода и выбор роли описаны в
[создании сети и подключении нод](./09-network-lifecycle.md). Здесь зафиксированы
криптографические требования, которым обязан удовлетворять любой такой сценарий:

- identity keypair генерируется на подключаемом устройстве и не покидает его secure storage;
- канал между устройствами аутентифицируется взаимно, с short authentication string, которую
  человек сверяет на обоих устройствах;
- членство возникает только записью `node-enrolled` в control log, подписанной устройством с
  полномочиями администратора; запись фиксирует публичный ключ, роль и разрешённые node capabilities;
- актуальные data key epochs передаются только по уже аутентифицированному каналу;
- подтверждение человеком на уже доверенном устройстве обязательно. Автоматическое
  присоединение по факту нахождения в одной локальной сети запрещено.

## Revocation

```text
1. Admin-устройство добавляет запись `node-revoked`.
2. Создаётся новая data key epoch, распространяемая
   на оставшиеся nodes.
3. Каждый node и relay, увидевший запись, отказывает
   отозванному ключу в установлении сессии.
```

Что гарантируется: отозванный node не получает данные, созданные после revocation, и не может устанавливать новые сессии с узлами, узнавшими о revocation.

Что **не** гарантируется: удаление уже полученных данных на отозванном устройстве и мгновенное вступление revocation в силу для узлов, которые ещё не получили запись. Это ограничение фиксируется как проектное решение, а не как дефект.
