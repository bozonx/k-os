# Control log профиля

Статус: готов  
Назначение: определить формат записей control log, правила авторизации, детерминированную
свёртку в состояние профиля, компактизацию и правила совместимости версий.

Связанные документы: [identity и доверие](./02-identity-and-trust.md),
[модель capabilities](../04-capabilities/01-model.md),
[профиль и ноды](../02-architecture/02-profile-and-nodes.md),
[репликация](./07-replication.md), [модель времени](./05-time.md),
[модель угроз](../10-security/02-threat-model.md).

Control log — единственная часть системы, для которой требуется строгая проверка
авторизации. Всё остальное состояние использует более слабые модели и опирается на него:
сессия устанавливается с нодой, членство которой подтверждено control log, а операция
применяется, если её автор обладал правом по control log.

## Область

| Попадает в control log | Не попадает |
|---|---|
| состав профиля: подключение, отзыв, роль ноды | пользовательские данные любого вида |
| полномочия администратора | содержимое и состояние приложений |
| эпохи ключей данных | оперативное состояние: доступность, метрики, leases |
| установка, активация версии и удаление пакетов | дескрипторы возможностей нод |
| удержание версии пакета после отката | кандидаты версий и готовность нод к обновлению |
| выдача и отзыв grants | связи с другими пользователями и выданные им доступы |

Правило отбора: в control log попадает то, **от чего зависит проверка авторизации**.
Всё, что можно вычислить или потерять без последствий для безопасности, живёт в обычном
[реплицируемом состоянии](./07-replication.md), где стоимость записи ниже.

Связи с другими пользователями и доступы, выданные им, в control log не входят намеренно:
они не расширяют полномочия внутри профиля, а их объём и частота изменений на порядки
больше. Их авторизация опирается на публичную идентичность профиля, см.
[федерацию](../07-federation/01-model.md).

## Свойство, определяющее всё остальное

**Состояние профиля есть функция от множества записей, а не от порядка их получения.**

```text
state = fold(S)   для любого множества записей S
fold(S ∪ T) = fold(T ∪ S)          порядок доставки не влияет
fold(S ∪ S) = fold(S)              повтор не влияет
```

Личные устройства неделями не встречаются друг с другом и получают записи в произвольном
порядке: телефон узнаёт об отзыве ноутбука раньше, чем о выдаче ему прав. Если бы состояние
зависело от порядка, два устройства с одинаковым набором записей показывали бы разный состав
профиля и по-разному отвечали бы на вопрос «имеет ли эта нода право». Расхождение в этом
вопросе — это либо потеря доступа, либо доступ у отозванного устройства.

Отсюда все решения ниже: hash-linked DAG вместо журнала с порядком, свёртка вместо
последовательного применения, доминирование отзыва вместо «последний победил» и
детерминированный tie-break вместо времени прибытия.

## Устройство лога

Control log — **hash-linked DAG подписанных записей**. Consensus с кворумом здесь
неприменим: требовать кворум для подключения устройства или выдачи разрешения означало бы
неработоспособность системы ровно тогда, когда все устройства, кроме одного, выключены.

```text
profile-created
      │
   node-enrolled(A)
      │        ╲
 grant-added   node-enrolled(B)        параллельные ветви — норма
      │        ╱
   key-epoch-created                    слияние = объединение множеств
```

Слияние ветвей не требует разрешения конфликтов на уровне лога: ветви объединяются
объединением множеств записей, а весь смысл «кто прав» выражен правилами свёртки.

## Формат записи

Запись кодируется в [CBOR](./04-transport-and-discovery.md) в каноническом виде: ключи
map упорядочены, целые в кратчайшей форме, неопределённых длин нет. Каноничность
обязательна — иначе одна и та же запись даёт два разных хеша и попадает в лог дважды.

```text
schema        версия формата записи: major.minor
type          тип записи
parents       множество record-id родителей, отсортировано лексикографически
author        идентификатор подписавшего: node-id или profile-root
issued-at     HLC отправителя: для отображения, не для авторизации
body          CBOR map, зависящий от типа
sig           Ed25519-подпись над каноническим кодированием всех полей выше
```

`record-id` = BLAKE3 от канонического кодирования подписанной записи целиком. Запись
самоидентифицируется: получив её, нода проверяет хеш и подпись, не обращаясь ни к кому.

Свойства формата:

- **`parents` — множество, а не список предшественников по времени.** Запись ссылается на
  все известные автору вершины DAG на момент создания;
- **`issued-at` не участвует в авторизации и не задаёт порядок применения.** Часы устройства
  не являются доверенным входом; HLC используется только для tie-break между заведомо
  конкурентными записями и для показа пользователю;
- **единственная запись без `parents` — `profile-created`.** Два разных корня — это два
  разных профиля, а не расхождение внутри одного, и объединение таких DAG запрещено;
- **размер записи ограничен.** Тела содержат идентификаторы, ключи и области прав, но не
  содержимое: лог профиля за годы работы — это десятки килобайт, и он реплицируется целиком
  на каждую ноду.

## Типы записей

| Тип | Тело | Кто вправе подписать |
|---|---|---|
| `profile-created` | публичный ключ profile root, публичная идентичность профиля | profile root key |
| `node-enrolled` | node-id, публичный ключ, роль, разрешённые node capabilities | admin или profile root |
| `node-revoked` | node-id, причина | admin или profile root |
| `node-role-changed` | node-id, новая роль | admin или profile root |
| `admin-granted` | node-id | admin или profile root |
| `admin-revoked` | node-id | admin или profile root |
| `key-epoch-created` | номер эпохи, ключи эпохи, обёрнутые на identity-ключ каждой действующей ноды | admin |
| `package-installed` | package-id, источник, ключ издателя | admin, либо нода с правом установки |
| `package-version-staged` | package-id, версия, хеш манифеста | тот же |
| `package-version-activated` | package-id, версия, хеш содержимого | тот же |
| `package-hold` | package-id, версия, признак удержания | тот же |
| `package-removed` | package-id | тот же |
| `grant-added` | package-id, capability, область, ограничения | admin, либо нода с правом выдачи |
| `grant-revoked` | package-id, capability, область | любая нода профиля |
| `checkpoint` | свёрнутое состояние и граница, см. ниже | admin |

Две асимметрии сделаны намеренно:

- **отзыв всегда доступнее выдачи.** `grant-revoked` вправе подписать любая нода профиля, а
  `node-revoked` — любой администратор. Человек, потерявший телефон, отзывает его с того
  устройства, которое у него в руках, а не с того, которое считается главным;
- **первая нода получает полномочия администратора при создании профиля**, иначе
  профиль был бы неуправляем до подключения второго устройства.

Записи о пакетах выражают только решение профиля: что установлено, какая версия намечена к
переходу, какая активна и какая удержана после отката. Всё остальное, что относится к
обновлению, — появление новой версии у издателя, готовность ноды к переходу, канал и
настройка автообновления — в лог не входит: оно не влияет на проверку авторизации и живёт в
обычном реплицируемом состоянии, см.
[распространение приложений](../03-apps/07-distribution.md).

## Авторизация

Валидность записи проверяется **по её собственным предкам и только по ним**.

```text
authority(r) = свёртка causal-closure(parents(r))
r авторизована ⟺ author(r) обладает требуемым полномочием в authority(r)
```

`causal-closure(P)` — множество всех записей, достижимых из `P` по ссылкам `parents`.
Параллельные ветви, о которых автор не знал, в проверку не входят.

Следствие, ради которого правило так сформулировано: **валидность записи не меняется со
временем**. Нода, однажды проверившая запись, не обязана перепроверять её при получении
новых. Если бы авторизация зависела от всего известного множества, то каждая новая запись
требовала бы повторной проверки всей истории, а две ноды с разной степенью осведомлённости
расходились бы в оценке одной и той же записи.

Запись, не прошедшая проверку — неверная подпись, неизвестный автор, отсутствие
полномочия у автора в его собственном контексте, — **отбрасывается и не передаётся
дальше**. Она не хранится в карантине: в отличие от неизвестного типа записи, здесь нет
сценария, в котором она позже станет действительной.

### Действие записи и его отмена

Валидность — свойство записи. Применяется ли её эффект — свойство всего множества:

| Уровень | От чего зависит | Может ли измениться |
|---|---|---|
| валидность | предки записи | нет, никогда |
| действие | всё известное множество записей | да, действие может быть снято отзывом |

Запись, подписанная нодой, для которой в **параллельной** ветви существует `node-revoked`,
валидна, но её действие снимается: она не применяется к состоянию. То же для записей,
подписанных нодой, чьи полномочия администратора отозваны параллельно.

Это осознанный выбор в пользу безопасности. Его цена: нода, получившая записи отозванного
устройства раньше, чем сам отзыв, применит их, а затем снимет их действие. Такое изменение
задним числом наблюдаемо — например, установленный пакет перестаёт быть установленным — и
показывается пользователю как результат отзыва, а не как самопроизвольное изменение.

Обратного хода нет: снятое действие не возвращается добавлением новых записей, потому что
отзыв не отменяется. Восстановление — только новым подключением, подписанным действующим
администратором или profile root key.

## Свёртка в состояние профиля

Свёртка обходит DAG и для каждого субъекта вычисляет значение по правилу его типа. Все
правила монотонны: добавление записей может изменить результат только в одну сторону.

| Субъект | Правило | Разрешение конкурентности |
|---|---|---|
| членство ноды | `revoked` доминирует над `enrolled` | отзыв побеждает при любом взаимном расположении |
| полномочия администратора | `revoked` доминирует над `granted` | то же |
| роль ноды | последнее по HLC, tie-break по `record-id` | обе записи сохраняются в истории |
| grant | `revoked` доминирует над `added` | отзыв побеждает |
| установка пакета | `removed` доминирует над `installed` | удаление побеждает |
| намеченная версия пакета | наибольшая HLC, tie-break по `record-id`; действует, пока нет активации той же или большей версии | обе записи сохраняются в истории |
| активная версия пакета | наибольшая HLC, tie-break по `record-id` | проигравшая версия остаётся доступной для отката |
| удержание версии пакета | последнее по HLC для пары «пакет, версия», tie-break по `record-id` | удержание блокирует только автоматическую активацию, ручная остаётся возможной |
| эпоха ключей | действует наибольший номер | при совпадении номеров действует запись с большим `record-id`, остальные отбрасываются |

Правило tie-break везде одно: **большая HLC, при равенстве — больший `record-id`**. Оно
детерминировано, не зависит от порядка получения и одинаково на всех нодах.

Взаимный отзыв двух администраторов приводит к отзыву обоих. Это безопасный исход, а не
дефект: ситуация означает, что как минимум одно из устройств считает другое
скомпрометированным. Восстановление выполняется новым enrollment, подписанным оставшимся
администратором или profile root key.

Записи монотонны: отменить запись можно только новой записью. Удаление записи из лога не
является операцией.

## Компактизация и checkpoints

Без компактизации лог растёт всё время жизни профиля, и новая нода при подключении обязана
проверить его целиком.

`checkpoint` — подписанная администратором запись, содержащая свёрнутое состояние и
**границу**: множество `record-id`, ниже которых история считается свёрнутой.

```text
1. Администратор публикует checkpoint с текущей границей.
2. Ноды продолжают работать: checkpoint — это подсказка, а не команда.
3. Нода вправе удалить историю ниже границы, когда checkpoint
   подтверждён всеми известными нодами профиля либо когда
   неподтвердившая нода вышла за горизонт отставания.
4. Границу и горизонт хранит профиль; они не являются константами.
```

Горизонт отставания — тот же механизм, что и в [репликации](./07-replication.md): нода, не
выходившая на связь дольше объявленного срока, синхронизируется полным переносом состояния,
а не историей.

Правило безопасности для свёрнутой истории: **запись, чьи предки лежат ниже границы,
принимается только если её автор уполномочен в состоянии checkpoint**. Проверить её по
исходным предкам уже невозможно, а принимать на веру нельзя. Отставшая нода, чьи записи
отклонены по этой причине, показывает пользователю, что её изменения не приняты, — молчаливая
потеря здесь недопустима.

Checkpoint не является источником истины сам по себе: нода, у которой есть полная история,
проверяет его свёрткой и отвергает при расхождении. Доверие к checkpoint без истории
возникает только в одном месте — при подключении новой ноды, где оно уже установлено
аутентифицированным каналом enrollment и подтверждением человека.

## Совместимость версий

Ноды профиля обновляются не одновременно, поэтому формат обязан пережить разницу версий.

- **неизвестное поле в теле известного типа сохраняется** и передаётся дальше без
  изменений; оно входит в подписанное кодирование, поэтому потеря поля разрушила бы подпись;
- **запись неизвестного типа с совместимой major-версией хранится, передаётся дальше и
  участвует в hash-links, но не применяется.** Отбрасывать её нельзя: она является предком
  других записей, и без неё DAG рвётся;
- **запись с более высокой major-версией схемы останавливает применение control log на этой
  ноде.** Нода продолжает хранить и передавать записи, но не выполняет свёртку и не
  принимает решений об авторизации, а сообщает пользователю, что её нужно обновить.

Последнее правило намеренно жёстче остальных. Major-версия повышается только при изменении
типов, влияющих на авторизацию, — а нода, которая не понимает часть записей о полномочиях,
не может отличить «полномочия не выдавались» от «полномочия выданы способом, которого я не
знаю». Продолжать работу в этом состоянии значит принимать решения о доступе по заведомо
неполному состоянию; отказ работать — единственный безопасный вариант.

Из этого следует ограничение на развитие формата: **типы записей, влияющие на авторизацию,
образуют ядро схемы и расширяются только повышением major-версии**. Всё, что можно выразить
без изменения правил авторизации, добавляется minor-версией.

## Распространение

Control log реплицируется между нодами профиля как отдельный поток, вне общего механизма
репликации данных: он нужен до того, как станет возможной проверка авторизации остальных
операций. Обмен идёт по version vector границ DAG — стороны сравнивают вершины и передают
недостающие записи.

Отставшая нода получает историю от границы известного ей checkpoint, а не с начала времён.

Узлы без ключей данных — роли `relay` и `appliance` — **не получают control log**: он
раскрывал бы состав сети, публичные ключи нод и историю установленных пакетов. Вместо этого
нода предъявляет им **подтверждение членства** — производное от control log, подписанное
администратором, с псевдонимным идентификатором, номером эпохи и ограниченным сроком
действия. Отзыв ноды выражается для них выпуском подтверждений новой эпохи и истечением
старых, а не проверкой лога на их стороне.

Различие между двумя ролями лежит не в доступе к логу, а в том, что им дополнительно
передаётся: `appliance` получает записи о правах на **свои устройства** — какому пакету
разрешено ими управлять, — потому что проверка на владеющей стороне обязательна, см.
[устройства и IoT](../08-devices/01-model.md). Состав профиля и права на данные в этот набор
не входят.

## Границы

Control log не решает и не обязан решать:

- **упорядочивание пользовательских данных** — для них действует причинный порядок и
  правила слияния типов, см. [репликацию](./07-replication.md);
- **актуальность отзыва в реальном времени** — нода, ещё не получившая `node-revoked`,
  продолжит принимать отозванное устройство. Это ограничение зафиксировано в
  [identity и доверии](./02-identity-and-trust.md) как проектное решение;
- **недоступность данных, уже полученных отозванным устройством**;
- **координацию исполнения** — leases и лидерство живут в
  [координации](./08-coordination.md), а не в логе.

## Проверяемые критерии

- две ноды с одинаковым множеством записей вычисляют одинаковое состояние профиля при любом
  порядке доставки;
- повторная доставка записи не изменяет состояние;
- запись, признанная валидной, остаётся валидной после получения любых новых записей;
- запись, подписанная нодой, отозванной в параллельной ветви, не влияет на состояние;
- взаимный отзыв двух администраторов отзывает обоих;
- нода, встретившая запись с более высокой major-версией схемы, прекращает применение лога,
  а не применяет его частично;
- удержанная версия пакета не становится активной в результате автоматического обновления;
- удаление истории ниже границы checkpoint не меняет вычисленное состояние;
- запись отставшей ноды, предки которой свёрнуты, либо принимается по состоянию checkpoint,
  либо отклоняется с уведомлением пользователя;
- relay не получает записей control log ни при каком сценарии;
- `appliance` не получает ни записей control log, ни ключей данных: доступное ему множество
  ограничено правами на его собственные устройства;
- симуляция с произвольным порядком доставки и разделением сети не приводит к расхождению
  состава профиля между нодами.

## Открытые вопросы

- нужна ли верхняя граница числа вершин DAG, за которой нода принудительно требует
  checkpoint, и что делать при её достижении в профиле без администратора онлайн;
- как выражать пользователю снятие действия записей отозванного устройства, когда их много:
  списком изменений или сводкой.
