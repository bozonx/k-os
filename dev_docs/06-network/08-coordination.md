# Координация: leases, лидерство, fencing

Статус: перенесено из прежних документов, требует ревизии.  
Назначение: зафиксировать, какие механизмы координации используются и для каких задач.

Связанные документы: [размещение и исполнение](../03-apps/08-placement-and-execution.md), [модель времени](./05-time.md).


Единый механизм не используется для всех задач:

- causal replication и CRDT — для большинства пользовательских данных;
- deterministic conflict resolution — для части domain state;
- lease с fencing token — для временного единственного владельца;
- leader election — для размещения и координации, но не как гарантия доступности;
- quorum consensus — не используется. Требуемое согласие о составе профиля и правах обеспечивается [control log](./03-control-log.md).

Персональные nodes часто выключены, поэтому система не требует кворума для обычной локальной работы. При наличии cloud node он является предпочтительным кандидатом в лидеры как наиболее доступный.

Lease, защищающий внешний side effect, всегда используется вместе с fencing token. Само по себе истечение lease не останавливает старого владельца после network partition.


## Размещение распределённой координации


Распределённая инфраструктура реализуется системными Rust services и работает независимо от WebView и приложений:

```text
Distributed Runtime
├── Node Identity
├── Profile Control Log
├── Peer Discovery
├── Secure Transport
├── Replication
├── Blob Transfer
├── Lease Service
├── Distributed Scheduler
└── Event Delivery
```

Выбор Rust связан не с тем, что распределённые алгоритмы невозможно реализовать на TypeScript, а с требованиями к жизненному циклу, владению ключами и соединениями, устойчивому локальному хранилищу и восстановлению после аварии.

Не следует вводить строгий consensus для каждой функции. Механизм выбирается по требуемой семантике:

- CRDT или version vectors — для части replicated state;
- lease с fencing token — для временного единственного владельца;
- leader election — когда работу должно координировать одно устройство;
- строгий consensus — только для данных, которым действительно необходим единый порядок изменений.

Lease, защищающий внешний side effect, используется вместе с fencing token, который проверяет владелец ресурса. Само по себе истечение lease не способно остановить старого лидера после network partition.

Границы сетевого слоя и механизм репликации описаны в [репликации состояния](./07-replication.md) и [общей модели сети](./01-overview.md).

Удалённые jobs должны быть idempotent или использовать ключи дедупликации. Потеря устройства либо lease рассматривается как нормальная ситуация, а не исключительное завершение всей системы.
