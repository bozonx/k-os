# Создание сети и подключение нод

Статус: готов  
Назначение: описать пользовательские сценарии первого запуска: создание новой сети,
подключение ноды с интерфейсом, подключение headless-ноды, а также отзыв и восстановление.

Связанные документы: [identity и доверие](../06-network/02-identity-and-trust.md),
[control log](../06-network/03-control-log.md), [NAT и достижимость](./02-nat-and-reachability.md),
[системная оболочка](../10-clients/04-system-shell.md),
[облачная нода](../10-clients/03-cloud-node.md).

Механизм ключей и enrollment описан в документе об identity; здесь — сценарии и то, что
видит пользователь.

## Первый запуск

При первом запуске десктопного или мобильного приложения пользователь выбирает:

```text
┌─────────────────────────────────────────────┐
│  Создать новую сеть      Присоединиться     │
│  это моё первое          у меня уже есть    │
│  устройство              другое устройство  │
└─────────────────────────────────────────────┘
```

Третьего варианта нет: среда не работает без профиля, а профиль либо создаётся, либо
принимается от существующей сети.

## Создание сети

```text
1. Генерируется profile root key и node identity key в защищённом хранилище.
2. Создаётся первая запись control log: profile-created.
3. Эта нода получает роль device и полномочия администратора.
4. Создаётся первая эпоха ключей данных.
5. Пользователю предъявляется recovery phrase.
```

Приложение становится **единственной нодой сети**. Она полноценна: работает без других
устройств, без интернета и без облачной ноды.

**Recovery phrase** — единственный способ восстановить профиль, если утрачены все
устройства с полномочиями администратора. Она предъявляется один раз и не хранится в
профиле в открытом виде.

Что происходит, если пользователь пропустил сохранение: система не блокирует работу, но
помечает профиль как «без резервного ключа» и периодически предлагает сохранить фразу.
Показать её повторно можно, пока есть доступ к устройству с полномочиями администратора;
после утраты всех таких устройств восстановление невозможно, и это сообщается прямо, а не
мелким шрифтом.

## Подключение ноды с интерфейсом

**Код генерирует подключаемая нода, а сканирует — нода, уже входящая в сеть.**

Это не произвольный выбор, а следствие достижимости. Новая нода ничего не знает о сети и не
может её найти; нода в сети, наоборот, знает, как обратиться по адресу из кода. Кроме того,
код, генерируемый сетью, содержал бы её адреса и ключи — утечка такого кода опаснее утечки
кода одиночного устройства, ещё не имеющего доступа к данным.

```text
Новое устройство N                        Устройство в сети A
──────────────────                        ───────────────────
1. генерирует identity keypair
2. генерирует одноразовый
   секрет подключения
3. показывает QR-код и
   короткий код для ручного ввода
                                          4. пользователь сканирует
                                             или вводит код
                                          5. A подключается к N
                                             по подсказкам из кода
6. взаимная аутентификация с использованием одноразового секрета
7. оба показывают короткую строку сверки
8. пользователь подтверждает совпадение и выбирает роль ноды
                                          9. A подписывает node-enrolled
                                             в control log
                                         10. A передаёт актуальные
                                             эпохи ключей данных
11. N синхронизирует control log и состояние профиля
```

### Состав кода

```text
kos-join:1:<отпечаток публичного ключа N>
          :<подсказки подключения>
          :<одноразовый секрет>
          :<контрольная сумма>
```

- **отпечаток ключа** позволяет A убедиться, что подключается именно к этому устройству;
- **подсказки подключения** — адреса в локальной сети, имя для обнаружения в локальной сети,
  идентификатор BLE, при наличии — постоянный адрес;
- **одноразовый секрет** используется для аутентифицированного обмена и не даёт доступа к
  данным сам по себе;
- **контрольная сумма** нужна для ручного ввода: опечатка обнаруживается сразу, а не после
  неудачного подключения.

Ручной ввод оформляется группами символов, различимых на слух и на вид. QR-код — основной
способ, ручной ввод — запасной.

### Свойства кода

| Свойство | Решение |
|---|---|
| срок жизни | несколько минут; истёкший код перегенерируется одним действием |
| одноразовость | после успешного подключения секрет недействителен |
| утечка кода | сама по себе не даёт доступа к профилю: сеть подключается **к** устройству и требует подтверждения человеком на устройстве в сети |
| подмена устройства | исключается сверкой короткой строки: она вычисляется из обоих ключей и не совпадёт при вмешательстве посредника |
| ручной ввод без визуальной сверки | не допускается: короткая строка сверки показывается обеими сторонами всегда |

Автоматическое присоединение по факту нахождения в одной локальной сети запрещено:
подтверждение человеком обязательно.

### Выбор роли

При подтверждении пользователь выбирает роль новой ноды: `device`, `cloud` или `relay`,
и решает, давать ли ей полномочия администратора. По умолчанию новая нода полномочий
администратора не получает: их наличие определяет, сможет ли она подключать другие
устройства и отзывать существующие.

## Подключение headless-ноды

Headless-нода **может только присоединяться и не может создать сеть**. У неё нет оболочки,
поэтому она не может ни показать диалог подтверждения, ни сканировать QR-код.

```text
1. При первом запуске нода печатает свой код подключения:
   в журнал, в файл рядом с конфигурацией и на консоль.
2. Пользователь вводит код в интерфейсе любой ноды сети.
3. Нода в сети подключается к headless-ноде по подсказкам из кода.
4. Короткая строка сверки показывается на устройстве с интерфейсом;
   на headless-ноде она записывается в журнал, чтобы пользователь мог
   сверить её при наличии доступа к консоли.
5. Пользователь подтверждает подключение и роль.
```

### Сценарий облачной ноды

Проблемы достижимости нет: у ноды постоянный адрес, который и попадает в подсказки
подключения. Это самый простой случай, и он же — рекомендуемый способ получить постоянно
доступную ноду.

### Сценарий ноды без экрана в локальной сети

Контроллер умного дома, одноплатный компьютер. Порядок:

1. Пользователь подключает устройство к локальной сети — кабелем или заранее записанной
   конфигурацией Wi-Fi. Это делается **до** подключения к профилю: K-OS не настраивает
   сетевые интерфейсы хоста.
2. Нода публикует себя для обнаружения в локальной сети под именем из кода.
3. Пользователь вводит код на телефоне или ноутбуке, находящемся в той же сети.
4. Дальше — обычный порядок.

Если устройство ещё не в локальной сети, подключение невозможно, и система сообщает об этом
прямо. Варианты, рассматриваемые как дополнительные и не входящие в базовую поставку:
подключение по BLE для первичной настройки и режим временной точки доступа на устройстве.
Оба требуют оборудования, наличие которого не гарантировано.

## Дальнейшие операции

### Отзыв ноды

Выполняется с устройства с полномочиями администратора: запись `node-revoked`, создание
новой эпохи ключей данных, отказ в установлении сессий.

Что гарантировано: отозванная нода не получает данные, созданные после отзыва, и не может
установить новую сессию с узлами, узнавшими об отзыве. Что **не** гарантировано: удаление
уже полученных данных на отозванном устройстве и мгновенное вступление отзыва в силу для
узлов, ещё не получивших запись. Интерфейс обязан формулировать это честно.

### Переустановка ноды

Переустановка означает новую identity: старый ключ ноды не восстанавливается, потому что он
не покидает устройство. Порядок — отозвать прежнюю ноду и подключить новую как обычно.
Локальные данные прежней установки при этом теряются, реплицируемые — приходят заново.

### Утрата всех устройств с полномочиями администратора

```text
1. Пользователь устанавливает K-OS на новое устройство.
2. Выбирает восстановление профиля и вводит recovery phrase.
3. Устройство получает полномочия администратора, подписав запись
   profile root key.
4. Остальные ноды принимают эту запись как валидную.
5. Пользователь отзывает утраченные устройства и создаёт новую эпоху ключей.
```

Восстанавливаются: состав профиля, права, установленные пакеты, реплицируемые данные — с
той полнотой, с какой они есть на доступных нодах. Не восстанавливаются: локальные данные
утраченных устройств и содержимое файлов, которое существовало только на них.

Если ни одной ноды профиля не осталось и восстанавливать нечего, recovery phrase позволяет
создать пустой профиль с прежней идентичностью — это важно для связанных пользователей,
которым не придётся заново устанавливать связь.

## Проверяемые критерии

- сеть из одной ноды полностью работоспособна;
- код подключения генерирует подключаемая нода, а не сеть;
- headless-нода не может создать сеть и не может сканировать код;
- подключение всегда требует подтверждения человеком на устройстве с интерфейсом;
- утечка кода подключения не даёт доступа к профилю;
- истёкший или использованный код не может быть применён повторно;
- отзыв ноды приводит к созданию новой эпохи ключей данных;
- восстановление по recovery phrase возможно без единого сохранившегося устройства.
