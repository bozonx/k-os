# Облачная нода

Статус: готов  
Назначение: описать headless-ноду пользователя: назначение, гарантии, отличия от device-ноды и от relay.

Связанные документы: [профиль и ноды](../02-architecture/02-profile-and-nodes.md), [NAT и достижимость](../07-onboarding/02-nat-and-reachability.md), [взаимодействие пользователей](../08-federation/01-model.md).


Headless-нода: ядро K-OS без Tauri, WebView и системного UI. Ставится пользователем на собственный сервер или VPS.

Cloud node:

- является **полноправным доверенным членом профиля** и владеет актуальными data encryption keys;
- по умолчанию хранит полную реплику replicated state и полный набор blobs;
- исполняет workers и system services, для которых разрешено удалённое размещение;
- является предпочтительным leader-кандидатом для `cluster-singleton` и точкой rendezvous для Internet-канала;
- **не запускает UI приложений**. Удалённый доступ к UI не проектируется: приложение и его состояние реплицированы, поэтому UI запускается локально на том устройстве, которое пользователь взял в руки.

Прямое следствие доверия: компрометация хоста cloud node означает компрометацию данных профиля. Поэтому cloud node предполагается на подконтрольном пользователю оборудовании, а для сценария «не доверяю хостингу» существует роль `relay`.

Отдельный namespace может быть помечен как `no-cloud` — тогда он не реплицируется на cloud nodes ценой доступности при выключенных личных устройствах.

Система обязана работать без cloud node. Cloud node улучшает доступность и время сходимости, но не является обязательным компонентом.


## Роли облачной ноды

Постоянная доступность — единственное её отличительное свойство, но из него следует
несколько разных ролей.

| Роль | Что даёт |
|---|---|
| полная реплика | содержимое файлов доступно, даже когда личные устройства выключены |
| точка встречи | остальные ноды устанавливают к ней исходящие сессии, снимая вопрос NAT |
| приёмник внешних обращений | сети других пользователей обращаются к ней, а не ловят момент, когда включён телефон |
| маршрутизатор | передаёт обращения к нодам, доступным только через неё |
| шлюз в интернет | выполняет делегированные `net.http`-запросы для нод без прямого доступа |
| предпочтительный лидер | берёт роли `cluster-singleton`, координатора уведомлений, фоновых заданий |
| фоновый исполнитель | выполняет тяжёлые задания вместо телефона и ноутбука |

«Источник истины» — неточная формулировка, и она не используется: единого источника истины
в модели нет, состояние сходится между всеми нодами. Облачная нода лишь **чаще других
доступна**, поэтому чаще оказывается той нодой, у которой есть нужная версия данных.

## Домашний сервер вместо облака

Альтернатива с теми же ролями — постоянно включённая нода на собственном оборудовании,
например одноплатный компьютер. Отличия:

| | Облако (VPS) | Домашний сервер |
|---|---|---|
| постоянный внешний адрес | обычно да | обычно нет, нужен механизм достижимости |
| доступность при отключении домашнего интернета | да | нет |
| доверие к оператору | нужно доверять хостингу | оборудование под контролем |
| стоимость | аренда | разовая |

Для роли точки встречи внешний адрес существен, поэтому домашний сервер без постоянного
адреса решает не все задачи. Рекомендация формулируется честно: постоянно доступная нода
желательна, а какая именно — выбор пользователя.

## Отличие от ноды умного дома

Обе работают headless и обе являются полноправными доверенными членами профиля. Различие в
назначении и в последствиях компрометации:

| | Облачная нода | Нода умного дома |
|---|---|---|
| основное назначение | доступность, хранение, маршрутизация | доступ к подключённому оборудованию |
| полная реплика содержимого | по умолчанию да | обычно нет: мало места |
| постоянный внешний адрес | да | как правило нет |
| последствие компрометации | доступ к данным профиля | доступ к данным профиля и к оборудованию |
| физическая доступность посторонним | нет | часто да |

Отсюда практическое следствие: устройство, физически доступное посторонним, — плохой
кандидат в ноды с ключами профиля. Подробнее — в [устройствах и IoT](../09-devices/01-model.md).

## Установка и эксплуатация

- ставится на сервер пользователя или VPS, подключается к профилю кодом, который печатает
  при первом запуске, см. [создание сети](../07-onboarding/01-network-lifecycle.md);
- оболочки не имеет, поэтому все операции, требующие подтверждения человеком, выполняются
  с устройства с интерфейсом;
- обновляется независимо от остальных нод; профиль обязан работать при неоднородных
  версиях;
- её отсутствие или остановка не ломает систему: сеть продолжает работать, ухудшаются
  доступность и время сходимости.
