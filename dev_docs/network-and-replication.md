# Сеть и репликация K-OS

Статус: design document  
Назначение: зафиксировать модель identity, доверия, времени, транспорта, репликации состояния и файлов между nodes одного профиля.

Смежные документы: [architecture.md](./architecture.md) — слои, модель прав, публичные контракты хранилища и VFS; [capabilities.md](./capabilities.md) — сигнатуры интерфейсов и таксономия ошибок.

Разделение ответственности между документами:

- `architecture.md` описывает **контракт**: что видит приложение (namespaces, пути, состояния файла, семантика вызовов);
- этот документ описывает **механизм**: как состояние и содержимое файлов оказываются на других nodes.

## 1. Цель

Network layer связывает доверенные nodes одного profile через доступные каналы и предоставляет transport-independent основу для:

- синхронизации состояния и файлов;
- доставки событий;
- удалённого исполнения commands и jobs;
- передачи package artifacts;
- обнаружения nodes и оценки их доступности.

Сеть не делает распределённые операции неотличимыми от локальных. Недоступность node, задержка, отмена, повтор, частичный результат и конфликт являются частью публичной семантики.

Ключевое продуктовое следствие модели: **состояние прозрачно, исполнение и ресурсы — нет**. Пользователь на любом своём устройстве видит те же приложения и те же данные. Но окно, соединение, GPIO-пин и запущенный процесс всегда принадлежат конкретному устройству.

## 2. Роли nodes

Профиль состоит из нод разных ролей. Роль объявляется при enrollment и записывается в control log.

| Роль | Ключи профиля | UI приложений | Исполнение workers | Назначение |
|---|---|---|---|---|
| `device` | да | да | да | ноутбук, десктоп, телефон |
| `cloud` | да | нет | да | всегда доступное хранилище, синхронизация, фоновые сервисы |
| `relay` | нет | нет | нет | шифрованный транзит и хранение непрозрачных данных |

### 2.1. Device node

Полноценный узел с системным UI. Может быть офлайн, приостановлен, выключен. Не предполагается, что device node доступен в произвольный момент.

### 2.2. Cloud node

Headless-нода: ядро K-OS без Tauri, WebView и системного UI. Ставится пользователем на собственный сервер или VPS.

Cloud node:

- является **полноправным доверенным членом профиля** и владеет актуальными data encryption keys;
- по умолчанию хранит полную реплику replicated state и полный набор blobs;
- исполняет workers и system services, для которых разрешено удалённое размещение;
- является предпочтительным leader-кандидатом для `cluster-singleton` и точкой rendezvous для Internet-канала;
- **не запускает UI приложений**. Удалённый доступ к UI не проектируется: приложение и его состояние реплицированы, поэтому UI запускается локально на том устройстве, которое пользователь взял в руки.

Прямое следствие доверия: компрометация хоста cloud node означает компрометацию данных профиля. Поэтому cloud node предполагается на подконтрольном пользователю оборудовании, а для сценария «не доверяю хостингу» существует роль `relay`.

Отдельный namespace может быть помечен как `no-cloud` — тогда он не реплицируется на cloud nodes ценой доступности при выключенных личных устройствах.

Система обязана работать без cloud node. Cloud node улучшает доступность и время сходимости, но не является обязательным компонентом.

### 2.3. Relay node

Узел без ключей профиля. Видит только зашифрованные op log records и blobs и метаданные маршрутизации: profile ID в псевдонимизированной форме, размеры, тайминги.

Relay:

- ретранслирует сессии между nodes за NAT;
- может хранить зашифрованные blobs и op log для доставки офлайн-узлам;
- не может исполнять workers, читать данные и участвовать в координации;
- обязан проверять авторизацию по control log, чтобы отозванный node не мог продолжать выкачивать данные.

### 2.4. Node capability descriptor

Каждый node публикует в replicated state описание своих возможностей: платформа, архитектура, роль, доступные capabilities, наличие оборудования, класс питания, метрика сети, объём хранилища, background-гарантии.

Дескриптор является входом для `placement` (см. `architecture.md`, раздел о распределённом исполнении) и обновляется при изменении состояния устройства. Он реплицируется как обычное replicated state, поэтому placement можно вычислить и на офлайн-узле по последнему известному состоянию — с явной пометкой staleness.

## 3. Identity и доверие

### 3.1. Иерархия ключей

```text
profile root key
├── admin authority (подмножество device nodes)
├── data key epochs: DEK[0], DEK[1], ...
│   └── производные ключи namespace / blob
└── node identity keys (по одному на node)
```

- **profile root key** создаётся при создании профиля, предъявляется пользователю как recovery phrase и хранится офлайн. Используется только для восстановления, когда потеряны все admin-устройства.
- **node identity key** генерируется на устройстве в платформенном secure storage и не покидает его. Класс состояния — `device-bound-secret`.
- **data key epoch** шифрует содержимое op log records и blobs. Новая эпоха создаётся при revocation node и при плановой ротации.

Данные шифруются на уровне записи и blob, а не только на уровне транспорта. Это условие существования роли `relay` и защита хранилища на потерянном устройстве.

Ротация эпохи не перешифровывает историю автоматически. Перешифрование прошлых данных является отдельной фоновой операцией с явной стоимостью; документ не обещает, что после revocation старые данные становятся недоступны отозванному устройству.

### 3.2. Enrollment

```text
1. Новый node генерирует identity keypair в secure storage.
2. Устанавливается канал между новым node и admin-устройством:
   LAN, либо BLE, либо ручной перенос кода.
3. Взаимная аутентификация с short authentication string:
   пользователь сверяет код или сканирует QR на обоих устройствах.
4. Admin-устройство подписывает запись `node-enrolled`
   с публичным ключом, ролью и разрешёнными node capabilities.
5. Admin-устройство передаёт актуальные data key epochs
   по установленному аутентифицированному каналу.
6. Новый node синхронизирует control log и replicated state.
```

Enrollment всегда требует подтверждения человеком на уже доверенном устройстве. Автоматическое присоединение по факту нахождения в одной локальной сети запрещено.

### 3.3. Revocation

```text
1. Admin-устройство добавляет запись `node-revoked`.
2. Создаётся новая data key epoch, распространяемая
   на оставшиеся nodes.
3. Каждый node и relay, увидевший запись, отказывает
   отозванному ключу в установлении сессии.
```

Что гарантируется: отозванный node не получает данные, созданные после revocation, и не может устанавливать новые сессии с узлами, узнавшими о revocation.

Что **не** гарантируется: удаление уже полученных данных на отозванном устройстве и мгновенное вступление revocation в силу для узлов, которые ещё не получили запись. Это ограничение фиксируется как проектное решение, а не как дефект.

## 4. Control log профиля

Control log — единственная часть системы, для которой требуется согласованный порядок и строгая проверка авторизации. Всё остальное состояние использует более слабые модели.

Содержимое control log:

```text
profile-created
node-enrolled
node-revoked
node-role-changed
admin-granted
admin-revoked
key-epoch-created
package-installed
package-version-activated
package-removed
grant-added
grant-revoked
```

### 4.1. Устройство лога

Control log — это hash-linked DAG подписанных записей, а не quorum-based журнал. Каждая запись содержит хеши родительских записей, идентификатор подписавшего node и подпись.

Consensus-алгоритм с кворумом здесь неприменим: личные устройства большую часть времени выключены, и требовать кворум для добавления устройства или выдачи разрешения означало бы неработоспособность системы.

### 4.2. Правила слияния

- запись валидна, если подписавший обладал требуемыми полномочиями в том состоянии DAG, на которое ссылается;
- параллельные ветви объединяются объединением записей;
- **безопасность имеет приоритет**: при конфликте `node-revoked` побеждает конкурирующий `node-enrolled` или `admin-granted` для того же субъекта;
- взаимный revocation двух admin-устройств приводит к отзыву обоих. Это осознанно выбранный безопасный исход; восстановление выполняется новым enrollment, подписанным оставшимся admin или profile root key;
- записи монотонны: отменить запись можно только новой записью, но не удалением.

### 4.3. Ограничение области

В control log попадает только то, что определяет доверие и состав профиля. Пользовательские данные, содержимое приложений и оперативное состояние в control log не помещаются.

## 5. Каналы и транспорт

### 5.1. Слои

```text
Node identity and trust (control log)
          ↓
Peer discovery and reachability
          ↓
Link adapters: LAN / Internet / BLE
          ↓
Authenticated encrypted sessions
          ↓
Multipath connection manager
          ↓
Streams / messages / datagrams
          ↓
Replication / RPC / events / blob transfer
```

Link adapter отвечает только за конкретный канал. Identity, шифрование, повторная установка session, маршрутизация и прикладные сообщения не дублируются отдельно для LAN, Internet и Bluetooth.

### 5.2. Свойства каналов

| Канал | Назначение | Ограничения |
|---|---|---|
| LAN | основной путь: репликация, blobs, RPC | требуется общая сеть, изоляция клиентов на части Wi-Fi-сетей |
| Internet | доступность вне дома, доставка через cloud/relay | латентность, metered-трафик, NAT |
| BLE | discovery, enrollment, control-сообщения, малые дельты | низкая пропускная способность, малый MTU, ограничения фонового режима |

BLE не используется для передачи blobs и полной синхронизации. Его роль — обнаружение, начальная установка доверия и обмен небольшими управляющими сообщениями, в том числе для поднятия LAN-соединения.

### 5.3. Выбор канала

Локальный канал предпочтителен по умолчанию, но порядок не задан жёстко. Connection manager оценивает:

- reachability и стабильность;
- latency и bandwidth;
- metered/unmetered status;
- энергетическую стоимость;
- доверие к каналу;
- максимальный размер передачи;
- возможность streaming и resume;
- доступность в фоне;
- стоимость установки соединения.

Session может менять link без изменения identity peer и в дальнейшем использовать несколько links одновременно.

### 5.4. Discovery и приватность

Обнаружение в локальной сети не должно раскрывать стабильный идентификатор пользователя или устройства. В эфир публикуется вращающийся идентификатор, вычисляемый из ключа профиля; реальная identity раскрывается только после аутентифицированного handshake.

## 6. Модель времени

Ошибки со временем являются одним из основных источников дефектов в распределённых системах, поэтому модель фиксируется явно.

### 6.1. Правила

1. **Wall clock — это данные, а не порядок.** Он используется для отображения пользователю и для расписаний, но никогда не определяет порядок применения операций.
2. **Причинность выражается явно.** Для обнаружения конфликтов используются version vectors или dotted version vectors по объекту.
3. **Порядок для разрешения ties — hybrid logical clock.** HLC — это `(physical_ms, logical, node_id)`, монотонно возрастающий и согласованный с причинностью. HLC используется для LWW-разрешения и для человекочитаемого порядка событий.
4. **Защита от неверных часов.** Физическая часть входящего HLC ограничивается сверху локальным временем плюс объявленный `max_clock_skew`. Node с сильно убежавшими часами не может произвольно «выиграть» все LWW-конфликты в будущем.
5. **Таймауты, retry и leases используют только monotonic clock** того узла, который их измеряет. Сравнение локального wall clock с удалённым запрещено.
6. **Истечение lease не является механизмом безопасности.** Безопасность обеспечивает fencing token — монотонно растущий счётчик, который проверяет владелец ресурса. Expiry — оптимизация, позволяющая быстрее переизбрать владельца.
7. **Проверка срока действия токенов** требует wall clock. Допускается расхождение в пределах `max_clock_skew`, оценка расхождения с peer выполняется при handshake и хранится в сессии.
8. **Пользовательские расписания хранятся в гражданском времени** с IANA timezone, а не в абсолютных отметках. Вычисление ближайшего срабатывания выполняется тем node, который выполняет задачу.
9. **Дедупликация периодических задач** scope `per-user` выполняется по ключу `(schedule id, гражданское время срабатывания)`, а не по локальной метке времени, иначе задача выполнится на каждом устройстве.

### 6.2. Требование к коду

Ядро не обращается к системным часам напрямую. Wall clock, monotonic clock и таймеры доступны только через `ClockAdapter`. Это требование тестируемости: без него детерминированная симуляция невозможна.

## 7. Сообщения и удалённые вызовы

### 7.1. Обязательный контекст

Любая durable или повторяемая операция содержит:

```text
profile ID
source node ID
destination or routing scope
protocol/schema ID and version
operation ID
idempotency key when applicable
deadline
causal context when required
authorization context
trace ID
```

Caller identity не передаётся как доверенное поле приложения. Она выводится из аутентифицированной node session и delegation capability, выданной системным runtime.

### 7.2. Семантика доставки

Exactly-once не является базовой гарантией. Для каждого типа operation явно определяются:

- at-most-once или at-least-once delivery;
- idempotency key;
- срок хранения deduplication records;
- timeout и retry budget;
- cancellation semantics;
- допустимость выполнения после deadline;
- владение результатом;
- поведение при network partition.

Локальный и удалённый вызов используют один versioned contract, но удалённый результат всегда допускает ошибки `unreachable`, `deadline-exceeded`, `placement-changed`, `authorization-expired` и `result-unknown`.

`result-unknown` не является исключительной ситуацией. Вызывающий код обязан её обрабатывать: либо операция идемпотентна, либо есть способ узнать её исход.

## 8. Репликация состояния

### 8.1. Базовый инвариант

**Реплицируется операция, а не файл базы данных.** Побайтовая синхронизация файлов SQLite или другого движка между nodes запрещена: это гарантированное повреждение данных при параллельной записи. Локальный движок хранения является деталью реализации конкретного node и может отличаться между платформами.

Это правило распространяется и на состояние самой системы: registry пакетов, grants, настройки — тоже наборы операций.

### 8.2. Атомарность локальной записи

Подтверждённая локальная mutation атомарно обновляет materialized state и durable replication outbox в одной транзакции. Sync не восстанавливает пропущенные изменения путём наблюдения за обычной базой постфактум.

Нарушение этого правила невозможно исправить позднее без потери данных, поэтому оно относится к критериям корректности архитектуры.

### 8.3. Структура операции

```text
object ID           стабильный, не зависящий от пути или имени
namespace           область репликации и класс данных
type                тип реплицируемой структуры
dot                 (origin node ID, счётчик)
hlc                 отметка для разрешения ties
causal context      version vector или зависимости
schema version      версия схемы данных приложения
payload             содержимое операции
```

### 8.4. Типы реплицируемых данных v0

| Тип | Семантика | Применение |
|---|---|---|
| `document` | map с LWW по полям | настройки, записи приложений |
| `set` | observed-remove set | коллекции, теги |
| `counter` | grow-only или PN counter | счётчики |
| `log` | append-only | события, история |
| `blob-ref` | ссылка на immutable content | файлы, вложения |
| `coordinated` | запись под lease | то, что нельзя разрешить слиянием |

Приложение выбирает **семантику данных**, а не алгоритм репликации. Реализация типа может измениться без изменения публичного API.

Совместное редактирование текста в v0 не входит в набор типов. Оно требует отдельного типа последовательности и проектируется отдельно.

### 8.5. Consistency profiles

- `local-first` — всегда доступна запись, слияние автоматическое. Профиль по умолчанию.
- `coordinated` — запись требует lease или лидера, при отсутствии связи операция недоступна и возвращает явную ошибку.

Приложение указывает профиль на уровне namespace или объекта. Молчаливого понижения гарантий не происходит.

### 8.6. Протокол синхронизации

```text
1. Сессия установлена и авторизована по control log.
2. Обмен version vectors по namespaces.
3. Передача недостающих операций.
4. Применение операций и обновление materialized state.
5. Отдельная передача blobs по потребности.
```

Передача операций и передача содержимого файлов разделены: метаданные дёшевы и реплицируются везде, содержимое передаётся по политике.

### 8.7. Компактизация и tombstones

Op log компактизируется по достижении причинной стабильности: операция может быть свёрнута, когда её получили все nodes профиля. Постоянно выключенный node блокирует компактизацию, поэтому вводится горизонт: node, не выходивший на связь дольше объявленного срока, считается отставшим и синхронизируется через полный state transfer, а не через историю операций.

Tombstones собираются по тому же горизонту. Значение горизонта — параметр профиля, а не константа.

## 9. Файлы

Публичная модель VFS, пути и состояния файла описаны в `architecture.md`. Здесь фиксируется механизм.

### 9.1. Разделение метаданных и содержимого

```text
metadata namespace          реплицируемый CRDT: дерево, имена, атрибуты, ссылки на blob
content-addressed blobs     неизменяемое содержимое, адресуемое хешем
per-node materialization    что физически лежит на конкретном node
external mounts             доступ за пределы VFS, не реплицируется
```

File identity не зависит от пути. Файл имеет стабильный ID; имя и родительский каталог являются атрибутами. Переименование и перемещение — операции над метаданными, а не удаление с созданием.

### 9.2. Blob store

- содержимое разбивается на чанки алгоритмом content-defined chunking с целевым размером порядка 1 MiB;
- blob описывается манифестом: список хешей чанков и общий хеш содержимого;
- дедупликация выполняется на уровне чанков между версиями и между файлами;
- чанки неизменяемы, что делает передачу возобновляемой и параллельной по источникам;
- сбор мусора удаляет чанки, на которые нет ссылок из метаданных ни одной живой версии.

Конкретный алгоритм chunking и хеш-функция фиксируются отдельным ADR, но контракт «blob = хеш содержимого + манифест чанков» является частью модели.

### 9.3. Selective sync и материализация

Метаданные реплицируются на все nodes: пользователь видит полное дерево файлов с любого устройства. Содержимое материализуется по политике:

- явный pin пути или поддерева на конкретном node;
- декларация потребности в manifest компонента;
- квота хранилища для профиля на этом node;
- давность обращения;
- класс node: `cloud` по умолчанию хранит полное зеркало.

Вытеснение содержимого не удаляет файл: запись остаётся в состоянии `evicted` и может быть восстановлена при доступности источника.

### 9.4. Конфликты

- параллельная запись содержимого одного файла сохраняет обе версии; запись переходит в состояние `conflicted`, разрешение выполняется приложением или пользователем, автоматическая потеря версии запрещена;
- коллизия имён в каталоге разрешается детерминированно переименованием более поздней по HLC записи с сохранением исходного имени в атрибутах;
- коллизия имён, различающихся только регистром, обрабатывается так же: platform-specific ограничения не должны приводить к разному дереву на разных платформах.

### 9.5. Внешние монтирования

Внешние точки монтирования не реплицируются. Реплицируется только факт существования mount и его описание, чтобы пользователь понимал, на каком устройстве находятся данные.

На Android внешний доступ выражается не путями, а SAF-идентификаторами с отзываемым системой разрешением. Adapter обязан представлять это явно: отзыв доступа платформой — нормальное состояние, а не ошибка.

## 10. Распространение приложений

```text
package artifacts   immutable blobs, адресуемые хешем
package registry    реплицируемое состояние профиля
installation        запись в registry, а не копирование файлов
materialization     загрузка артефактов на конкретный node
```

Установка приложения — операция над replicated state. Она немедленно видна всем nodes; артефакты подтягиваются каждым node по мере необходимости запуска компонента.

Обновление создаёт новую версию: артефакты неизменяемы, поэтому старая и новая версия сосуществуют, а rollback является переключением активной версии.

Расширение permissions при обновлении не активируется автоматически. Новая версия переходит в состояние `pending-grant` и не запускается ни на одном node, пока пользователь не подтвердит изменение. Подтверждение — запись в control log.

Подпись пакета проверяется при установке и при материализации на каждом node отдельно.

## 11. Удалённое исполнение и delegation

Право компонента на локальный ресурс не переносится на remote node автоматически.

Delegation token содержит: издающий node, субъекта (profile, package, component, execution), целевую capability и её scope, deadline, признак возможности дальнейшей передачи и подпись.

Проверка на целевом node двусторонняя:

1. token валиден, не истёк, издан узлом с соответствующими полномочиями;
2. локальная политика целевого node сама по себе разрешает этому package использовать эту capability здесь.

Отсутствие второй проверки означало бы, что компрометация одного устройства даёт доступ к оборудованию всех остальных.

По умолчанию delegation непереходящая. Результат удалённого вызова подчиняется семантике раздела 7.

Типовой сценарий: UI на телефоне управляет GPIO на Linux-ноде. Это основной, а не краевой случай, поэтому remote capability является частью базовой модели, а не расширением.

## 12. Координация

Единый механизм не используется для всех задач:

- causal replication и CRDT — для большинства пользовательских данных;
- deterministic conflict resolution — для части domain state;
- lease с fencing token — для временного единственного владельца;
- leader election — для размещения и координации, но не как гарантия доступности;
- quorum consensus — не используется. Требуемое согласие о составе профиля и правах обеспечивается control log из раздела 4.

Персональные nodes часто выключены, поэтому система не требует кворума для обычной локальной работы. При наличии cloud node он является предпочтительным кандидатом в лидеры как наиболее доступный.

Lease, защищающий внешний side effect, всегда используется вместе с fencing token. Само по себе истечение lease не останавливает старого владельца после network partition.

## 13. Security boundaries

- каждый node имеет отдельную криптографическую identity в платформенном secure storage;
- добавление node требует enrollment с подтверждением человеком;
- транспорт использует взаимную аутентификацию и шифрование независимо от канала;
- данные шифруются на уровне записей и blobs, а не только в канале;
- удалённое исполнение требует явной ограниченной delegation capability и согласия целевого node;
- revocation узла влечёт создание новой key epoch;
- relay не получает ключей и обязан проверять авторизацию по control log;
- discovery не раскрывает стабильные идентификаторы до аутентификации.

## 14. Тестируемость сети

Требования являются архитектурными, а не рекомендациями: их невозможно добавить позднее без переписывания.

- каждый link adapter имеет mock-реализацию;
- ядро запускается как N нод в одном процессе поверх симулированной сети;
- симулятор управляет: задержкой, потерей, дублированием, переупорядочиванием сообщений, разделением сети, падением и перезапуском node, расхождением часов, заполнением диска, повреждением blob;
- время в симуляции виртуальное, через `ClockAdapter`;
- прогон детерминирован по seed и воспроизводится по записи.

Проверяемые инварианты:

- сходимость: при прекращении изменений и восстановлении связи все nodes приходят к одному состоянию;
- отсутствие потери подтверждённой mutation при падении в любой момент;
- отсутствие двойного внешнего side effect без корректного fencing token;
- невозможность получения admin-полномочий без валидной цепочки подписей в control log;
- отсутствие материализации файла с содержимым, не соответствующим хешу.

## 15. Что намеренно не выбирается сейчас

- конкретный wire format сообщений;
- QUIC, WebSocket или другой основной Internet transport;
- конкретная реализация relay infrastructure;
- CRDT-библиотека и локальный storage engine;
- алгоритм content-defined chunking и хеш-функция;
- протокол NAT traversal;
- политика UI разрешения конфликтов;
- окончательный Bluetooth-профиль и формат сообщений BLE.

Эти решения принимаются отдельными ADR после стабилизации identity, control log, capability contracts и storage mutation model.
