Новая идея ноябрь 2026



коротко

- k-os — это надстройка над любой хостовой ос (linux, windows, macos, android), а не замена ей. хостовая система остается полнофункциональной, k-os подстраивается под нее
- по сути это демон, который создает общее пространство пользователя и синхронизирует его между всеми устройствами пользователя, объединенными в одну сеть
- пользовательские файлы — обычные файлы хоста в `~/kos/`, их можно менять и из хоста, и через k-os. поэтому синхронизация двусторонняя, по типу syncthing
- приложения — обычные внешние программы хоста на любом языке. своей графической оболочки для приложений нет, старая идея с web ui + wasm внутри k-os отброшена
- чтобы работать с k-os, приложение использует sdk: файлы, сеть пользователя, интернет через k-os, общие llm/stt
- приложения не ограничиваем принудительно, иначе не получится универсальных приложений. вместо этого в репозитории приложений помечаем тех, кто ходит в хост мимо k-os
- граница доверия — процесс демона. всё, что внутри процесса приложения, включая sdk, считается недоверенным
- драйверы — часть системы и не устанавливаются. доустанавливать можно только io (механизм), но не политику
- раздача обновлений и синхронизация без мастера: раздает тот, у кого уже есть данные
- свой дистрибутив необязателен, это просто удобная готовая сборка



k-os внешне

- это демон/сервис пользователя, где происходит вся работа
- необязательный привилегированный помощник (root-демон) с узким api — только для того, что без прав не сделать, см. «подумать»
- cli для управления и статуса
- gui — трей иконка со статусом, начальный экран для подключения к своей сети и центр управления (настройки системы и сервисов)
- написано на rust
- ставится на любую ос как обычное приложение, без root: linux, windows, macos, android



k-os внутри

- в нем запущены системные сервисы и драйверы
- сама система тонкая: по сути выходы вовне и платформа для сервисов и драйверов
- имеет свои хранилища для программ, кэша, логов и предоставляет программам и сервисам свои папки
- управляет папкой пользователя `~/kos/`
- единые llm и stt модели в системе для использования любыми приложениями
  - это системный сервис с очередью на gpu: несколько приложений не грузят по своей копии модели и не дерутся за gpu
  - доступ через capability `ml.llm`, `ml.stt`



раскладка файлов на хосте

- `~/kos/` — пользовательские папки: документы, загрузки, медиа, проекты и т.д.
  - обычные незашифрованные файлы, полностью доступны из хоста
  - синхронизируются между устройствами
  - в `~/kos/` можно монтировать другие диски средствами хоста — тогда они видны и хосту, и k-os
  - можно монтировать на уровне k-os — тогда монтирование видно только через k-os (sdk, файловый менеджер), но не хосту
- системные данные k-os — в стандартном для платформы месте данных приложения, не в `~/kos/`
  - linux `~/.local/share/k-os/`, windows `%LOCALAPPDATA%\k-os\`, macos `~/Library/Application Support/k-os/`, android — внутреннее хранилище приложения
  - там: приложения, данные приложений, кэш, логи, база состояния, blob store
- папки приложений (как в старой vfs): у каждого приложения свое поддерево
  - `replicated/` — синхронизируется между устройствами
  - `local/` — свое на каждом устройстве
  - `cache/` — можно удалить в любой момент
  - `tmp/` — очищается при перезапуске
  - всё, что принадлежит приложению, лежит в одном поддереве, поэтому удаление приложения убирает всё одной операцией



синхронизация пользовательских файлов

- двусторонняя: изменения приходят и из хоста (через watcher файловой системы и периодический скан), и из сети
- у файла стабильный id, не зависящий от пути: переименование и перемещение — это операции над метаданными, а не удаление + создание
- содержимое режется на чанки (fastcdc ~1 MiB, blake3) и хранится в blob store, поэтому одинаковые данные не передаются дважды
- конфликт — это не перезапись: обе версии сохраняются, вторая получает имя вида `файл (конфликт, ноутбук, 2026-11-24).ext`
- удаление и перезапись, пришедшие с другого устройства, не уничтожают данные: прежняя версия уходит в корзину и историю версий k-os на N дней. это главная защита от «удалил на одном устройстве — пропало везде»
- `.kosignore` для исключений (node_modules, временные файлы и т.д.)
- volumes (из старой спеки): большие коллекции (фото, видео) хранятся только на выбранных устройствах, а не на всех
- синхронизация без мастера: каждый узел сходится со всеми доступными, отдельной главной ноды нет
- правила путей — пересечение ограничений всех платформ (без `\ : * ? " < > |`, без имен con/nul/..., без двух имен, отличающихся только регистром). проверяется при записи, иначе дерево разойдется между linux и windows



безопасность данных

- пользовательские файлы по умолчанию не шифруем: это обычные файлы хоста, их защищает вход в аккаунт хоста, как и все остальные файлы пользователя
- при первой настройке k-os проверяет, включено ли шифрование диска хоста (luks / bitlocker / filevault / android по умолчанию), и если нет — предлагает включить. это единственная реальная защита от кражи выключенного устройства, и она лучше любого шифрования отдельных файлов
- отдельные папки пользователь может явно сделать зашифрованными, с пониманием, что из хоста они будут недоступны
- шифруются внутренние данные k-os, куда пользователю не нужно ходить из хоста:
  - ключ ноды и секреты — в хранилище ключей платформы (secret service / kwallet, windows credential manager / dpapi, macos keychain, android keystore), ключ не покидает устройство
  - база состояния k-os — зашифрованный sqlite, ключ из хранилища ключей платформы
- всё, что уходит на чужие или не до конца доверенные ноды (облачная нода на vps, relay), шифруется на уровне чанков и записей ключами сети. relay ключей не получает
- шифрование имен файлов через хэш не делаем



приложения

- приложения — внешние, это обычные программы хоста, пишутся на любом языке, где есть sdk: rust, tauri, electron, python, c++, c, c#, go и т.д.
- своей графической оболочки для приложений нет: окна, ярлыки и меню — хостовые
- приложение включает в себя все библиотеки и зависимости, включая sdk
- через sdk приложение получает: файлы пользователя и свои папки, сеть пользователя (обращение к нодам и их api), запросы в интернет через k-os, логи, кэш, события, уведомления, llm/stt
- gpu и специфичные устройства приложение может использовать напрямую
- принудительно приложения не ограничиваем: тогда не получится универсальное приложение, которое работает и без k-os
- в репозитории приложений ставим отметки, если приложение:
  - само ходит в хостовые папки мимо k-os
  - само ходит в интернет мимо k-os
  - приложение без отметок всё делает через k-os
- отметки показываются пользователю при установке и в каталоге
- форки популярных приложений (браузер, офис) не делаем: пользовательские файлы — обычные файлы хоста, поэтому обычный браузер и офис и так с ними работают, а поддержка форков браузера неподъемна
- установка и обновление — через k-os, он ставит приложения в свои папки. ярлыки и desktop файлы указывают на эти файлы
  - ярлыки создаются в профиле пользователя без прав администратора, удаление приложения удаляет ярлыки
- в android k-os ставит apk как обычное приложение
- ставить приложения через системные репозитории тоже можно. это имеет смысл для приложений, которые хотят быть одновременно обычными и поддерживать k-os



sdk и связь с демоном

- граница доверия — процесс демона. sdk живет в процессе приложения, поэтому считается недоверенным: приложение может его подменить. в sdk нет ни настоящего драйвера, ни прямого доступа к io
- «экземпляр драйвера» в sdk — это клиентский stub: асинхронный, работает в потоке приложения, а вся логика драйвера (права, квоты, метрики, отзыв) — в демоне
- права проверяются один раз при открытии ресурса, а не на каждую операцию. приложение получает непрозрачный handle, дальше данные идут быстрым путем:
  - файлы и сокеты — демон открывает ресурс сам и передает приложению готовый дескриптор (unix socket + scm_rights на linux/macos, duplicatehandle на windows, binder на android). накладных расходов на данные ноль
  - потоки, которые идут через k-os (сеть пользователя, зашифрованное хранилище) — кольцевой буфер в разделяемой памяти на каждый handle
  - управляющие вызовы — локальный ipc (unix socket / named pipe / binder)
- handle привязан к приложению и процессу: при завершении процесса закрывается, при отзыве права становится `revoked`
- протокол sdk ↔ демон версионированный (cbor со схемой), sdk на разных языках генерируется из одной схемы
- приложение обязано обрабатывать `unavailable`: устройство, сеть или нода могут отсутствовать, и это нормальное состояние, а не ошибка



асинхронность и io

- цель — никакого бутылочного горлышка: мощный поток (видео, копирование) не должен забивать всё остальное
- io соответствуют реальным независимым устройствам и шинам хоста:
  - свой поток io (actor) на каждое физическое блочное устройство — на диск, а не на раздел
  - свой поток io на каждое эксклюзивное устройство и шину: serial порт, gpio чип, bluetooth адаптер, usb устройства
  - сеть — общий асинхронный реактор: сетевую карту выбирает маршрутизация ос, поэтому поток на сетевую карту не нужен. справедливость — по потокам данных (соединениям), а не по картам
- io — это потоки внутри демона, а не отдельные процессы: процесс на каждую шину дает лишний ipc без выигрыша. отдельный процесс — только для доустановленных io-расширений, чтобы их сбой не ронял демон
- против бутылочного горлышка:
  - очереди ограничены, при переполнении — backpressure / `quota-exceeded` с `retry-after`, а не бесконечный буфер
  - очередь, лимиты и учет — по каждому потребителю, одно приложение не исчерпает очередь другого
  - классы приоритета: служебный трафик k-os (управление сетью, ключи) > интерактивный > фоновый массовый (синхронизация, обновления). приложение не может повысить свой приоритет
  - в сети между нодами каждый поток данных идет своим stream в quic, поэтому большой файл не блокирует мелкие сообщения
  - тяжелые данные по возможности идут мимо демона (передача дескриптора), демон не копирует байты, которые можно не копировать
  - отмена запроса сразу освобождает место в очереди



внутренние сущности k-os

- io
  - обертки над реальными io, на каждое независимое устройство — свой экземпляр в своем потоке, включая однотипные устройства, например диски
  - все io идут в комплекте сразу: пока устройства нет, код io занимает только место на диске и не инициализируется
  - дополнительно можно ставить io-расширения для редкого оборудования и протоколов: отдельно подписанные, с явным подтверждением пользователя, в отдельном процессе
- драйвера
  - прослойка между io и потребителем — сервисом или приложением
  - все драйвера — часть системы и не доустанавливаются: от них зависят права, квоты и отзыв доступа для всех приложений. механизм (io) можно доустановить, политику (драйвер) — нет
  - чтобы доустановленное io работало без своего драйвера, драйвера обобщены по классам ресурса:
    - разделяемый (сокеты, файлы) — одновременный доступ, изоляция по потребителю
    - эксклюзивный (serial, камера, линия gpio) — один владелец, остальным `unavailable` с указанием владельца
    - арендуемый (gpio под фоновой задачей) — владение через lease
  - драйвер выдает handle и проверяет его при каждой операции (владелец, scope, отзыв), собирает метрики по каждому приложению
  - драйвер не читает манифест и не решает, выдавать ли право — это делает capability service
  - драйвер работает в потоке своего io, отдельного потока у драйвера нет
- сервис
  - сервис — это воркер, который реагирует на события, а не работает постоянно в фоне
  - системные сервисы — внутренние: на rust, внутри демона, поставляются вместе с k-os
  - сторонние сервисы — только внешние: отдельный процесс через sdk, как приложение без окна. сторонний нативный код в процессе демона не запускаем
  - k-os запускает внешний сервис по событию и останавливает, когда он не нужен
  - сервис без своего окна не выглядит как приложение: он виден и настраивается в центре управления
- приложение
  - только внешнее, работает с k-os через sdk, см. выше



настройки и ui сервисов

- единый центр управления k-os: системные настройки, сеть, устройства, приложения, сервисы
- единый формат конфигов как правило хорошего тона:
  - сервис объявляет в манифесте схему настроек: поля, типы, значения по умолчанию, описания, группы
  - значения хранятся в k-os (toml), сервис читает их через sdk и получает событие при изменении
  - у каждой настройки область: на весь профиль (синхронизируется между устройствами) или на конкретное устройство
  - центр управления по схеме сам генерирует форму, разработчику не нужно писать ui
- три уровня, разработчик выбирает сам:
  1. только схема — форма генерируется автоматически (по умолчанию)
  2. своя панель на html/js/css внутри центра управления — в изолированном контейнере, работает только через api k-os
  3. свой ui / свое приложение / свой формат конфигов — можно, но в центре управления тогда только ссылка
- центр управления на tauri: ему нужен webview для панелей сервисов. трей и начальный экран — slint
- диалоги выдачи прав, подтверждение подключения устройства и подобное рисует только k-os, приложение не может нарисовать неотличимый системный запрос



менеджер приложений V1

- доверие — от ключа издателя, а не от места хранения:
  - разработчик заводит аккаунт и ключ издателя, публикует подписанный манифест версии с хэшами всех файлов
  - новая версия принимается только от издателя, зафиксированного при установке
  - сервис регистрации — это каталог и индекс подписанных манифестов, а не источник доверия
- сами файлы хранятся в релизах github, gitlab и т.д., это просто недоверенное хранилище байт: либо подпись и хэши сходятся, либо файл отбрасывается
- набор установленных приложений и их версии — общие для всей сети пользователя. артефакты — свои под каждую платформу, приложение без сборки под платформу на этом устройстве просто недоступно
- раздача без мастера:
  - любое устройство, у которого есть сеть, проверяет обновления и публикует найденную версию в сеть пользователя
  - каждое устройство скачивает нужное ему, предпочитая локальную сеть интернету; первое скачавшее сразу становится источником для остальных
  - чтобы несколько устройств в одной квартире не качали одно и то же из интернета, устройство берет короткий lease на загрузку. потеря lease ничего не ломает, только лишний трафик
- пользователи могут включать ноды для ретрансляции приложений и раздавать их своим контактам — только публичное содержимое
- обновление, которое расширяет права или меняет отметки (хост-файлы / интернет мимо k-os), не применяется без подтверждения пользователя
- откат и удержание версии — на уровне всей сети пользователя
- защита от подмены установленных файлов:
  - при установке проверяются подпись издателя и хэши всех файлов
  - linux: на файлы включается fs-verity (ext4, btrfs, f2fs) — ядро проверяет содержимое при чтении, файл становится неизменяемым, а проверка при запуске — сравнение одного digest
  - если установлен root-помощник — хранилище приложений принадлежит root и недоступно для записи пользователю
  - android — подпись apk проверяет система и не дает поставить обновление с другой подписью; k-os сверяет сертификат с ключом издателя
  - честно признаем: если вредонос уже работает от имени пользователя, он может многое и без подмены файлов (например, подменить ярлык). поэтому это защита от случайной порчи и подмены при доставке, а не от вредоноса в сессии пользователя



менеджер приложений V2

- на базе распределенной сети на майнерах



сеть

- в пространстве k-os действует оверлейная сеть, где у каждой ноды свой уникальный id (ключ ed25519)
- в сети пользователя у устройств пользователя свои id
- добавление устройства в сеть требует подтверждения человеком на уже доверенном устройстве
- состав сети и права хранятся в журнале подписанных записей (control log): кворум не нужен, личные устройства большую часть времени выключены, и две ноды без интернета полноценно синхронизируются
- потерянное устройство отзывается с другого устройства, после отзыва ключи шифрования сети меняются
- транспорт: quic, запасной — websocket поверх tls; формат сообщений — cbor; всё взаимно аутентифицировано и зашифровано на любом канале
- при взаимодействии с внешними сетями других пользователей выдаются внешние id, которые генерируются на каждого собеседника, хранятся постоянно, и их можно отозвать, чтобы разорвать связь
- обнаружение в сети не раскрывает постоянные id до аутентификации
- приоритет локальной сети: если устройства видят друг друга в локальной сети, они работают через нее
- еще можно сделать связь через bluetooth mesh
- роутинг — так, чтобы преимущественно всё происходило внутри сети пользователя, если запрос явно не внешний
  - если у устройства нет интернета, но есть связь с другой нодой сети пользователя, оно ходит в интернет ближайшим маршрутом через ноду, у которой интернет есть
  - для устройств в локальной сети выбирается автоматически или назначается пользователем шлюз в интернет для служебных запросов k-os. запросы самих приложений идут через интернет этого устройства, если пользователь явно не указал шлюз
  - можно указать выход в интернет через удаленный шлюз — получится что-то вроде vpn: запросы в интернет идут через удаленную ноду ближайшим маршрутом через ноды, которые могут находиться в разных сетях
- для взаимодействия с внешними сетями выбирается автоматически или назначается явно приоритетный шлюз, например экземпляр k-os в докер контейнере на vps, который всегда в сети
  - шлюз — это подсказка для маршрутизации, а не точка полномочий: без него всё работает, просто медленнее сходится
  - если не доверяем хостингу — нода на vps работает в роли relay без ключей данных
- мастеров для обновлений и синхронизации нет: раздает тот, у кого уже есть данные
- приложения внутри сети пользователя обращаются по id ноды, а всё остальное происходит внутри: ноды могут быть в разных сетях, через интернет или bluetooth, для приложений всё прозрачно
  - кроме недоступности: задержка, отмена и недоступность ноды доходят до приложения явно
  - можно адресовать и не конкретную ноду, а «любую ноду, где есть этот сервис»
  - обращение к ноде проверяется с двух сторон: право вызывающего и собственное правило принимающей ноды
- для общения с сетями других пользователей известны связки внешних id и ip адресов. по приоритетным делаются запросы в api сети другого пользователя, а кто там ответит — решает сеть того пользователя
- файлы, которыми поделились с другим пользователем, по возможности не копируются: ему открывается доступ в сети владельца, и владелец может его закрыть



android версия

- k-os — обычное приложение, постоянно работает как foreground service с уведомлением
- приложения ставятся из k-os как обычные apk файлы, k-os их обновляет
  - первая установка каждого apk требует подтверждения пользователя — это ограничение android
  - обновления без подтверждения возможны с android 12 для приложений, установленных самим k-os
- приложения так же используют k-os для доступа к файлам, кэшу и т.д.



свой android дистрибутив

- на базе lineageos или другой ос, которая работает на современных устройствах
- k-os — системное привилегированное приложение: устанавливает и обновляет apk без подтверждений
- изначально все лишние приложения удалены
- при первом запуске спрашивается подключение к сети k-os, после чего скачиваются и устанавливаются все приложения



серверный контейнер

- для запуска на серверах headless
- роли: обычная нода с ключами данных (своя облачная нода), или relay без ключей данных (транзит зашифрованных данных), или шлюз



свой дистрибутив на десктопе (необязательный)

- k-os ставится на любой дистрибутив, свой дистрибутив — это просто удобная готовая сборка
- база:
  - openSUSE Kalpa — хороший вариант: неизменяемая система на базе Tumbleweed с KDE Plasma, атомарные обновления через transactional-update, откат из коробки
  - либо openSUSE Tumbleweed — rolling release с откатом через snapper + btrfs, timeshift не нужен
- на базе KDE Plasma
- свой пикер файлов/папок — как бэкенд xdg-desktop-portal, тогда его получат все qt, gtk и flatpak приложения
- конфиг ос и plasma
  - сконфигурировано так, чтобы минимально конфигурировать и чтобы использовать tecloid и tyco, чтобы им ничего не мешало
- упрощенный установщик
  - спрашиваем только, на каких дисках располагать — с расширенной настройкой разделов
  - шифрование диска (luks) включено по умолчанию
  - пароль системы — обычный локальный пароль, он же для root
  - после установки запускается k-os, где предлагается подключиться к сети и настроить папки, и тогда всё скачается с других нод
- оставляем только базовые пакеты
  - терминал
  - системный менеджер пакетов
  - утилита для управления дисками
  - диспетчер задач

  - rdp/vnc viewer
  - браузер, офис и просмотрщик документов (okular) — обычные, из репозитория дистрибутива
- cli утилиты

подумать

- файлы, которых нет на этом устройстве (volume без этого устройства, выборочная синхронизация): как показывать их на хосте. есть системные механизмы заглушек — windows cloud files api, macos file provider, — а на linux стандартного нет, только fuse. пока: на хосте видны только скачанные файлы, остальные — через k-os
- android: где лежит `~/kos/`, чтобы его видели другие приложения — общее хранилище требует широких прав на файлы, которые google play ограничивает
- монтирования на уровне k-os: показывать ли их хосту (через fuse) или только через k-os
- алгоритм синхронизации пользовательских файлов: версии на файл (как в syncthing) или общий журнал операций, как для данных приложений. и ui разрешения конфликтов
- что именно делает root-помощник: tun для vpn-шлюза, хранилище приложений под root, системные пакеты в своем дистрибутиве. как ставить его отдельно и не требовать для базовой работы
- отметки в репозитории — самодекларация издателя. как их проверять: на linux можно запускать приложение без отметок в песочнице (bubblewrap/landlock, без сети) — тогда отметка проверяется сама собой. делать ли это опцией
- gui на двух стеках (slint + tauri) — оставить так или свести к одному
- ipc на macos (xpc или unix socket) и детали передачи дескрипторов на каждой платформе
- macos: gatekeeper и карантин для приложений, установленных k-os мимо app store
- фоновые внешние сервисы на android: как k-os запускает их по событию
- совместимость версий sdk и демона: сколько старых версий протокола поддерживаем
- bluetooth mesh — какой профиль и формат
- менеджер приложений V2 на майнерах — что именно это значит
