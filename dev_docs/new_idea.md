k-os внешне

- это демон/сервис где происходит вся работа
- может еще быть демон для root
- cli для управления и статуса
- GUI приложение - трей иконка со статусом и начальный экран для подключения к своей сети

k-os внутри

- в нем запущены сервисы и драйверы
- сама система тонкая, по сути выходы во вне и платформа для серсисов и драйверов
- имеет свои хранилища для программ, кэша, логов и предоставляет программам и сервисам свои папки
- управляет пользовательской домашней папкой
- файлы шифруются , включая названия папок и файлов через односмторонний хэш
- единые llm и stt модели в системе для исползвания любыми приложениями

- навеное половательскую папку не шифровать если пользватель сам не хочет, а шифровать системные файлы. если шифровать польваельскую папку то не будет доступа с хостовой системы

- можно для попрулярных приложений делать форки в которые встраивается поддержка k-os чтобы они работали с его файлами и через сеть
- приложение включает в себя все библиотеки и зависимости, включая наш sdk
- может писаться на любом языке

асинхронность

- io могут работать с несколькими источниками тогда например на каждый диск должен создаваться экземпляр io и в том же потоке драйвер основной экземпляр драйвера а инстансы которые он дает в потоках потребителя. 
- либо основной экземляр драйвера это просто фабрика , инстанс выдается потребителю и работает в его потоке, и через этот инстанс идет связь с потоком io который отдельный на каждое устройство, включая разные диски, разные сетевые карты, порты usb и тд чтобы асинхронно работать с каждым источником



внутренние сущности k-os

- io
  - это обертки над реальными io, на каждое устройство запускается отдеьный экземпляр в своем потоке, включая однотипные устрйоства например диски
  - их можно устанавливать дополнительно, например для  gpio которых обычно нет на обычных компах
  - ❓ хотя может сразу все вставлять в комплект ос, скорее всего слишком много памяти прям не отъест
- драйвера
  - все драйвера идут сразу в комплекте, даже для io которые не установлены. но можно доустанавливать драйвера
  - это прослойка между io и потребителем - сервисом или приложением
  - драйвер это фабрика которая выдает экземпляр потребителю который будет рабоать в потоке потребителя
  - драйвер это связь между потребителем и io со сбоом метрик и правами на доступ
  - получается что экземпляр драйвера выдается в skd приложения
- сервис
  - работает на базе K-OS, может быть как внешний и рабоать как приложение через sdk так и внутренний и работать в отдельно потоке K-OS
  - все системные сервисы внутренние, дополнительно устанавливаемые сервисы могут быть как внутренние так и внешние
  - сервис это практически приложение, тоолько без полноценного ui, если нужен ui то он встраивается в системный ui управления сервисами на базе html/js/css - предоставляется свой ui фреймворк но можо делать что угодно
  - сервис это воркер который реагирует на события а не работает в фоне
  - внутренний сервис можно писать толко на rust
- приложение
  - они бывают только внешние
  - приложение рабоатет с k-os чрез sdk
  - можно писать на любом языке где есть sdk - rust, tauri, electron, python, c++, c, c#, go и тд
  - приложение не должно использовать доступ к фс или сети в системе, все должно работать только через sdk. но GPU или какието специфичные устройства может использовать напрямую
  - приложение в осталном работет как обычное приложение в хостовой системе
  - установка и обнволение приложеий делается самим k-os он ставит их в свои папки. ярлыки или desktop файлы указывают на эти файлы
  - в android k-os ставит apk как обычное приложение
  - по большому счету можно ставить приложения и через системные репозитории или любым другим образом, для разработки это удобно, но для обычного опыта не удобно так как надо самому беспокоиться чтобы приложения были бы последних версий
    - смысл имеет только для приложений которые хотят быть универсальными и обычными приложениями и поддерживать k-os одновременно, тогда они могут распостранятся через системные репозитории
  - в каком потоке запускается приложение это уже на усмотрение системы
  - ‼️ если экземпеляр драйвера создается на уровне приложения и он работает напрямую с потоком io то как тогда недопустить несанкционированного доступа к io? если делать чтобы все шло через систему то потеряется асинхронность, если напрямую то придется давать доступ и sdk, если шифровать поток то это потеря производительности. либо драйверы делать отедльными сущностями со своим потоком, но драйверы это по сути тонкие обертки над io и для оберток делать отедльным поток кажется не разумным



сеть

- в пространстве k-os действует оверлейная сеть, где у каждой ноды есть свой уникалный id
- в сети пользвателя у устройств пользователя свои id
- при взаимодействии с внешними сетями других пользователей выдаются внешние id которые генерируются на каждого потребителя и хранятся постоянно и их можно отозвать чтобы разорвать связь с внешней сетью
- приоритет локальной сети, если устройства обнаруживают друг друга в локалнгой сети то работают через нее
- еще можно сделать через bluetooth mesh чтобы все работало
- роутинг - маршрутизирует так чтобы приимущественно все происходило внутри пользовательской сети, если запрос явно не внешний
  - если устройство не имеет доступа в интернет но имеет связь с другой нодой сети пользователя то оно ходит через сеть пользвоателя ближайшим маршрутом через ноду которая имеет доступ в интернет
  - для устройств в локальной сети выбирается или явно назначается ползжователем шлюз через которые идет выход в интернет или в сети ползователя для котоых нужно ходить в интернет, это для запросов обслуживания, но явные запросы пользователя например чеез браузер идут напрямую если пользователь явно не указал ходить через какойто шлюз.
  - так же можно указать выход в интернет через удаленный шлюз и получится чтото типа vpn, тогда запросы в интернет будут идти через удаленную ноду и идти к ней ближайшим маршрутом через ноды котоыре могут находитсья в разных сетях
- для взаимодействия с внешними сетями, для обмена данными с польвзжоателями с котоырми знаком юзер может выбираться автоматически или назначаться явно приоритетный шлюз, например экземпляр k-os в докер контейнере на vps хостинге котоырй всегда в сети
- для обновленя приложений и ос может выбираться или назначаться мастер который скачивает обновления и расслывает их всем нодам в сети пользжователя, с приоритетом локальных сетей
- для синхронизации файлов может выбираться или явно назначаться приоритетный мастер который владеет самыми свежими версиями файлов и у него синхронизируются остальные. (либо както это дедать полностью асинхронно)
- приложения внутри сети пользователя обращаются по id ноды а все осталное происходит внутри, ноды могут быть в разных сетях, через интернет или даже bluetooth, но для приложений все прозрачно
- так же для общения с сетями других пользователей - известны связки внешних id и ip адресов и по приоритетным делаются запросы в api сети другого польвзоателя и там все происходит внутри , а внешне как просто запрос к api, а кто там ответит это уже решает сеть того пользвателя
