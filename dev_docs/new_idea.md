Новая идея ноябрь 2026



коротко

- k-os — это надстройка над любой хостовой ос (linux, windows, macos, android), а не замена ей. хостовая система остается полнофункциональной, k-os подстраивается под нее
- по сути это демон, который создает общее пространство пользователя и синхронизирует его между всеми устройствами пользователя, объединенными в одну сеть
- пользовательские файлы — обычные файлы хоста в `~/kos/`, их можно менять и из хоста, и через k-os. поэтому синхронизация двусторонняя, по типу syncthing, с главным приоритетом — бережность к файлам
- приложения — обычные внешние программы хоста на любом языке. своей графической оболочки для приложений нет, старая идея с web ui внутри k-os отброшена
- чтобы работать с k-os, приложение использует sdk: файлы, пространство, интернет через k-os, доступ к llm/stt
- приложения не ограничиваем принудительно, иначе не получится универсальных приложений. вместо этого в репозитории приложений помечаем тех, кто ходит в хост мимо k-os, и предупреждаем при установке
- граница доверия — процесс демона. всё, что внутри процесса приложения, включая sdk, считается недоверенным
- сущности: адаптер (работа с возможностью хоста), брокер (распределяет ресурс, права, квоты), сервис (системный), воркер (сторонний, событийный)
- все адаптеры и брокеры — в общей сборке под платформу, ничего не доустанавливается
- сторонние фоновые обработчики (воркеры) — wasm в дочернем процессе k-os: одна сборка работает на всех платформах
- root для работы не нужен
- раздача обновлений и синхронизация без мастера: раздает тот, у кого уже есть данные
- свой дистрибутив необязателен, это просто удобная готовая сборка



k-os внешне

- это демон/сервис пользователя, где происходит вся работа
- ставится на любую ос как обычное приложение, без root: linux, windows, macos, android
- root-демона нет. права нужны только для отдельных необязательных функций (vpn-шлюз), они запрашиваются один раз при включении функции, см. «root и привилегии»
- cli для управления и статуса
- gui на slint: трей иконка со статусом, начальный экран для подключения к своему пространству и центр управления (настройки системы, сети, устройств, приложений и воркеров)
- написано на rust



k-os внутри

- в нем запущены системные сервисы, адаптеры и брокеры, а в дочерних процессах — воркеры
- сама система тонкая: по сути выходы вовне и платформа для сервисов и воркеров
- имеет свои хранилища для программ, кэша, логов и предоставляет программам и воркерам свои папки
- управляет папкой пользователя `~/kos/`
- доступ к llm и stt для любых приложений
  - сами модели в k-os не встраиваем, встраиваем доступ к ним
  - модели работают отдельно: локальный сервер (llama.cpp, ollama, whisper.cpp и т.п.) или внешний api
  - k-os подключается к ним (websocket / http — как требует бэкенд) и раздает доступ приложениям через sdk в соответствии с правами
  - ключи внешних api хранит k-os, приложение их не видит
  - k-os ведет очередь и лимиты по приложениям, чтобы одно приложение не заняло модель целиком
  - модель может работать на другой ноде пространства: телефон пользуется моделью на домашнем компьютере с gpu
  - в sdk — свой небольшой типизированный api (`ml.llm`, `ml.stt`), а под ним адаптеры к бэкендам: openai-совместимый api (его понимают llama.cpp, ollama, vllm), whisper и т.д.



раскладка файлов на хосте

- `~/kos/` — пользовательские папки: документы, загрузки, медиа, проекты и т.д.
  - обычные незашифрованные файлы, полностью доступны из хоста
  - синхронизируются между устройствами
- своих монтирований на уровне k-os не делаем:
  - чтобы папка внутри `~/kos/` была видна еще в одном месте — это символическая ссылка. синхронизируется как ссылка, а не как второе содержимое. на платформах, где ссылки не поддерживаются, на хосте лежит просто файл ссылки и ничего больше; в файловом менеджере k-os ссылка работает везде
  - внешние диски монтирует хост (файловый менеджер k-os предлагает смонтировать средствами хоста). если диск смонтирован внутрь `~/kos/`, k-os видит границу устройства и считает его внешним томом:
    - по умолчанию содержимое не синхронизируется; на других устройствах папка видна в той же точке дерева, а файлы читаются по сети с того устройства, к которому подключен диск (если оно в сети)
    - можно сделать внешний том volume — тогда он синхронизируется с выбранными устройствами как обычно
    - отключенный диск — это «недоступно», а не «удалено» (маркер `.kos-folder`)
  - так файловая структура одинакова на всех устройствах, и при этом нет механизма, который хост не понимает
- зашифрованные папки и папки k-os (см. «синхронизация» — режимы папок): физически хранятся в данных k-os, а в файловом менеджере k-os показываются на своем месте в дереве `~/kos/`. на хосте в этом месте ничего нет
  - если на хосте в этом месте создадут папку с тем же именем — это конфликт имен, k-os показывает обе и предлагает переименовать одну
- системные данные k-os — в стандартном для платформы месте данных приложения, не в `~/kos/`
  - linux `~/.local/share/k-os/`, windows `%LOCALAPPDATA%\k-os\`, macos `~/Library/Application Support/k-os/`, android — внутреннее хранилище приложения
  - там: приложения, данные приложений, кэш, логи, база состояния, blob store, история версий, корзина
- папки приложений (как в старой vfs): у каждого приложения свое поддерево
  - `replicated/` — синхронизируется между устройствами
  - `local/` — свое на каждом устройстве
  - `cache/` — можно удалить в любой момент
  - `tmp/` — очищается при перезапуске
  - всё, что принадлежит приложению, лежит в одном поддереве, поэтому удаление приложения убирает всё одной операцией
- куда приложению класть данные:
  - `~/kos/` — то, с чем пользователь работает как с файлами: документы, фото, экспорт. видно на хосте, открывается любой программой, не удаляется вместе с приложением
  - данные приложения — то, с чем пользователь работает только через приложение: раскладки, вложения заметок, сохранения игр, портфель. в `~/kos/` их не кладем: не захламляют папку пользователя, их нельзя случайно сломать руками, они не лежат открыто на хосте и удаляются вместе с приложением
- синхронизацией данных приложения всегда занимается k-os, а не приложение. приложение работает с ними только через sdk:
  - локальная база данных — api базы в sdk, файл базы держит k-os
  - синхронизируемая база данных — api базы в sdk, k-os синхронизирует ее журналом операций (как в старой 05-storage/02-database.md), а не файлом: файл базы, синхронизируемый побайтово, превращается в испорченную базу или постоянные конфликты. файлов синхронизируемой базы приложение не видит
  - локальные файлы (`local/`) — через sdk, для чтения и записи k-os выдает дескриптор. свою sqlite приложение может держать здесь (это удобно для портируемых приложений): локальные данные не синхронизируются, вреда нет
  - синхронизируемые файлы (`replicated/`) — только через sdk: чтение — по дескриптору, запись — во временный файл, который k-os атомарно фиксирует при закрытии. так k-os видит каждое изменение как операцию, а не следит за папкой watcher'ом, как с файлами хоста. по сути это та же «папка k-os», только принадлежит приложению
  - данные пишутся по дескриптору напрямую, без копирования через демон



синхронизация пользовательских файлов

- приоритеты, в этом порядке:
  1. ничего не затереть неожиданно для пользователя
  2. удаленное остается удаленным и не появляется снова
  3. как можно меньше конфликтов
  4. текстовые конфликты по возможности решаются автоматически

- два режима папок
  - обычная папка — файлы на хосте, их можно менять кем угодно. синхронизация снимками файлов (ниже)
  - папка k-os — живет только внутри k-os, доступ только через sdk, на хосте ее нет. k-os видит каждое изменение как операцию и ведет журнал. можно хранить зашифрованной. подходит для заметок: neptu note работает с ней через sdk
  - режим выбирается для папки пользователем, по умолчанию — обычная

- обычная папка: как обнаруживаем изменения хоста
  - watcher файловой системы (inotify / fsevents / readdirectorychangesw) плюс периодический полный скан как источник истины — watcher может пропускать события
  - файл считается измененным по mtime + размер + inode, хэш считается только у измененных
  - ждем, пока файл перестанет меняться (несколько секунд тишины), прежде чем отправлять: редакторы сохраняют в несколько шагов
  - переименование на хосте: тот же inode — это переименование; иначе удаление + создание с тем же хэшем в коротком окне тоже считаем переименованием

- обычная папка: модель версий
  - у файла стабильный id, путь — атрибут. переименование и перемещение — операции над метаданными
  - у каждого файла вектор версий (как в syncthing): у каждого устройства свой счетчик изменений этого файла
  - новая версия доминирует над старой — просто применяется. две версии, сделанные независимо, — конфликт
  - удаление — это тоже версия (tombstone), а не отсутствие записи. поэтому устройство, которое было выключено и еще держит старую версию, видит, что удаление новее, и удаляет файл у себя, а не возвращает его обратно
  - удаление против независимого изменения — побеждает изменение: файл остается, данные не теряются
  - в tombstone хранится хэш удаленного содержимого. устройство, которое вернулось после очень долгого отсутствия, когда история уже почищена, сверяет свои файлы с этими хэшами: совпадает с удаленным — удаляет, а не воскрешает
  - содержимое режется на чанки (fastcdc ~1 MiB, blake3) и хранится в blob store, одинаковые данные не передаются дважды

- обычная папка: бережная запись
  - пришедшая версия пишется во временный файл в той же папке, потом fsync
  - перед заменой k-os проверяет, что файл на диске всё еще тот, который он знает (mtime / размер / хэш). если пользователь успел его изменить — это конфликт, а не перезапись
  - замена — атомарный rename
  - прежняя версия всегда уходит в историю версий k-os на N дней, удаленные файлы — в корзину k-os на N дней. окончательно стирается только по истечении срока или вручную
  - в корне каждой синхронизируемой папки лежит маркер `.kos-folder` с id папки. если маркера нет (диск отмонтирован, папку переместили), папка считается недоступной, а не удаленной — иначе отмонтированный диск выглядит как «пользователь удалил всё»
  - защита от массового удаления: если из папки за раз пропадает больше заданной доли файлов, синхронизация удалений приостанавливается и k-os спрашивает пользователя
  - файлы, созданные на хосте с именами, недопустимыми на других платформах (`a:b`, `CON`, два имени, отличающиеся регистром), k-os не переименовывает молча: файл остается, помечается «не синхронизируется: недопустимое имя», пользователь видит это в k-os

- обычная папка: конфликты
  - для текстовых файлов (utf-8, `.md`, `.txt`, код и т.д., до разумного размера) — автоматическое трехстороннее слияние: общий предок берется из истории версий (она у нас и так есть), изменения в разных местах файла сливаются сами
  - если изменения пересеклись или файл не текстовый — сохраняются обе версии, вторая получает имя `файл (конфликт, ноутбук, 2026-11-24).ext`, k-os показывает конфликт и дает сравнить
  - маркеры конфликта внутрь файла не вписываем

- папка k-os
  - изменения приходят как операции через sdk, а не как снимки файла
  - для текстовых документов — crdt (loro / automerge / yjs — выбрать): правки с разных устройств сливаются посимвольно, конфликтов нет, есть полная история
  - бинарные файлы — та же модель версий, что и в обычной папке
  - экспорт в обычную папку / открыть копию на хосте — отдельное явное действие

- общее
  - `.kosignore` для исключений (node_modules, временные файлы и т.д.)
  - volumes (из старой спеки): большие коллекции (фото, видео) хранятся только на выбранных устройствах, а не на всех
  - без мастера: каждый узел сходится со всеми доступными
  - правила путей — пересечение ограничений всех платформ (без `\ : * ? " < > |`, без имен con/nul/..., без двух имен, отличающихся только регистром)



безопасность данных

- пользовательские файлы по умолчанию не шифруем: это обычные файлы хоста, их защищает вход в аккаунт хоста, как и все остальные файлы пользователя
- при первой настройке k-os проверяет, включено ли шифрование диска хоста (luks / bitlocker / filevault / android по умолчанию), и если нет — предлагает включить. это единственная реальная защита от кражи выключенного устройства, и она лучше любого шифрования отдельных файлов
- если пользователь хочет зашифровать папку — это папка k-os в зашифрованном виде, из хоста она недоступна
- шифруются внутренние данные k-os, куда пользователю не нужно ходить из хоста:
  - ключ ноды и секреты — в хранилище ключей платформы (secret service / kwallet, windows credential manager / dpapi, macos keychain, android keystore), ключ не покидает устройство
  - база состояния k-os — зашифрованный sqlite, ключ из хранилища ключей платформы
- всё, что уходит на чужие или не до конца доверенные ноды (облачная нода на vps, relay), шифруется на уровне чанков и записей ключами пространства. relay ключей не получает
- шифрование имен файлов через хэш не делаем



приложения

- приложения — внешние, это обычные программы хоста, пишутся на любом языке, где есть sdk: rust, tauri, electron, python, c++, c, c#, go и т.д.
- своей графической оболочки для приложений нет: окна, ярлыки и меню — хостовые
- приложение включает в себя все библиотеки и зависимости, включая sdk
- через sdk приложение получает: файлы пользователя и свои папки, пространство (обращение к нодам и их api), запросы в интернет через k-os, логи, кэш, события, уведомления, llm/stt
- gpu и специфичные устройства приложение может использовать напрямую
- принудительно приложения не ограничиваем: тогда не получится универсальное приложение, которое работает и без k-os
- в репозитории приложений ставим отметки, если приложение:
  - само ходит в хостовые папки мимо k-os — за пределами `~/kos/` и папок самого приложения. читать `~/kos/` напрямую можно, это не отметка: это разрешенное место. sdk при этом дает то, чего нет при прямом доступе: id файлов, события, конфликты, файлы с других устройств, папки k-os
  - само ходит в интернет мимо k-os
  - приложение без отметок всё делает через k-os
- как ставятся отметки:
  - издатель объявляет их сам при публикации
  - репозиторий проверяет автоматически: анализ сборки и кода (импорты сетевых и файловых функций, зависимости) и пробный запуск в песочнице без сети и без доступа к хосту на стороне репозитория
  - расхождение с объявленным — отметка ставится принудительно, издатель получает предупреждение
- отметки показываются пользователю при установке и в каталоге. если пользователь предупрежден и установил — это его выбор, дальше k-os ничего не ограничивает: доступ за пределы k-os может быть вполне нормальным для приложения
- форки популярных приложений (браузер, офис) не делаем: пользовательские файлы — обычные файлы хоста, поэтому обычный браузер и офис и так с ними работают
- установка и обновление — через k-os, он ставит приложения в свои папки. ярлыки и desktop файлы указывают на эти файлы
  - ярлыки создаются в домашней папке пользователя хоста без прав администратора, удаление приложения удаляет ярлыки
- в android k-os ставит apk как обычное приложение
- ставить приложения через системные репозитории тоже можно. это имеет смысл для приложений, которые хотят быть одновременно обычными и поддерживать k-os
- выбор ui для своих приложений: slint — где нужен быстрый запуск и не нужны текстовый редактор и медиа функции; tauri — для более сложных приложений



sdk и связь с демоном

- граница доверия — процесс демона. sdk живет в процессе приложения, поэтому считается недоверенным: приложение может его подменить. в sdk нет ни брокера, ни адаптера, ни прямого доступа к ресурсам k-os
- то, что приложение получает в sdk, — это клиентский stub брокера: асинхронный, работает в потоке приложения, а вся логика брокера (права, квоты, метрики, отзыв) — в демоне
- права проверяются один раз при открытии ресурса, а не на каждую операцию. приложение получает непрозрачный handle, дальше данные идут быстрым путем:
  - файлы и сокеты — демон открывает ресурс сам и передает приложению готовый дескриптор (unix socket + scm_rights на linux/macos, duplicatehandle на windows, binder на android). накладных расходов на данные ноль
  - потоки, которые идут через k-os (трафик пространства, папки k-os) — кольцевой буфер в разделяемой памяти на каждый handle
  - управляющие вызовы — локальный ipc (unix socket / named pipe / binder)
- как демон узнаёт, какое приложение к нему обращается
  - нативный процесс может назваться любым пакетом, поэтому его слова не являются доказательством. личность определяется по процессу на той стороне ipc
    - linux: so_peercred → pid → исполняемый файл → он лежит в хранилище приложений k-os, и его digest fs-verity совпадает с манифестом → пакет
    - windows: pid клиента named pipe → путь образа и подпись
    - macos: audit token → подпись кода
    - android: binder calling uid → имя пакета → сертификат подписи
  - приложения, поставленные мимо k-os (из системного репозитория, при разработке), — «неподтвержденные»: пользователь один раз связывает их с пакетом вручную, как при подключении устройства
  - воркеров это не касается: их запускает сам k-os и знает, кто есть кто
- права (capabilities)
  - раз приложения не ограничиваем, права защищают то, что есть только у k-os: пространство и другие ноды, папки k-os, ключи llm, устройства на других нодах, данные других приложений
  - каталог capabilities старой спеки пересматриваем: права, которые теряют смысл для внешних приложений (например, `process.exec`, внешние монтирования), убираем
- handle привязан к приложению и процессу: при завершении процесса закрывается, при отзыве права становится `revoked`
- протокол sdk ↔ демон версионированный (cbor со схемой), sdk на разных языках генерируется из одной схемы. та же схема — интерфейсы wit для wasm воркеров
- приложение обязано обрабатывать `unavailable`: устройство, сеть или нода могут отсутствовать, и это нормальное состояние, а не ошибка



асинхронность и ввод-вывод

- цель — никакого бутылочного горлышка: мощный поток (видео, копирование) не должен забивать всё остальное
- нужно и то, и другое, но сложная часть становится маленькой:
  - прямой путь (передача дескриптора) снимает основную нагрузку: локальные файлы и сокеты в интернет приложение читает и пишет само, демон в этом не участвует, а очередность между дисками и сетевыми картами обеспечивает ядро ос
  - через демон неизбежно идет только то, что k-os делает сам: трафик пространства между нодами (шифрованный, мультиплексированный), синхронизация, обновления, папки k-os. вот здесь и нужны очереди и приоритеты
- главное правило: нет одной общей очереди. очередь — на каждый ресурс: на каждый диск, на каждое соединение, на каждое устройство. ресурсы, которые в ос работают параллельно (разные диски, разные шины), у нас тоже никогда не ждут друг друга
- сколько потоков — деталь реализации: общий асинхронный runtime (tokio, io_uring на linux) + отдельный поток-владелец (actor) только для эксклюзивных устройств, где важен один владелец и порядок: serial порт, gpio чип, bluetooth адаптер
- отдельные процессы на шины не нужны: ядро ос и так параллелит устройства, процесс даст только лишний ipc
- против бутылочного горлышка:
  - очереди ограничены, при переполнении — backpressure / `quota-exceeded` с `retry-after`, а не бесконечный буфер
  - очередь, лимиты и учет — по каждому потребителю, одно приложение не исчерпает очередь другого
  - классы приоритета: служебный трафик k-os (управление сетью, ключи) > интерактивный > фоновый массовый (синхронизация, обновления). приложение не может повысить свой приоритет
  - собственная фоновая дисковая работа k-os (синхронизация, blob store) идет с пониженным приоритетом ввода-вывода (ioprio idle на linux и аналоги) и с лимитом на диск, чтобы не мешать пользователю
  - в сети между нодами каждый поток данных идет своим stream в quic, поэтому большой файл не блокирует мелкие сообщения
  - отмена запроса сразу освобождает место в очереди



внутренние сущности k-os

- адаптер (adapter)
  - умеет работать с конкретной возможностью хоста: файлы, сеть, bluetooth, wi-fi direct, serial, gpio, usb, камера и т.д. — «как выполнить операцию на этой платформе»
  - все адаптеры входят в общую сборку под платформу, ничего не доустанавливается
    - это небольшой код на rust (сотни килобайт на адаптер), а не модели или библиотеки вендоров
    - сборка и так своя под каждую платформу: адаптеры, которых на платформе быть не может (gpio на windows), просто не компилируются в нее
    - пока устройства нет, адаптер не инициализируется и не занимает память
    - одна сборка на все устройства платформы проще поддерживать и тестировать, и она переносима: тот же бинарник работает и на ноутбуке, и на raspberry pi
  - если когда-то понадобится редкое оборудование с закрытыми библиотеками вендора — это внешний процесс-поставщик устройства через тот же протокол sdk, а не загружаемый в демон код. в v1 не делаем
- брокер (broker)
  - распределитель между адаптером и потребителями — сервисом, воркером или приложением: «как безопасно владеть ресурсом и делить его»
  - все брокеры — часть системы: от них зависят права, квоты и отзыв доступа для всех приложений
  - брокеры обобщены по классам ресурса:
    - разделяемый (сокеты, файлы) — одновременный доступ, изоляция по потребителю
    - эксклюзивный (serial, камера, линия gpio) — один владелец, остальным `unavailable` с указанием владельца
    - арендуемый (gpio под фоновой задачей) — владение через lease
  - брокер выдает handle и проверяет его при каждой операции (владелец, scope, отзыв), собирает метрики по каждому приложению
  - брокер не читает манифест и не решает, выдавать ли право — это делает capability service
  - брокер работает в потоке своего адаптера, отдельного потока у брокера нет
- сервис
  - только системный: на rust, внутри демона, поставляется вместе с k-os (синхронизация, сеть, установщик, llm-доступ и т.д.)
  - пользователь сервисы не устанавливает
- воркер
  - сторонний фоновый обработчик, который ставится как часть пакета приложения или отдельным пакетом
  - формат — wasm component, исполняется в wasmtime, в песочнице: получает только то, что разрешено через права, без прямого доступа к файлам и сети
  - переносимость дает формат wasm, а не процесс: одна сборка `.wasm` работает на всех платформах (linux, windows, macos, android), ставится через k-os и не требует установки в систему. нативный код в дочернем процессе всё равно пришлось бы собирать под каждую платформу
  - исполняется не в процессе демона, а в дочернем процессе k-os (хост воркеров):
    - падение или зависание воркера не роняет демон
    - поверх песочницы wasm — ограничения ос на процесс (память, cpu; cgroups на linux, job objects на windows, отдельный процесс-сервис на android)
    - каждый воркер — в своем отдельном процессе, воркеры не объединяются даже внутри одного пакета. простаивающий процесс k-os останавливает
    - связь с демоном — тот же ipc, что и у sdk
  - пишется на любом языке, который собирается в wasm component: rust, go, c/c++, python, js / typescript
  - js / typescript поддерживаем через сборку в wasm component (движок js упаковывается внутрь компонента), а не отдельным встроенным js-движком: одна песочница и один формат вместо двух. lua отдельно не поддерживаем — нет выигрыша перед js, а экосистема меньше
  - реагирует на события (таймер, изменение файла, входящий запрос из сети, сообщение), а не работает постоянно в фоне. k-os запускает его по событию и останавливает, когда он не нужен
  - ограничены память, время работы, частота запуска
  - api воркера — те же интерфейсы, что и в sdk
  - api, экспортированные в пространство, и входящие сообщения обслуживают воркеры: k-os запускает их по событию, даже когда приложение закрыто. нативное приложение обслуживает запросы, только пока запущено, — по событию k-os его сам не запускает
  - не выглядит как приложение: виден и настраивается в центре управления
- приложение
  - только внешнее, работает с k-os через sdk, см. выше
  - если нужен тяжелый фоновый нативный процесс (свои нативные библиотеки, gpu) — это приложение без окна, со сборкой под каждую платформу, а не воркер



настройки в центре управления

- центр управления — одно приложение на slint: системные настройки, сеть, устройства, приложения, воркеры
- чтобы не писать целый фреймворк форм, логика настроек остается у самого воркера / приложения, а k-os дает только простое описание и проверку
- два уровня, разработчик выбирает сам:
  1. схема настроек — по ней центр управления сам рисует форму (по умолчанию, правило хорошего тона)
  2. свой интерфейс — свое окно / свое приложение / свой формат конфигов. в центре управления тогда кнопка «открыть настройки», и всё
- схема намеренно простая:
  - поля: тип (строка, число, флаг, выбор из списка, путь, секрет, список значений), значение по умолчанию, описание, группа
  - проверки: min / max, шаблон, обязательность
  - связи между полями — только одна: показать / разрешить поле, если другое поле имеет определенное значение
  - списки выбора могут браться из системы: ноды пространства, устройства нужного класса, папки, модели llm
  - всё сложнее (проверка связки полей, проверка подключения к серверу) — центр управления отправляет черновик настроек воркеру / приложению, а тот возвращает ошибки по полям. логика проверки живет в коде разработчика, а не в нашем формате
- значения хранятся в k-os в toml, их можно править и руками. воркер / приложение читает их через sdk и получает событие при изменении
- у каждой настройки область: на всё пространство (синхронизируется между устройствами) или на конкретное устройство
- встроенные html-панели в центре управления не делаем: это снова webview и свой ui-фреймворк, а кому нужен сложный ui — делает свое окно
- диалоги выдачи прав, подтверждение подключения устройства и подобное рисует только k-os, приложение не может нарисовать неотличимый системный запрос



root и привилегии

- для базовой работы k-os root не нужен: файлы пользователя, пространство, bluetooth (через bluez / системные api), установка приложений в папки пользователя, ярлыки — всё работает без прав
- что требует прав и как решается:
  - выход в интернет через удаленный шлюз (vpn-режим): на linux нужен tun — права один раз при включении функции (setcap на отдельный маленький бинарник помощника), на windows — установка драйвера wintun с правами администратора, на android — vpnservice без root, на macos — network extension
  - установка системных пакетов — не задача k-os на чужой ос, только в своем дистрибутиве
- в своем дистрибутиве всё, что требует прав, настраивается заранее (помощник с нужными capability, правила polkit), пользователю ничего подтверждать не нужно



менеджер приложений V1

- доверие — от ключа издателя, а не от места хранения:
  - разработчик заводит аккаунт и ключ издателя, публикует подписанный манифест версии с хэшами всех файлов
  - новая версия принимается только от издателя, зафиксированного при установке
  - сервис регистрации — это каталог и индекс подписанных манифестов, а не источник доверия. поэтому в v2 его можно заменить распределенной сетью без изменения модели доверия
- сами файлы хранятся в релизах github, gitlab и т.д., это просто недоверенное хранилище байт: либо подпись и хэши сходятся, либо файл отбрасывается
- набор установленных приложений и их версии — общие для всего пространства. артефакты — свои под каждую платформу (wasm воркеры — одни на все), приложение без сборки под платформу на этом устройстве просто недоступно
- раздача без мастера:
  - любое устройство, у которого есть сеть, проверяет обновления и публикует найденную версию в пространстве
  - каждое устройство скачивает нужное ему, предпочитая локальную сеть интернету; первое скачавшее сразу становится источником для остальных
  - чтобы несколько устройств в одной квартире не качали одно и то же из интернета, устройство берет короткий lease на загрузку. потеря lease ничего не ломает, только лишний трафик
- пользователи могут включать ноды для ретрансляции приложений и раздавать их своим контактам — только публичное содержимое
- обновление, которое расширяет права или меняет отметки (хост-файлы / интернет мимо k-os), не применяется без подтверждения пользователя
- откат и удержание версии — на уровне всего пространства
- защита от подмены установленных файлов:
  - при установке проверяются подпись издателя и хэши всех файлов
  - linux: на файлы включается fs-verity (ext4, btrfs, f2fs, root не нужен) — ядро проверяет содержимое при чтении, файл становится неизменяемым, а проверка при запуске — сравнение одного digest
  - windows / macos: проверка хэшей при запуске для основного исполняемого файла, подпись кода платформы, если издатель ее сделал
  - android — подпись apk проверяет система и не дает поставить обновление с другой подписью; k-os сверяет сертификат с ключом издателя
  - честно признаем: если вредонос уже работает от имени пользователя, он может многое и без подмены файлов (например, подменить ярлык). поэтому это защита от случайной порчи и подмены при доставке, а не от вредоноса в сессии пользователя



распределенная сеть (V2, пока только идея, в v1 делаем централизованный сервис)

- пользователи запускают майнеры и предоставляют ресурсы: процессор, gpu, дисковое хранилище — за это получают криптовалюту
- свой токен: одним токеном оплачивается всё — хранение файлов, cpu общего назначения, gpu (например, для запуска моделей)
- часть дискового хранилища майнеров используется для нужд k-os: хранение и раздача приложений
- пользователи могут создавать свои хранилища в этой сети за плату, которая уходит майнерам
  - данные в таком хранилище не анонимные (привязаны к аккаунту плательщика), но зашифрованы: прочитать их может только сам пользователь
- майнер — провайдер хранения и вычислений, а не владелец данных
  - как у любого провайдера, нужна процедура по жалобам: список хэшей, которые сеть перестает раздавать
- публичные данные:
  - всё публичное привязано к аккаунту, который его опубликовал. анонимной публикации нет
  - удаление обещаем настолько, насколько это возможно: сеть перестает раздавать данные (удаление владельцем или истечение срока кэша). если кто-то уже скопировал — это за пределами нашего контроля, и пользователь видит это честно при публикации
- анонимность — только для своего: личные данные защищены, общение со знакомыми — через подключение к их пространствам, а не через публичные сервисы
- k-os работает без токена: всё, что в v1, не зависит от v2, токен нужен только для оплаты ресурсов чужих майнеров
- менеджер приложений становится распределенным: вместо центрального сервиса регистрации — распределенная база метаданных приложений
- распределенная сеть также служит для:
  - обнаружения устройств (вместо / в дополнение к bootstrap-узлам)
  - публичных данных: например, приложение-соцсеть, где пользователь публикует свои фото. данные попадают в распределенный кэш на какое-то время. если пользователь больше не хочет их раздавать, он удаляет их, либо кэш протухает и данные больше неоткуда взять
  - запуска моделей на чужих gpu и вычислений на чужих cpu за токен
- что заложить уже в v1, чтобы v2 встал без переделки:
  - адресация содержимого по хэшу (blake3 чанки) — v2 становится просто еще одним источником байт
  - доверие от подписи издателя, а не от места хранения — распределенной базе метаданных не нужен консенсус о достоверности, подписанные манифесты проверяются сами. блокчейн нужен только для оплаты, а не для метаданных
  - внешние id на каждого собеседника — обнаружение через общую сеть не должно раскрывать постоянные id
- см. также старую спеку: 12-future/01-bootstrap-discovery.md, 02-compute-market.md, 03-web3-and-social.md



сеть

- в пространстве k-os действует оверлейная сеть, где у каждой ноды свой уникальный id (ключ ed25519)
- в пространстве у каждого устройства пользователя свой id
- добавление устройства в пространство требует подтверждения человеком на уже доверенном устройстве
- состав пространства и права хранятся в журнале подписанных записей (control log): кворум не нужен, личные устройства большую часть времени выключены, и две ноды без интернета полноценно синхронизируются
- потерянное устройство отзывается с другого устройства, после отзыва ключи шифрования пространства меняются
- транспорт: quic; формат сообщений — cbor; всё взаимно аутентифицировано и зашифровано на любом канале
  - запасной транспорт — websocket поверх tls на 443 порту. зачем: quic работает поверх udp, а udp режут или замедляют во многих сетях — корпоративные, гостиничные, некоторые мобильные операторы, сети с dpi. websocket поверх tls выглядит как обычный https, проходит через http-прокси и cdn. без него нода в такой сети просто не подключится
- при взаимодействии с пространствами других пользователей выдаются внешние id, которые генерируются на каждого собеседника, хранятся постоянно, и их можно отозвать, чтобы разорвать связь
- обнаружение в сети не раскрывает постоянные id до аутентификации
- приоритет локальной сети: если устройства видят друг друга в локальной сети, они работают через нее
- роутинг — так, чтобы преимущественно всё происходило внутри пространства, если запрос явно не внешний
  - если у устройства нет интернета, но есть связь с другой нодой пространства, оно ходит в интернет ближайшим маршрутом через ноду, у которой интернет есть
  - для устройств в локальной сети выбирается автоматически или назначается пользователем шлюз в интернет для служебных запросов k-os. запросы самих приложений идут через интернет этого устройства, если пользователь явно не указал шлюз
  - можно указать выход в интернет через удаленный шлюз — получится что-то вроде vpn: запросы в интернет идут через удаленную ноду ближайшим маршрутом через ноды, которые могут находиться в разных сетях
- для взаимодействия с пространствами других пользователей выбирается автоматически или назначается явно приоритетный шлюз, например экземпляр k-os в докер контейнере на vps, который всегда в сети
  - шлюз — это подсказка для маршрутизации, а не точка полномочий: без него всё работает, просто медленнее сходится
  - если не доверяем хостингу — нода на vps работает в роли relay без ключей данных
- мастеров для обновлений и синхронизации нет: раздает тот, у кого уже есть данные
- приложения внутри пространства обращаются по id ноды, а всё остальное происходит внутри: ноды могут быть в разных сетях, через интернет или bluetooth, для приложений всё прозрачно
  - кроме недоступности: задержка, отмена и недоступность ноды доходят до приложения явно
  - можно адресовать и не конкретную ноду, а «любую ноду, где есть этот сервис»
  - обращение к ноде проверяется с двух сторон: право вызывающего и собственное правило принимающей ноды
- для общения с пространствами других пользователей известны связки внешних id и ip адресов. по приоритетным делаются запросы в api пространства другого пользователя, а кто там ответит — решает пространство того пользователя
- файлы, которыми поделились с другим пользователем, по возможности не копируются: ему открывается доступ в пространстве владельца, и владелец может его закрыть



сеть без интернета (bluetooth / wi-fi напрямую)

- это дополнительное использование k-os, а не основная функция: делаем, если получится реализовать. ценность в том, что ничего не нужно ставить и брать заранее — есть телефон и k-os, и связь на небольшом расстоянии уже есть

- цель: где-то в отдалении (поход, лес), где нет интернета, пользоваться общей сетью только телефонами, без дополнительных устройств, которые можно забыть, и без установки дополнительных приложений:
  - переписка и обмен фото внутри группы
  - голос по типу рации (push-to-talk) на небольшом расстоянии
  - поиск потерявшегося человека
  - пространства разных пользователей взаимодействуют друг с другом без розданного wi-fi
- от bluetooth не отказываемся, отказываемся только от стандарта bluetooth mesh (sig): он сделан для iot и передает сообщения в десятки байт. каналы:
  - bluetooth le — обнаружение соседей, короткие сообщения, маяк для поиска. мало расходует батарею
  - wi-fi direct / wi-fi aware (android) или точка доступа на одном из устройств — объемные данные: фото, голос, синхронизация
- реалистичные ожидания (ориентировочно, проверить на реальных телефонах):
  - на открытой местности прямая связь телефон-телефон — десятки, до пары сотен метров; в лесу заметно меньше — листва и стволы сильно глушат сигнал
  - bluetooth le long range (coded phy) на поддерживающих телефонах дает больше, но не везде есть
  - это не замена рации на километры. дальность группы растет за счет ретрансляции: каждый телефон в цепочке передает дальше
  - голос — только в пределах прямой связи или короткой цепочки: с каждым шагом ретрансляции растет задержка
- поиск человека — самая реалистичная и ценная часть:
  - телефон в режиме маяка периодически вещает по bluetooth le свой id (для своих) и последние координаты gps; это экономно, телефон может так работать долго
  - телефоны поисковиков показывают «ближе / дальше» по силе сигнала и последние известные координаты
  - координаты и сообщения потерявшегося передаются через любые встреченные телефоны с k-os (store-and-forward) и доходят до своих, как только кто-то из цепочки окажется в зоне связи
- ограничения, которые надо принять:
  - iphone не поддерживаем, значит люди с iphone в группе не участвуют
  - android ограничивает фоновое сканирование ble и wi-fi, а wi-fi aware есть не на всех телефонах — нужен явный «походный режим», который пользователь включает
  - если нужна дальность в километры — это уже отдельное радио (lora): можно поддержать как необязательный адаптер, но не основной путь
- в v1 не входит, но адаптеры ble и wi-fi direct и store-and-forward проектируем сразу с прицелом на этот режим
- модель — store-and-forward (delay-tolerant): сообщение передается от устройства к устройству по мере того, как они встречаются, и доходит до получателя через промежуточные устройства, даже если прямого пути никогда не было
  - это естественно ложится на k-os: синхронизация и так построена на «сойтись, когда узлы встретились»
  - промежуточные устройства (в том числе чужих пользователей) переносят только зашифрованные сообщения, которые не могут прочитать
  - перенос чужих сообщений — по согласию пользователя, с лимитами по месту, трафику и батарее, со сроком жизни сообщения
  - защита от спама: лимиты на отправителя, приоритет сообщениям от своих контактов



android версия

- k-os — обычное приложение, постоянно работает как foreground service с уведомлением
- распространяется вне google play (свой сайт, f-droid): k-os сам устанавливает apk и использует полный доступ к файлам, а play ограничивает и то, и другое
- `~/kos/` на android — папка `KOS/` в общем хранилище (рядом с Download, DCIM и т.д.)
  - k-os всегда запрашивает полный доступ к файлам (all files access) именно для себя
  - файлы видны другим приложениям (галерея, плеер, офис) и не удаляются при удалении k-os
  - стандартные папки android можно привязать к папкам k-os: например, DCIM/Camera синхронизируется в `~/kos/Фото/Телефон`, Download — в `~/kos/Загрузки`. тогда то, что пишет камера и браузер, само попадает в синхронизацию
  - если пользователь отказал в доступе — файлы во внутренней папке k-os, с явным предупреждением: другие приложения их не видят, и при удалении k-os копия на этом телефоне пропадет (на других устройствах пространства она останется)
  - saf (выбор папки через системный диалог) не используем как основной путь: он медленный и не дает нормально отслеживать изменения
- приложения ставятся из k-os как обычные apk файлы, k-os их обновляет
  - первая установка каждого apk требует подтверждения пользователя — это ограничение android
  - обновления без подтверждения возможны с android 12 для приложений, установленных самим k-os
- приложения так же используют k-os для доступа к файлам, кэшу и т.д.



свой android дистрибутив

- на базе lineageos или другой ос, которая работает на современных устройствах
- k-os — системное привилегированное приложение: устанавливает и обновляет apk без подтверждений, доступ к файлам выдан заранее

- при первом запуске спрашивается подключение к своему пространству, после чего скачиваются и устанавливаются все приложения

термины

- пространство (space) — все устройства (ноды) одного пользователя, объединенные в одну сеть, и общее состояние на них. в старой спеке это называлось «профиль», при переписывании заменяем везде
  - не «кластер»: это слово означает постоянно включенные серверы, кворум и лидера, а у нас устройства большую часть времени выключены и мастера нет
- профиль — профиль публичных данных пользователя (то, что он публикует от своего аккаунта, например в соцсети)
- нода — одно устройство в пространстве
- адаптер, брокер, сервис, воркер, приложение — см. «внутренние сущности k-os»
- обычная папка / папка k-os — режимы синхронизируемых папок



порядок переписывания старой спеки

1. видение, принципы, словарь — от них зависит всё остальное
2. слои и сущности: адаптер, брокер, сервис, воркер, приложение; модель процессов (демон, хосты воркеров, внешние приложения)
3. модель приложения, sdk и идентификация вызывающего, каталог capabilities
4. хранилище: раскладка на хосте, синхронизация пользовательских файлов, реплицируемые данные приложений
5. клиенты по платформам, распространение приложений, безопасность
6. сеть и федерация — там меньше всего изменений: термины и шлюзы
7. направления развития: v2, сеть без интернета
