# Воркеры: backend приложения в WebAssembly

## Место воркера в приложении

Приложение — это в первую очередь frontend, работающий с предоставленным API. Backend
**необязателен**: приложение без собственного воркера обязано быть полноценным, работая
через стандартные capabilities. Воркер добавляется, когда нужно то, чего frontend дать не
может:

- работа без открытого UI: реакция на события, расписания, фоновая обработка;
- обработка входящих вызовов экспортированного API приложения;
- длительные и тяжёлые вычисления, которые нельзя держать в UI-потоке;
- операции, продолжающиеся после закрытия окна;
- логика, которая должна выполняться одинаково на всех устройствах профиля;
- код, который должен исполниться на другой ноде — там, где есть оборудование или данные.

Воркер не является способом получить больше прав. Набор capabilities объявляется в
манифесте на уровне компонента, и воркер получает ровно то, что ему выдано; фоновый режим
работы сам по себе никаких прав не добавляет.

## Формат и язык

Рекомендуемый формат — **WebAssembly Component** с явно импортированными capability
interfaces, описанными в каталоге. Rust является основным рекомендуемым языком, но контракт
не зависит от Rust ABI: подойдёт любой язык, компилируемый в совместимый компонент.

```wit
world app-worker {
  import kos:core/context@1.0;
  import kos:core/events@1.0;
  import kos:storage/store@1.0;
  import kos:fs/files@1.0;

  export handle-event: func(ev: event) -> result<_, error>;
  export handle-call:  func(ctx: call-context, payload: list<u8>) -> result<list<u8>, error>;
  export run-command:  func(name: string, args: list<u8>) -> result<list<u8>, error>;
}
```

Язык реализации не является частью модели безопасности: изоляцию обеспечивает песочница и
набор импортов, а не свойства языка.

## Виды воркеров

| Вид | Что запускает | Время жизни | Типичное применение |
|---|---|---|---|
| event worker | системное или прикладное событие | до завершения обработчика | реакция на изменение данных, входящее сообщение |
| command handler | явный вызов из UI или другого компонента | одно ограниченное выполнение | «пересканировать библиотеку» |
| api handler | входящий вызов экспортированного API | до ответа | обслуживание запроса с другой ноды или от связанного пользователя |
| scheduled worker | расписание планировщика | до завершения задания | ночная переиндексация, выгрузка |
| background worker | задача с выданным lease | пока действует lease | длительная обработка, продолжающаяся после закрытия UI |
| compute worker | явный запрос на тяжёлое вычисление | до завершения или отмены | преобразование данных, анализ, подготовка производных данных |

Все виды — один и тот же исполняемый компонент с разными точками входа и разными условиями
активации. Отдельного типа «демон» не существует: см. [отказ от пользовательских
daemons](./01-app-model.md).

## Активация

```text
Событие / вызов / расписание / lease
        ↓
scheduler-service: выбор ноды по placement
        ↓
проверка манифеста и выданных прав
        ↓
создание экземпляра воркера с deadline и токеном отмены
        ↓
исполнение обработчика
        ↓
сохранение checkpoint (при необходимости) и завершение
```

Существенные свойства:

- **экземпляр не переиспользуется молча.** Runtime вправе создать новый экземпляр на каждую
  активацию; глобальные переменные модуля не являются местом хранения состояния между
  активациями;
- **события доставляются не менее одного раза.** Обработчик обязан быть идемпотентным либо
  использовать ключ дедупликации; система не обещает exactly-once;
- **порядок событий не гарантирован глобально.** Гарантируется причинный порядок в пределах
  одного объекта, а не единый порядок между объектами;
- **активация квотируется.** Частота пробуждений ограничена политикой ноды и режимом
  питания; превышение возвращает `quota-exceeded` при постановке задачи, а не приводит к
  бесконечной очереди.

## Модель исполнения

| Ограничение | Кто задаёт | Поведение при превышении |
|---|---|---|
| deadline выполнения | runtime, с учётом вида активации | отмена, затем принудительная остановка |
| память экземпляра | политика ноды и манифест | остановка с `quota-exceeded` |
| время CPU за окно | политика ноды | снижение приоритета, затем отмена |
| число одновременных экземпляров пакета | политика ноды | постановка в очередь либо отказ |
| объём хранилища и трафика | квоты драйверов | `quota-exceeded` на конкретной операции |

Воркер обязан периодически проверять отмену или использовать операции, прерываемые по
deadline:

```wit
interface execution {
  deadline: func() -> option<instant>;
  cancelled: func() -> bool;
  on-cancel-checkpoint: func(state: list<u8>) -> result<_, error>;
}
```

Runtime вправе прервать исполнение принудительно. **Подтверждённое состояние при этом не
должно повреждаться** — это требование к системе, а не к приложению: запись подтверждается
атомарно вместе с записью для будущей репликации, поэтому прерывание не оставляет
полузаписанных данных. Что приложение обязано обеспечить со своей стороны — возможность
возобновления с последнего checkpoint.

### Checkpoints

Длительная работа разбивается на шаги, между которыми сохраняется checkpoint. При следующей
активации воркер получает сохранённое состояние и продолжает с него. Это заменяет
предположение «процесс будет жить, пока я не закончу», которое неверно на мобильных
платформах и неверно на десктопе при закрытии крышки.

Checkpoint принадлежит классу `device-local`, если работа привязана к этой ноде, и
`replicated`, если задача может быть продолжена другой нодой. Выбор объявляется в манифесте
компонента, потому что от него зависит, можно ли перенести задачу.

## Работа с состоянием

Воркер не имеет файловой системы хоста, окружения и сети сверх выданных capabilities.
Всё состояние — через API:

- база данных приложения и namespaces — `storage.*`;
- файлы приложения и пользователя — `files.*`;
- секреты — `secrets.read-write`;
- события — `events.*`;
- сеть — `net.http`, `net.ws`, экспорт и вызов API.

Прикладная картина работы с данными — в [данных приложения](./06-app-data-api.md).

Отдельное правило: воркер и Web UI одного пакета работают с **одними и теми же** данными и
видят изменения друг друга через подписки. Они не обмениваются состоянием через общую
память и не считают себя частями одного процесса — на разных нодах они и не будут ими.

## Тяжёлые вычисления и GPU

Сложные расчёты — одна из основных причин заводить воркер: WebAssembly даёт предсказуемую
производительность и не блокирует интерфейс.

Правила:

1. **Расчёт должен переживать прерывание.** Долгая задача разбивается на шаги с
   checkpoints, иначе она не завершится на мобильном устройстве никогда.
2. **Расчёт может быть перенесён на другую ноду.** Если в манифесте объявлено
   `remote = "allowed"`, планировщик вправе выбрать ноду с питанием от сети и свободным
   процессором. Для этого входные данные должны быть доступны выбранной ноде — то есть
   лежать в реплицируемом состоянии или в VFS, а не в локальном кэше.
3. **Параллелизм ограничен политикой ноды**, а не решением приложения.

**Доступ к GPU.** На сегодня он разделён по средам:

| Среда | Доступ к ускорителю | Статус |
|---|---|---|
| Web UI | WebGPU внутри контейнера приложения | доступен там, где его даёт движок платформы |
| Воркер | `compute.gpu` — отдельная capability | зарезервирована, в v0 не входит |

Причина разделения: WebGPU — возможность web-среды, и воркер, исполняемый headless вне
WebView, её не наследует. Пока `compute.gpu` не введена, вычисления на ускорителе доступны
приложению только при открытом UI, и приложение обязано обрабатывать её отсутствие как
`unavailable`, а не считать наличие GPU данностью. Введение `compute.gpu` потребует решить
вопрос изоляции и квотирования ускорителя между приложениями и является отдельной работой.

## Размещение

Воркер исполняется на ноде, выбранной планировщиком в соответствии с
[размещением](./08-placement-and-execution.md): scope задаёт требуемую кардинальность
(`per-node`, `per-user`, `cluster-singleton`, …), placement выбирает конкретную ноду по
требованиям, предпочтениям и доступности.

Следствия для кода воркера:

- нельзя предполагать, что воркер запустится на том же устройстве, где открыт UI;
- нельзя предполагать, что предыдущая активация была на этой же ноде;
- локальные пути, локальные порты и локальное оборудование доступны только если они
  объявлены в `requires` и потому учтены при выборе ноды;
- задача `cluster-singleton` защищается lease с fencing token; потеря lease означает, что
  работу продолжает другая нода, и внешние эффекты старого владельца обязаны быть
  отклонены владельцем ресурса.

## Сбои

| Ситуация | Поведение системы |
|---|---|
| воркер завершился с ошибкой | событие помечается как неуспешное, применяется ограниченный повтор с задержкой |
| воркер стабильно падает на одном событии | событие отправляется в «карантин» и перестаёт вызывать активацию, пользователю показывается диагностика |
| превышен deadline | отмена, затем принудительная остановка; подтверждённое состояние сохраняется |
| нода стала недоступна во время выполнения | задача переразмещается, если она идемпотентна или защищена lease |
| воркер исчерпал квоту | операция возвращает `quota-exceeded`, активация не повторяется немедленно |

Бесконечный повтор запрещён: он превращает дефект приложения в разряд батареи. Бюджет
повторов и правило карантина принадлежат планировщику, а не приложению.

## Версии и обновление

- новая версия пакета приносит новый артефакт воркера; артефакты неизменяемы, поэтому
  версии сосуществуют и откат является переключением активной версии;
- расширение прав при обновлении не активируется автоматически: пакет переходит в
  `pending-grant` и его воркеры не запускаются ни на одной ноде до подтверждения;
- checkpoints и данные, сохранённые предыдущей версией, обрабатываются миграциями,
  объявленными в манифесте. Ноды профиля обновляются не одновременно, поэтому воркер обязан
  корректно вести себя при чтении данных, записанных другой версией — правила в
  [базе данных приложения](../05-storage/02-database.md);
- воркер, чьи обязательные права отозваны, не запускается: компонент переходит в состояние
  `not-permitted`, а не работает с урезанной функциональностью.

## Тестируемость

Воркер — обычный WebAssembly-компонент с явными импортами, поэтому он проверяется без
запуска всей системы: импорты заменяются mock-реализациями capability-интерфейсов, время и
случайность контролируются, события подаются сценарием.

Требование к разработчику приложения формулируется как проверяемое: обработчик, вызванный
дважды с одним и тем же событием, обязан дать тот же результат, что и вызванный один раз.
Без этого приложение будет ломаться на повторной доставке, которая является штатным
поведением системы.

## Проверяемые критерии

- приложение без воркера полноценно работает через стандартное API;
- добавление воркера не требует от пользователя устанавливать отдельный сервис;
- воркер можно остановить и позже возобновить из checkpoint;
- воркер не имеет доступа к ОС и сети сверх объявленных capabilities;
- повторная активация тем же событием не приводит к повреждению данных;
- отсутствие ускорителя, оборудования или сети выражается `unavailable` и обрабатывается;
- воркер исполняется на выбранной планировщиком ноде и не предполагает конкретное устройство.
