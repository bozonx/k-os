# Данные приложения глазами разработчика

Статус: готов  
Назначение: дать связный прикладной ответ на вопрос «где хранить данные и что при этом
произойдёт». Документ не вводит новых механизмов, а собирает их в порядке принятия решений
разработчиком.

Связанные документы: [модель состояния](../05-storage/01-state-model.md),
[база данных приложения](../05-storage/02-database.md), [VFS](../05-storage/03-vfs.md),
[мусор и квоты](../05-storage/05-garbage-and-quotas.md),
[воркеры](./05-backend-wasm.md), [каталог capabilities](../04-capabilities/02-catalog/00-index.md).

## Карта решений

```text
Это настройка приложения?
├── да  → kos.config            (объявляется в манифесте, слои профиль/нода)
└── нет → нужна на всех устройствах пользователя?
          ├── да  → большая и является содержимым файла?
          │         ├── да  → /app/<pkg>/files/  (files.app.*)  ссылка в базе как blob-ref
          │         └── нет → app.data.replicated (storage.replicated.read-write)
          └── нет → переживёт перезапуск ноды?
                    ├── нет → app.tmp            (storage.tmp.read-write)
                    └── да  → можно потерять в любой момент?
                              ├── да  → app.cache      (storage.cache.read-write)
                              └── нет → это секрет?
                                        ├── да  → app.secrets    (secrets.read-write)
                                        └── нет → app.data.local (storage.local.read-write)
```

Пользовательские файлы (`/user/`) и внешние каталоги (`/mnt/<mount-id>/`) не принадлежат
приложению: доступ к ним выдаётся отдельно и может быть отозван.

| Задача | Место | Право |
|---|---|---|
| настройки приложения | `kos.config` | `storage.replicated.*`, `storage.local.*` |
| записи и состояние приложения | `app.data.replicated` | `storage.replicated.read-write` |
| выбранное аудиоустройство, раскладка окна | `app.data.local` | `storage.local.read-write` |
| миниатюры, распакованные данные, индекс | `app.cache` или `derived` | `storage.cache.read-write` |
| промежуточный файл на время операции | `app.tmp` | `storage.tmp.read-write` |
| токен внешнего сервиса | `app.secrets` | `secrets.read-write` |
| файлы, созданные приложением | `/app/<pkg>/files/` | `files.app.read-write` |
| документы и медиа пользователя | `/user/` | `files.user.read`, `files.user.write` |
| папка вне среды, выбранная пользователем | `/mnt/<mount-id>/` | `files.external.<mount-id>.*` |

## Изолированная база данных

Приложение получает собственную базу: другие пакеты её не видят, а система обеспечивает
синхронизацию между устройствами. Приложение объявляет коллекции и их типы в манифесте,
затем работает с объектами:

```ts
const db = kos.storage.replicated;

await db.put("tracks", track.id, { title, artist, durationMs });
const page = await db.query({
  collection: "tracks",
  filters: [{ field: "artist", op: "eq", value: "Autechre" }],
  orderBy: [{ field: "title" }],
  limit: 50,
});
```

Что делает система и о чём не нужно думать: транзакция, журнал операций для репликации,
передача изменений на другие ноды, слияние параллельных правок, шифрование, эпохи ключей,
сборка мусора.

О чём думать нужно:

- **тип данных выбирается осознанно.** `document`, `set`, `counter`, `log`, `coordinated`
  сливаются по-разному, и от выбора зависит поведение при параллельной правке;
- **уникальность значения не гарантируется** без `coordinated` и lease;
- **запрос обязан опираться на объявленный индекс**, иначе пакет не установится;
- **порядок между объектами не определён**: причинность есть, глобального порядка нет.

Механизмы — в [базе данных приложения](../05-storage/02-database.md).

## Настройки

Настройки — это не отдельное хранилище, а типизированный слоистый вид на уже существующие
namespaces. Отдельного хранилища для них нет намеренно: оно продублировало бы репликацию,
слияние и миграции ради данных, ничем от прочих не отличающихся.

Схема настроек и значения по умолчанию объявляются в манифесте, а чтение разрешает слои:

```text
config.get(key)  →  переопределение на этой ноде (local)
                 →  значение профиля            (replicated)
                 →  значение по умолчанию       (манифест)
```

```ts
const cfg = kos.config;

await cfg.get("syncIntervalMs");           // разрешённое значение с учётом слоёв
await cfg.set("theme", "dark");            // в слой профиля: подействует везде
await cfg.setLocal("audioDevice", "hdmi"); // только на этой ноде
await cfg.origin("syncIntervalMs");        // откуда взято: default | profile | node
```

Что это даёт помимо экономии кода:

- **сценарий «здесь работать иначе»** решается штатно: приложение читает одно значение и
  ничего не знает о слоях, а нода получает переопределение, которое не уезжает на другие
  устройства;
- **системная оболочка рисует экран настроек приложения, не запуская его** — схемы из
  манифеста достаточно, и пользователь видит, какие значения переопределены на этом
  устройстве;
- значения валидируются по объявленной схеме при записи, а не при чтении;
- настройки профиля целиком входят в экспорт и восстановление профиля.

Приложение вправе не пользоваться фасадом и писать настройки как обычные объекты, но тогда
оболочка их не покажет и не перенесёт.

## Изолированная файловая система

У приложения есть собственное поддерево `/app/<pkg>/files/`, которое ведёт себя как обычная
файловая система, но синхронизируется между устройствами и **не гарантирует наличие
содержимого локально**.

```ts
const st = await kos.files.stat("/app/com.example.music/files/cover.jpg");
if (st.state !== "materialized") {
  await kos.files.materialize(st.path, 5000);   // ждать не дольше 5 секунд
}
```

Отличие от пользовательских файлов: поддерево приложения принадлежит пакету и удаляется
вместе с ним; `/user/` принадлежит пользователю и переживает удаление приложения. Файл,
записанный приложением в `/user/`, становится файлом пользователя и сохраняет атрибут
`created-by` — см. [мусор и квоты](../05-storage/05-garbage-and-quotas.md).

Правило разделения: **в базе — то, что запрашивается и фильтруется; в файлах — то, что
читается целиком и велико**. Хранить изображение внутри объекта базы неверно: оно попадёт в
журнал операций и будет реплицироваться на все устройства безусловно. Правильная форма —
файл в VFS и `blob-ref` на него в объекте.

## Данные, доступ к которым выдал пользователь

```ts
const mount = await kos.files.pickDirectory();   // системный picker, не UI приложения
```

Существенные свойства:

- доступ выдаёт пользователь через системный диалог, приложение не может его инициировать
  скрытно;
- доступ выдан **этому приложению**, а не среде: другой пакет им не воспользуется;
- содержимое внешнего каталога не реплицируется — оно физически находится на той ноде, где
  каталог смонтирован. Обращение с другого устройства идёт через сеть к этой ноде и требует
  её доступности;
- платформа может отозвать доступ в любой момент, что возвращается как `revoked`. Это
  нормальное состояние, а не сбой.

## Реакция на изменения

Опрос базы в цикле — антипаттерн: он расходует батарею и квоты, и всё равно не заметит
изменения вовремя. Подписка:

```ts
const feed = await kos.storage.replicated.watch({ collection: "tracks" });
for await (const ev of feed) {
  switch (ev.type) {
    case "changed": upsert(ev.id, await db.get("tracks", ev.id)); break;
    case "removed": drop(ev.id); break;
    case "reset":   await reloadEverything(); break;   // обязателен к обработке
  }
}
```

`reset` приходит, когда нода синхронизировалась полным переносом состояния — например, после
долгого офлайна. Приложение, не обрабатывающее `reset`, будет показывать устаревшие данные.

Изменения, сделанные воркером того же пакета, приходят UI тем же каналом: общей памяти между
компонентами нет, и на разных нодах её и не может быть.

## Отсутствие содержимого файла

Полное дерево файлов видно на любом устройстве, содержимое — не всегда. Это самое частое
ошибочное предположение при переносе обычного приложения в K-OS.

| Режим открытия | Когда применять |
|---|---|
| `auto` | обычный случай: материализовать при необходимости, ждать в пределах deadline |
| `require-local` | интерфейс не должен ждать: показать «нет на этом устройстве» |
| `stream` | чтение диапазонов большого файла без полной загрузки |

Состояния `metadata-only`, `fetching`, `evicted`, `unavailable` являются штатными.
`unavailable` означает, что ни одна доступная нода не содержит содержимого — например,
файл есть только на выключенном ноутбуке. Правильная реакция интерфейса — сообщить, где
содержимое есть, а не показать ошибку чтения.

## Конфликты

Параллельная правка — не исключительная ситуация: пользователь мог изменить данные на
телефоне в самолёте и на десктопе дома.

```ts
const versions = await kos.files.conflicts(path);
if (versions.length > 1) showConflictUi(versions);
```

Для базы большинство конфликтов сливается автоматически по типу данных. Наблюдаемыми
остаются: конкурирующая правка одного поля, удаление против правки, конфликт содержимого
файла. Приложение либо разрешает их по прикладному правилу, либо показывает выбор
пользователю. Молча терять версию нельзя — система такого поведения и не навязывает.

## Миграции при обновлении

Схема коллекций объявляется в манифесте и версионируется. Ноды обновляются не одновременно,
поэтому:

- неизвестные поля сохраняются старой версией и не теряются при синхронизации;
- добавление поля, коллекции или индекса миграции не требует;
- несовместимое изменение объявляется миграцией и выполняется локально на каждой ноде;
- операции с более новой схемой помещаются в карантин, и пользователю показывается, что на
  этом устройстве приложение нужно обновить.

## Первый запуск на новом устройстве

Данные приходят не мгновенно. Приложение обязано работать в состоянии «состояние ещё не
загружено» и не показывать пустой список как «данных нет»:

```ts
const s = await kos.storage.replicated.status();
// s.initialSyncComplete, s.pendingObjects, s.lastSyncAt
```

То же относится к файлам: дерево может прийти раньше содержимого, и это видно по состоянию
записей.

Состояние синхронизации даётся **сводно по namespace**, а не по отдельным объектам:
`status()` — единственный источник этой информации для базы. Состояния «объект N ещё не
доехал» не существует, и приложение не должно его ожидать: причинность гарантируется,
а поштучное отслеживание вынуждало бы систему хранить и реплицировать метаданные
доставки на каждый объект. Исключение — файлы, где состояние содержимого относится к
конкретной записи и уже выражено полями `stat`.

Прогресс первичной загрузки крупных приложений показывает **системная оболочка**: она
знает объём и источник, приложение — нет. Приложению остаётся корректно работать до
`initialSyncComplete` и не изображать незагруженное состояние как пустое.

## Типичные ошибки

| Ошибка | Почему это ошибка |
|---|---|
| `localStorage` или IndexedDB как основное хранилище | не реплицируется, очищается вместе с данными контейнера |
| предположение, что чтение файла мгновенно | содержимое может отсутствовать на этом устройстве |
| ожидание единого порядка записей | гарантируется причинность, а не глобальный порядок |
| хранение больших двоичных данных в объектах базы | они попадут в журнал операций и разъедутся по всем устройствам |
| опрос базы в цикле вместо подписки | расход батареи и квот, запоздалая реакция |
| предположение, что воркер и UI работают на одной ноде | размещение выбирает планировщик |
| игнорирование `reset` в подписке | устаревший интерфейс после полного переноса состояния |
| хранение секретов в обычных данных | секреты имеют отдельный класс и отдельное хранилище |
| использование `app.cache` под промежуточные файлы операции | они вытеснят из кэша то, что дорого получить заново; для этого есть `app.tmp` |
| запись настроек мимо `kos.config` | оболочка их не покажет, слой ноды и перенос профиля работать не будут |
| попытка обеспечить уникальность проверкой перед записью | параллельная запись на другом устройстве её обойдёт |
