# Данные приложения глазами разработчика

Статус: план, документ не наполнен.  
Назначение: собрать в одном месте прикладную картину работы приложения с данными:
изолированная база, изолированная файловая система, события об изменениях.

Связанные документы: [модель состояния](../05-storage/01-state-model.md),
[база данных приложения](../05-storage/02-database.md), [VFS](../05-storage/03-vfs.md),
[каталог capabilities](../04-capabilities/02-catalog.md).

## Зачем отдельный документ

Механизмы описаны в разделах 05 и 06, но разработчику приложения нужен связный ответ на
вопрос «где хранить данные и что при этом произойдёт». Этот документ — прикладной
путеводитель, не вводящий новых механизмов.

## Что войдёт в документ

- карта решений: какой класс данных выбрать под задачу и почему;
- изолированная база данных приложения: что видит приложение, что делает система;
- изолированная файловая система приложения и её отличие от пользовательских файлов;
- работа с данными, доступ к которым приложение получило от пользователя;
- реакция на изменения: подписка на события вместо опроса;
- поведение при отсутствии содержимого файла на этом устройстве;
- поведение при конфликте параллельных изменений;
- миграции схемы данных приложения при обновлении пакета;
- типичные ошибки: попытка использовать `localStorage` как основное хранилище,
  предположение о мгновенном чтении файла, ожидание единого порядка записей.

## Исходные требования

- приложению доступна его собственная база данных, но через прослойку синхронизации:
  базой управляет система, приложение пишет и читает данные;
- у приложения есть изолированная файловая система;
- доступ к внешним папкам возможен, но только через приложение, которое этот доступ
  запросило у пользователя.

## Открытые вопросы

- нужен ли приложению явный доступ к состоянию синхронизации своих данных, или достаточно
  состояния отдельных объектов;
- как выражается прогресс первичной загрузки данных приложения на новом устройстве.
