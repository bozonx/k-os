# Размещение и распределённое исполнение

Статус: перенесено из прежних документов, требует ревизии.  
Назначение: определить execution scope, правила выбора ноды и поведение при отсутствии подходящей ноды.

Связанные документы: [профиль и ноды](../02-architecture/02-profile-and-nodes.md), [координация](../06-network/08-coordination.md), [делегирование](../06-network/06-rpc-and-delegation.md).


Состояние приложения может быть общим между устройствами, но процессы, views, соединения и аппаратные ресурсы всегда принадлежат конкретному устройству.

Cloud node участвует в исполнении наравне с остальными, но никогда не выбирается для компонентов типа `web-ui`. Компонент, требующий UI, размещается только на `device` node.

Для jobs и workers manifest или scheduler задаёт execution scope. Scope описывает требуемую кардинальность, а placement отдельно выбирает подходящий node:

| Scope | Семантика |
|---|---|
| `per-view` | Отдельно для каждого открытого view приложения |
| `per-node` | Один экземпляр на устройстве |
| `per-user` | Логически один экземпляр пользователя |
| `cluster-singleton` | Одно активное выполнение среди устройств |
| `leader-elected` | Выполнение на выбранном устройстве-лидере |

Placement учитывает обязательные `requires`, необязательные `prefers`, platform compatibility, локальность необходимых данных и разрешение на remote execution. Отсутствие подходящего node возвращает явное состояние `not-placed`, а не запускает component с урезанными неоговорёнными возможностями.

Распределённый scheduler должен учитывать:

- доступность устройства;
- необходимые capabilities и оборудование;
- online/offline состояние;
- питание и батарею;
- idempotency задачи;
- lease и потерю лидера;
- checkpoint и повтор выполнения.

Распределённая операция не получает гарантию exactly-once по умолчанию. Обработчики должны проектироваться как idempotent либо использовать системные механизмы дедупликации.
