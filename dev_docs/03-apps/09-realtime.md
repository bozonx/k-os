# Realtime-возможности

Статус: готов  
Назначение: определить, какие realtime-возможности предоставляются приложениям, какой ценой
и почему они не являются основным режимом работы системы.

Связанные документы: [каналы и транспорт](../06-network/04-transport-and-discovery.md),
[репликация](../06-network/07-replication.md), [события и push](./10-events-and-push.md),
[модель времени](../06-network/05-time.md), [устройства и IoT](../08-devices/01-model.md).

## Позиция в системе

Основной режим — репликация с последующей сходимостью, а не мгновенная доставка.
Предполагается, что всеми устройствами управляет один человек, поэтому одновременное
активное изменение одних данных с двух устройств — редкий случай, ради которого не стоит
держать постоянные соединения и расходовать батарею на всех нодах.

Realtime существует для приложений, которым он действительно нужен, объявляется явно и
квотируется.

## Три способа доставки

| Способ | Гарантии | Стоимость | Когда применять |
|---|---|---|---|
| Репликация | сходимость, сохранность, причинный порядок | низкая, работает офлайн | данные, документы, настройки — по умолчанию |
| События | доставка не менее одного раза, дедупликация, переживают офлайн | средняя | уведомления, активация воркеров, изменения состояния |
| Realtime-канал | доставка по возможности, порядок в пределах канала, без сохранности | высокая: соединение, энергия, трафик | поток показаний, управление, интерактивность |

Главное различие: **realtime-сообщение, не доставленное сейчас, не доставляется никогда**.
Оно не сохраняется, не повторяется и не участвует в сходимости. Приложение, которому важна
сохранность, обязано записать данные обычным способом; realtime — это способ узнать раньше,
а не способ узнать надёжно.

## Сценарии, оправдывающие realtime

- управление устройством: изменение положения регулятора должно ощущаться мгновенно;
- потоковые показания датчиков, где важно последнее значение, а не полная история;
- удалённое управление нодой: клавиатура, указатель, просмотр экрана;
- совместное присутствие: курсор собеседника, индикатор набора текста;
- голос и видео между связанными пользователями.

Не оправдывают realtime: синхронизация списков, доставка сообщений чата, уведомления,
обновление интерфейса по изменению данных — для всего этого есть подписка на изменения,
которая дешевле и надёжнее.

## Контракт

```wit
interface realtime {
  enum target-kind { node, profile, linked-peer }

  record channel-options {
    target: target-kind,
    target-id: string,          // node-id, profile-id
    topic: string,              // тема внутри приложения
    max-rate-hz: u32,           // запрошенная частота, может быть понижена
    ordered: bool,              // порядок в пределах канала
    lossy: bool,                // допустимо отбрасывать при перегрузке
  }

  record frame {
    seq: u64,                   // монотонный номер отправителя
    payload: list<u8>,
    sent-at: instant,           // часы отправителя, только для отображения
  }

  variant channel-event {
    data(frame),
    gap(u64),                   // сколько кадров потеряно
    degraded(string),           // канал сменился на худший, с причиной
    closed(string),
  }

  resource channel {
    send:    func(payload: list<u8>) -> result<_, error>;
    receive: func() -> result<option<channel-event>, error>;
    stats:   func() -> channel-stats;    // rtt, потери, текущий транспорт
    close:   func();
  }

  open: func(opts: channel-options) -> result<channel, error>;
}
```

Существенные свойства:

- **`gap` обязателен к обработке.** Потеря кадров — штатное поведение канала, а не сбой;
  приложение, считающее поток непрерывным, будет показывать неверное состояние;
- **`degraded` сообщает о смене пути.** Переход с локальной сети на ретранслятор меняет
  задержку на порядок, и интерфейс обязан это отражать, а не делать вид, что всё прежнее;
- **`stats` доступна приложению**, потому что решение «показывать ли живое управление»
  зависит от реальной задержки;
- **канал принадлежит execution.** Он закрывается вместе с представлением или задачей;
  канал, переживающий закрытие интерфейса, требует фонового lease.

## Транспорт и деградация

Канал строится поверх уже существующей аутентифицированной сессии между нодами и не вводит
собственной модели identity и шифрования.

```text
Локальная сеть      прямое соединение, минимальная задержка — предпочтительно
Прямое соединение   через посредника после установления пути
Ретранслятор        гарантированный путь, задержка выше, метаданные видит узел транзита
BLE                 только управляющие сообщения малого объёма
Нет пути            open возвращает unavailable со списком доступных нод
```

Деградация выражается явно: система не подменяет realtime «почти realtime» молча.
Приложение получает `degraded` с причиной и может понизить частоту, упростить содержимое
или предложить пользователю выполнить операцию на другом устройстве.

## Стоимость и ограничения

| Фактор | Поведение |
|---|---|
| энергия | открытый канал удерживает соединение; на батарее частота ограничивается политикой ноды |
| metered-трафик | объёмные потоки в сотовой сети требуют явного согласия пользователя |
| фоновый режим | на Android канал не переживает выгрузку процесса; после возвращения канал открывается заново |
| число каналов | квотируется по пакету и по ноде |
| частота и полоса | запрошенная частота может быть понижена; фактическая видна в `stats` |

Право: `realtime.channel` с областью — тема приложения и класс адресата (свои ноды,
связанные пользователи). Оно не выдаётся молча вместе с сетевыми правами, потому что
означает постоянный расход ресурсов устройства.

## Время и порядок

- порядок гарантируется **в пределах одного канала** по `seq` отправителя;
- порядок между разными каналами и между каналом и реплицируемым состоянием **не
  гарантируется**: realtime-сообщение может прийти раньше, чем изменение данных, которое
  его вызвало;
- `sent-at` — настенные часы отправителя, пригодны только для отображения; задержка
  измеряется монотонными часами получателя через `stats`;
- realtime-канал не участвует в причинности реплицируемого состояния и не может служить
  способом упорядочить записи.

Отсюда практическое правило: realtime сообщает «как сейчас», реплицируемое состояние —
«что произошло». Приложение, использующее оба, обязано считать источником истины второе.

## Между сетями разных пользователей

Realtime между связанными пользователями допускается, если обе стороны выдали
соответствующий доступ. Отличия от внутрипрофильного случая:

- адресуется сеть собеседника, а не устройство: канал устанавливается с той нодой,
  которая доступна и которой пользователь пользуется сейчас;
- переход собеседника на другое устройство закрывает канал и требует его переоткрытия;
  бесшовной миграции канала система не обещает;
- прямое соединение между двумя сетями за NAT не всегда достижимо, поэтому вероятность
  деградации до ретранслятора выше;
- содержимое канала шифруется между конечными нодами; узел транзита видит только
  метаданные.

## Взаимодействие с устройствами

Потоки показаний датчиков — основной практический случай realtime внутри профиля. Здесь
канал открывается не к приложению, а к [устройству](../08-devices/01-model.md), и запросы
маршрутизируются к ноде, которая им владеет. Правила те же: последнее значение важнее
полноты, потеря кадров штатна, история показаний хранится отдельно как обычные данные, если
приложение её ведёт.

## Проверяемые критерии

- отсутствие realtime-канала не мешает работе ни одного базового сценария системы;
- приложение получает явные `gap` и `degraded`, а не бесшумную потерю качества;
- канал закрывается вместе с владеющим execution и не удерживает соединение сам по себе;
- realtime не используется как способ упорядочить или сохранить данные;
- стоимость канала видна пользователю: открытый канал наблюдаем в системном интерфейсе.
