# Host adapters

Статус: перенесено из прежних документов, требует ревизии.  
Назначение: описать нижний платформозависимый слой: набор контрактов, правила реализации и требования к mock-реализациям.

Связанные документы: [drivers](./05-drivers.md), [каталог capabilities](../04-capabilities/02-catalog.md), [тестируемость](../12-testing/01-determinism-and-simulation.md).


Host adapter — нижний платформозависимый слой, реализующий примитив ОС или устройства.

Термин `host adapter` является единственным для этой роли. Название `platform provider` считается устаревшим и в новом коде и документации не используется. Соглашение об именовании типов: `<Domain>Adapter`, например `FileSystemAdapter`, реализации — `<Platform><Domain>Adapter`.

Набор контрактов:

| Adapter | Назначение |
|---|---|
| `FileSystemAdapter` | доступ к хранилищу устройства и внешним монтированиям |
| `SocketAdapter` | TCP/UDP/TLS-примитивы |
| `SecureKeyStoreAdapter` | платформенное хранилище ключей |
| `ClockAdapter` | wall clock, monotonic clock, таймеры |
| `RandomAdapter` | криптографическая и обычная случайность |
| `BackgroundSchedulerAdapter` | платформенные возможности фонового запуска |
| `BluetoothLeAdapter` | BLE-канал и discovery |
| `ProcessAdapter` | запуск программ хостовой ОС |
| `SystemAdapter` | сведения о системе и управление питанием |
| `NotificationAdapter` | системные уведомления |
| `MediaCaptureAdapter` | захват и воспроизведение |
| `GpioAdapter` | линии GPIO, если платформа их предоставляет |
| `SerialAdapter` | последовательные порты |

`ClockAdapter` и `RandomAdapter` выделены явно: без них невозможна детерминированная симуляция, а прямое обращение к системным часам и генератору случайных чисел из ядра запрещено.

У разных видов adapters нет общего универсального API. Общим является контракт между реализациями одного вида:

```text
FileSystemAdapter
├── LinuxFileSystemAdapter
├── WindowsFileSystemAdapter
├── AndroidFileSystemAdapter
└── MockFileSystemAdapter
```

Наличие mock-реализации для каждого контракта обязательно и является частью определения adapter, а не тестовой инфраструктурой.

Host adapter:

- выполняет низкоуровневую операцию;
- скрывает различия ОС и платформ;
- не знает о приложениях и пользователях;
- не определяет permissions и квоты;
- не управляет распределением ресурса между потребителями;
- не отвечает за синхронизацию пользовательского состояния.

Adapter также сообщает runtime свои возможности и ограничения: availability, поддерживаемые режимы, лимиты payload и streaming, background guarantees и стоимость использования ресурса, если она известна.

HTTP, WebSocket и MQTT являются переносимыми protocol engines или системными services поверх network primitives. Они не относятся к host adapters только потому, что используют платформенные API. Внешние инструменты вроде FFmpeg и Git не являются host adapters: это capability с несколькими взаимозаменяемыми backends, см. раздел о внешних инструментах.

В первой версии adapters являются встроенными Rust-компонентами ядра.

### SystemAdapter

`SystemAdapter` предоставляет сведения о хосте и ограниченный набор управляющих действий. Он разделён на две части с разным уровнем доверия.

Чтение — `system.info`:

```text
os, версия, архитектура, тип устройства
hostname и локальное имя устройства
uptime
CPU: число ядер, загрузка
память: объём, доступно
хранилище: объём, свободно по томам
питание: наличие сети, уровень батареи, режим экономии
сеть: тип подключения, metered/unmetered
locale, timezone
экран: размер, плотность, ориентация
```

Данные разделены на низкочувствительный и чувствительный поднаборы. Низкочувствительный доступен приложениям с базовым разрешением, потому что от него зависит адаптация UI и решение о тяжёлых операциях. Чувствительный — hostname, серийные номера, список сетевых интерфейсов, полный список томов — требует отдельного разрешения, поскольку служит для фингерпринтинга.

Управление — `system.power`:

```text
reboot
shutdown
suspend
отмена запланированного действия
```

Это высокодоверенная capability. Она не выдаётся обычным приложениям, требует явного подтверждения пользователя, может требовать эскалации прав в ОС и на Android недоступна. Отсутствие capability — нормальное состояние, обрабатываемое явно.

Сводка `system.info` каждого node публикуется в node capability descriptor и используется для placement, поэтому она доступна другим nodes профиля даже когда устройство офлайн — с пометкой давности.

### GpioAdapter и оборудование

Оборудование доступно не везде, и это нормальное состояние модели.

Способы поставки:

1. **Сборочная feature платформенного crate.** `host-linux` собирается с включённым `gpio`, где это имеет смысл. Сборки для платформ без поддержки просто не содержат этот код.
2. **Platform extension package.** Отдельный подписанный нативный пакет, устанавливаемый пользователем явно, с отдельным уровнем доверия. Это не обычное приложение и не WASM worker; см. раздел о расширяемости.

Для приложения оба способа выглядят одинаково: capability либо доступна на этом node, либо возвращает `unavailable`. Приложение не определяет способ поставки.

Типовой сценарий использования — удалённый: UI на телефоне управляет GPIO на Linux-ноде через delegation capability. Поэтому отсутствие оборудования на текущем устройстве не означает недоступность функции для пользователя.
