## Роль слоя

Host adapter — нижний платформозависимый слой, реализующий один примитив операционной
системы или оборудования. Это единственное место в системе, где допустимо обращение к
внешнему миру: к файловой системе хоста, сокетам, часам, генератору случайных чисел,
хранилищу ключей, шинам и процессам.

Инвариант, из которого следует всё остальное: **любое обращение к внешнему миру проходит
через host adapter, имеющий mock-реализацию**. Нарушение этого правила не обнаруживается
компилятором, поэтому оно вынесено в [критерии корректности](./10-correctness-criteria.md)
и проверяется тестом сборки: ядро, собранное с `host-mock`, не должно иметь ни одного
обращения к системным API.

Термин `host adapter` является единственным для этой роли. Название `platform provider`
считается устаревшим и в новом коде и документации не используется; в разговорной речи оно
означает то же самое, см. [словарь](../01-overview/02-glossary.md).

### Что adapter делает и чего не делает

| Adapter делает | Adapter не делает |
|---|---|
| выполняет низкоуровневую операцию платформы | не знает о приложениях, пакетах и пользователях |
| скрывает различия ОС за одним контрактом | не определяет permissions, grants и квоты |
| сообщает о своей доступности и лимитах | не решает, кому и в каком объёме выдать ресурс |
| владеет платформенным дескриптором ресурса | не мультиплексирует ресурс между потребителями |
| транслирует платформенные ошибки в общую таксономию | не выполняет retry-политику и reconnect |
| отдаёт данные потоками с backpressure | не буферизует неограниченно и не кэширует |

Всё, что перечислено в правой колонке, относится к [слою drivers](./05-drivers.md).
Смешение этих ролей — самая частая ошибка проектирования нижнего слоя: adapter, который
начинает переиспользовать соединения, немедленно перестаёт быть заменяемым и
тестируемым.

## Соглашения

```text
контракт:     <Domain>Adapter          FileSystemAdapter
реализация:   <Platform><Domain>Adapter LinuxFileSystemAdapter
mock:         Mock<Domain>Adapter       MockFileSystemAdapter
crate:        host-adapters             контракты и общие типы
              host-linux / -windows / -android / -mock
```

У разных видов adapters нет общего универсального API: попытка ввести единый интерфейс для
файлов, часов и GPIO даёт бессмысленную абстракцию. Общим является контракт между
реализациями **одного** вида:

```text
FileSystemAdapter
├── LinuxFileSystemAdapter
├── WindowsFileSystemAdapter
├── AndroidFileSystemAdapter
└── MockFileSystemAdapter
```

## Общие правила контракта

Каждый контракт adapter обязан удовлетворять следующему, независимо от домена:

1. **Отсутствие ambient authority.** Adapter не читает переменные окружения, не обращается к
   глобальным синглтонам и не определяет пути самостоятельно. Всё, что нужно для работы,
   передаётся при создании: корневые каталоги, конфигурация, ссылки на `ClockAdapter` и
   `RandomAdapter`.
2. **Асинхронность и отмена.** Каждая потенциально блокирующая операция принимает deadline и
   токен отмены. Синхронные блокирующие вызовы в контракте запрещены.
3. **Явная таксономия ошибок.** Платформенная ошибка транслируется в общий вариант
   (`not-found`, `denied`, `unavailable`, `io`, `quota-exceeded`, …) с сохранением исходного
   кода в диагностическом поле. Приложение никогда не видит `errno`.
4. **Потоки с backpressure.** Передача данных выражается через reader/writer с явным числом
   принятых байт, а не через «отдай всё содержимое».
5. **Время и случайность — только через adapters.** `ClockAdapter` и `RandomAdapter`
   передаются явно даже внутрь других adapters. Прямое обращение к системным часам и
   генератору случайных чисел запрещено везде, включая платформенные реализации, кроме
   самих этих двух adapters.
6. **Идемпотентность освобождения.** Закрытие ресурса можно вызвать повторно; двойное
   закрытие не является ошибкой.
7. **Отсутствие скрытого состояния между вызовами.** Если состояние нужно (открытый файл,
   установленное соединение), оно выражается ресурсом с явным временем жизни.

## Модель доступности

Отсутствие возможности на конкретном устройстве — **нормальное состояние модели**, а не
ошибка реализации. Adapter обязан сообщать о себе достаточно, чтобы вышестоящие слои могли
принять решение без попытки вызова.

```text
AdapterDescriptor
├── kind                 вид adapter
├── availability         available | unavailable(reason) | degraded(reason)
├── implementation       имя платформенной реализации и её версия
├── features             поддерживаемые режимы: streaming, seek, watch, listen, …
├── limits               максимальный payload, число одновременных операций, MTU
├── background           поведение, когда устройство в фоне или спит
└── cost                 энергетическая и трафиковая стоимость, если известна
```

Дескрипторы всех adapters сводятся в **node capability descriptor**, который реплицируется
между нодами профиля (см. [профиль и ноды](./02-profile-and-nodes.md)). Благодаря этому
placement и UI могут ответить на вопрос «где эта возможность есть» даже когда нужное
устройство выключено — с явной пометкой давности сведений.

`degraded` введён отдельно от `unavailable`: например, файловая система доступна только для
чтения, или BLE работает, но платформа не даёт фонового сканирования. Молчаливая деградация
запрещена, поэтому состояние выражается явно и доходит до приложения как причина в
`unavailable-info` или как ограничение в дескрипторе.

## Каталог контрактов

### Системные примитивы

| Adapter | Назначение | Ключевые ограничения |
|---|---|---|
| `ClockAdapter` | wall clock, monotonic clock, таймеры | единственный источник времени в системе |
| `RandomAdapter` | криптографическая и обычная случайность | единственный источник энтропии |
| `SystemAdapter` | сведения о системе, питание, управление питанием | часть операций недоступна на Android |
| `SecureKeyStoreAdapter` | платформенное хранилище ключей | ключ не покидает хранилище, только операции над ним |
| `BackgroundSchedulerAdapter` | платформенные возможности фонового запуска | гарантии платформы различаются радикально |
| `ProcessAdapter` | запуск программ хостовой ОС | на Android недоступен для произвольных программ |
| `NotificationAdapter` | системные уведомления | ограничения частоты и права платформы |

### Хранилище

| Adapter | Назначение | Ключевые ограничения |
|---|---|---|
| `FileSystemAdapter` | доступ к хранилищу устройства | ограничения имён — объединение ограничений платформ |
| `ExternalStorageAdapter` | внешние монтирования и пользовательские каталоги | на Android — SAF-идентификаторы, отзываемые платформой |
| `BlockDeviceAdapter` | сведения о томах, свободное место, вытеснение | не входит в v0, контракт зарезервирован |

`FileSystemAdapter` и `ExternalStorageAdapter` разделены намеренно: первый работает с
приватным каталогом ноды, где семантика одинакова на всех платформах, второй — с
пространством, которым владеет платформа и где доступ может быть отозван в любой момент.

### Сеть

| Adapter | Назначение | Ключевые ограничения |
|---|---|---|
| `SocketAdapter` | TCP/UDP-примитивы, `connect`, `listen`, `accept` | фоновые ограничения на мобильных |
| `TlsAdapter` | установление TLS поверх потока, проверка цепочки | хранилище корневых сертификатов платформенное |
| `NetworkInfoAdapter` | интерфейсы, тип подключения, metered, смена сети | список интерфейсов — чувствительные данные |
| `BluetoothLeAdapter` | BLE-канал, advertising, discovery | малый MTU, ограничения фонового режима |
| `MdnsAdapter` | обнаружение в локальной сети | часть Wi-Fi-сетей изолирует клиентов |

**HTTP, WebSocket и MQTT не являются host adapters.** Это переносимые protocol engines,
реализованные один раз поверх `SocketAdapter` и `TlsAdapter` и живущие на слое drivers и
services. Вертикальный разбор этих стеков — в [базовом стеке](./12-base-stack.md).
Причина решения: реализация HTTP платформенными средствами дала бы разное поведение
редиректов, заголовков и таймаутов на трёх платформах, то есть ровно то, что слой adapters
обязан устранять.

Исключение допускается только там, где платформа не даёт сокетов нужного класса и
предоставляет протокол как системную услугу; такое исключение оформляется отдельным ADR и
объявляется в дескрипторе как `implementation`, чтобы различие было наблюдаемым.

### Оборудование

| Adapter | Назначение | Ключевые ограничения |
|---|---|---|
| `GpioAdapter` | линии GPIO: чтение, запись, прерывания | доступен в основном на Linux-нодах |
| `SerialAdapter` | последовательные порты | требует прав доступа к устройству на хосте |
| `I2cAdapter`, `SpiAdapter` | шины датчиков | поставляются платформенным расширением |
| `UsbAdapter` | перечисление и доступ к USB-устройствам | не входит в v0 |
| `MediaCaptureAdapter` | захват и воспроизведение аудио и видео | требует пользовательского разрешения платформы |
| `InputAdapter` | синтез ввода: клавиатура, указатель | только для [управления нодами](../09-devices/02-node-control.md) |
| `ScreenCaptureAdapter` | снимок и поток экрана | высокий класс доверия, отдельное подтверждение |

Оборудование доступно не везде, и это часть модели, а не дефект поставки. Типовой сценарий
использования — удалённый: UI на телефоне управляет GPIO на Linux-ноде через delegation.
Поэтому отсутствие оборудования на текущем устройстве не означает недоступность функции для
пользователя, и UI обязан предлагать выполнение на другой ноде вместо сообщения об ошибке.

## Примеры контрактов

Полные определения находятся в `crates/host-adapters`; здесь зафиксирована форма, из
которой следуют требования к реализациям.

### ClockAdapter

```rust
trait ClockAdapter {
    fn now(&self) -> WallTime;            // настенные часы, только для отображения
    fn monotonic(&self) -> Monotonic;     // для интервалов, таймаутов, leases
    fn timezone(&self) -> TimeZone;       // IANA
    async fn sleep_until(&self, at: Monotonic, cancel: &Cancel) -> Result<(), Error>;
    fn timer(&self, period: Duration) -> Timer;
}
```

Разделение `now` и `monotonic` не является удобством: [модель времени](../06-network/05-time.md)
запрещает использовать настенные часы для измерения интервалов и для упорядочивания
операций. Единственный способ сделать это правило проверяемым — разделить их на уровне
типов, чтобы `WallTime` нельзя было вычесть из `WallTime` и получить длительность.

### FileSystemAdapter

```rust
trait FileSystemAdapter {
    async fn open_read(&self, path: &HostPath, opts: ReadOpts) -> Result<Box<dyn ByteReader>, Error>;
    async fn open_write(&self, path: &HostPath, opts: WriteOpts) -> Result<Box<dyn ByteWriter>, Error>;
    async fn stat(&self, path: &HostPath) -> Result<HostStat, Error>;
    async fn list(&self, path: &HostPath, cursor: Option<Cursor>) -> Result<Page<HostEntry>, Error>;
    async fn mkdir(&self, path: &HostPath, parents: bool) -> Result<(), Error>;
    async fn remove(&self, path: &HostPath, recursive: bool) -> Result<(), Error>;
    async fn rename_atomic(&self, from: &HostPath, to: &HostPath) -> Result<(), Error>;
    async fn sync_data(&self, path: &HostPath) -> Result<(), Error>;
    async fn watch(&self, path: &HostPath, recursive: bool) -> Result<Box<dyn ChangeStream>, Error>;
    fn free_space(&self, path: &HostPath) -> Result<SpaceInfo, Error>;
}
```

Существенные требования, которые нельзя переложить на верхние слои:

- `rename_atomic` обязан быть атомарной операцией платформы. На этом строится атомарная
  публикация файла: запись во временный объект, `sync_data`, затем `rename_atomic`.
  Если платформа не даёт атомарного переименования, adapter обязан объявить
  `features` без `atomic-rename`, а не имитировать его копированием;
- `sync_data` отделён от закрытия: `commit` в публичном API опирается на реальный
  сброс на носитель, иначе обещание «частично записанный файл не наблюдаем» ложно;
- `HostPath` — не строка. Это тип, различающий корни (`node-private`, `external-mount`,
  `temp`) и запрещающий выход за пределы корня. Проверка выполняется в конструкторе, а не
  на каждом вызове;
- `watch` не гарантирован: часть платформ и сетевых файловых систем не дают надёжных
  уведомлений. Отсутствие выражается через `features`, вышестоящий слой переходит на
  периодическое сканирование явно.

### SocketAdapter

```rust
trait SocketAdapter {
    async fn connect(&self, addr: &Endpoint, opts: ConnectOpts) -> Result<Box<dyn Stream>, Error>;
    async fn listen(&self, bind: &BindSpec, opts: ListenOpts) -> Result<Box<dyn Listener>, Error>;
    async fn bind_udp(&self, bind: &BindSpec) -> Result<Box<dyn Datagrams>, Error>;
    fn local_endpoints(&self) -> Vec<Endpoint>;
}
```

`listen` присутствует на уровне adapter, потому что на нём строятся HTTP- и
WebSocket-серверы приложений. Платформенные ограничения — запрет привилегированных портов,
ограничения фонового прослушивания на Android, отсутствие входящих соединений в сотовой
сети — выражаются дескриптором и ошибкой `unavailable`, а не молчаливой заменой поведения.

### SecureKeyStoreAdapter

```rust
trait SecureKeyStoreAdapter {
    async fn create_key(&self, spec: KeySpec) -> Result<KeyHandle, Error>;
    async fn sign(&self, key: &KeyHandle, data: &[u8]) -> Result<Signature, Error>;
    async fn agree(&self, key: &KeyHandle, peer: &PublicKey) -> Result<SharedSecret, Error>;
    async fn public_key(&self, key: &KeyHandle) -> Result<PublicKey, Error>;
    async fn delete_key(&self, key: &KeyHandle) -> Result<(), Error>;
    fn protection(&self) -> KeyProtection;   // hardware | os-keystore | software
}
```

Контракт намеренно не содержит экспорта приватного ключа: `node identity key` относится к
классу `device-bound-secret` и не покидает устройство ни при каких операциях, включая
резервное копирование профиля. `protection` сообщает реальный уровень защиты, потому что
software-реализация на ноде без TPM и аппаратный ключ дают разные гарантии, и
[модель угроз](../11-security/03-threat-model.md) обязана это различать.

## Жизненный цикл adapter

```text
1. Сборка       платформенный crate предоставляет набор реализаций
2. Регистрация  ядро строит таблицу adapters по виду
3. Probe        adapter сообщает дескриптор: availability, features, limits
4. Работа       drivers получают ссылки на adapters
5. Изменение    доступность может измениться в любой момент
6. Остановка    освобождение ресурсов в порядке, обратном запуску
```

Пункт 5 существенен: устройство подключают и отключают, платформа отзывает доступ к
внешнему каталогу, пользователь выключает Bluetooth. Изменение дескриптора публикуется как
системное событие; drivers обязаны обрабатывать исчезновение adapter, закрывая выданные
handles с ошибкой `revoked`, а не удерживая их бесконечно.

Adapter не перезапускает себя сам и не выполняет retry: это решение вышестоящего слоя,
который знает контекст операции.

## Доустанавливаемые платформенные расширения

Набор adapters не фиксируется навсегда. Часть оборудования и протоколов невозможно и не
нужно включать в основную сборку: промышленные шины, специфические радиомодули, редкие
периферийные устройства. Для них существует **platform extension package** — отдельно
устанавливаемый подписанный нативный пакет, добавляющий реализации adapters.

```text
Platform extension package
├── манифест: какие adapter kinds предоставляет, для каких платформ и архитектур
├── подпись издателя, проверяемая отдельно от подписи обычных пакетов
├── объявление требуемых прав у хостовой ОС
└── бинарные артефакты по платформам
```

Правила:

1. **Устанавливается только явным действием пользователя** с отдельным подтверждением,
   текст которого отличается от установки обычного приложения. Расширение входит в
   доверенную вычислительную базу ноды, и диалог обязан это сообщать.
2. **Устанавливается на конкретной ноде, а не в профиле.** Факт установки реплицируется как
   сведение, но артефакты и активация — решение ноды: расширение для шины I²C бессмысленно
   на телефоне.
3. **Не расширяет права автоматически.** Расширение объявляет, какие capabilities оно
   предоставляет; чтобы приложение получило к ним доступ, требуется обычный grant.
4. **Изолируется по возможности платформы.** Предпочтительная форма исполнения —
   отдельный процесс с узким IPC-контрактом, чтобы сбой расширения не завершал ядро.
   Внутрипроцессная загрузка допускается только для расширений, подписанных издателем
   системы, и только через стабильный C ABI.
5. **Версионируется по контракту adapter, а не по версии ядра.** Расширение объявляет
   диапазон версий контракта, который поддерживает; несовпадение делает его неактивным с
   явной причиной, а не приводит к падению.
6. **Обязано предоставлять mock.** Расширение без mock-реализации нельзя проверить в
   симуляции, поэтому оно принимается только с ним.

**Драйверы, в отличие от adapters, не доустанавливаются.** Слой владения ресурсами
целиком принадлежит системе: от корректности мультиплексирования, квот и отзыва handles
зависит безопасность всей среды, и внешний код там не появляется. Расширение поставляет
механизм; политику применяет система. Обоснование и полный список механизмов расширения —
в [модели расширяемости](./09-extensibility.md).

## Mock-реализации и contract tests

Наличие mock-реализации для каждого контракта — часть определения adapter, а не тестовая
инфраструктура. `host-mock` поддерживается наравне с платформенными crate и входит в
поставку.

Mock обязан уметь:

- воспроизводить нормальное поведение контракта полностью;
- вносить сбои: ошибка ввода-вывода, исчерпание места, отказ в доступе, отзыв платформой;
- вносить задержки и порядок завершения операций, задаваемые сценарием;
- работать детерминированно при фиксированном seed `RandomAdapter` и виртуальном времени
  `ClockAdapter`.

**Contract tests** — общий для всех реализаций одного вида набор тестов, проверяющий
одинаковую наблюдаемую семантику: одинаковую трансляцию ошибок, одинаковое поведение при
отмене, одинаковые ограничения имён. Платформенная реализация считается готовой, когда
проходит contract tests своего вида; собственные тесты реализации их не заменяют.

Отдельно проверяется соответствие дескриптора реальности: если реализация объявляет
`features: [watch]`, contract test обязан наблюдать уведомление об изменении.

## Матрица платформ

Матрица является частью публичного контракта: приложение видит её через
`capabilities.query` и через node capability descriptor.

| Adapter | Linux desktop | Linux headless | Windows | Android |
|---|---|---|---|---|
| `ClockAdapter`, `RandomAdapter` | да | да | да | да |
| `FileSystemAdapter` | да | да | да | да |
| `ExternalStorageAdapter` | да | ограниченно | да | SAF, отзываемо |
| `SocketAdapter`, `TlsAdapter` | да | да | да | ограничения фона |
| `SocketAdapter::listen` | да | да | да | ограниченно |
| `NetworkInfoAdapter` | да | да | да | часть данных требует прав |
| `MdnsAdapter` | да | да | да | ограничения энергосбережения |
| `BluetoothLeAdapter` | да | зависит от оборудования | да | ограничения фона |
| `SecureKeyStoreAdapter` | keyring / файл с защитой | файл с защитой | DPAPI / CNG | Keystore |
| `BackgroundSchedulerAdapter` | да | да, без ограничений | да | жёсткие ограничения ОС |
| `ProcessAdapter` | да | да | да | нет |

## Проверяемые критерии

Реализация слоя соответствует этому документу, если:

- ни один crate выше `host-adapters` не обращается к системным API напрямую;
- каждый контракт имеет mock-реализацию и набор contract tests;
- ядро, собранное только с `host-mock`, запускается и проходит симуляцию кластера;
- замена платформенной реализации не требует изменения API drivers и services;
- отсутствие возможности выражается дескриптором и `unavailable`, а не исключением;
- дескрипторы всех adapters попадают в node capability descriptor и реплицируются;
- ни один adapter не выполняет retry, reconnect, кэширование и мультиплексирование;
- платформенное расширение можно установить и удалить без пересборки ядра.
