# Базовый стек: HTTP, WebSocket, файловая система

Статус: готов  
Назначение: разобрать по вертикали три базовые возможности системы — HTTP client и server,
WebSocket client и server, файловую систему — от host adapter до контракта приложения, и
зафиксировать решения, общие для всех будущих протокольных стеков.

Связанные документы: [host adapters](./03-host-adapters.md), [drivers](./04-drivers.md),
[services](./05-services.md), [каталог capabilities](../04-capabilities/02-catalog/00-index.md),
[VFS](../05-storage/03-vfs.md), [удалённые вызовы](../06-network/06-rpc-and-delegation.md).

## Зачем этот документ

Приложениям **не предоставляется низкоуровневый доступ к IO**. Вместо него система даёт
набор типизированных возможностей, под которыми находятся платформозависимые реализации.
Три из них — HTTP, WebSocket и файлы — являются базовыми: через них выражается почти всё,
что делает обычное приложение, и на их примере фиксируются правила, которым обязаны
следовать MQTT, медиа, Git, GPIO и любой протокол, добавленный позже.

Общее правило вертикали:

```text
Приложение          типизированный контракт, ничего не знает о платформе
Service             прикладная семантика, durable-состояние, маршрутизация
Driver              владение ресурсом, пул, квоты, retry, handles
Protocol engine     переносимая реализация протокола, одна на все платформы
Host adapter        сокеты, TLS, файлы — платформозависимый примитив
```

**Протокол реализуется один раз и переносимо.** HTTP, WebSocket и MQTT не являются host
adapters: если бы каждая платформа приносила собственную HTTP-реализацию, поведение
редиректов, заголовков, таймаутов и повторов различалось бы на трёх платформах — ровно та
проблема, которую слой adapters обязан устранять.

## HTTP client

### Вертикаль

```text
capability net.http:<host>          право на обращение к конкретному хосту
        ↓
http-client-driver                  пул keep-alive, квоты, retry, редиректы
        ↓
http protocol engine                HTTP/1.1 и HTTP/2, переносимая реализация
        ↓
network-broker                      разрешение имён, выбор интерфейса, учёт трафика
        ↓
SocketAdapter + TlsAdapter          платформенный примитив
```

### Что видит приложение

Контракт зафиксирован в [каталоге, раздел «Сеть»](../04-capabilities/02-catalog/04-network.md):
`send`, `send-stream`, ответ в виде ресурса `exchange` с потоковым телом.

### Решения

1. **Право выдаётся по хосту.** `net.http:api.example.com` — не «доступ в интернет», а
   доступ к названному хосту. Пакет, запросивший `net.http:*`, показывается пользователю
   иначе, чем пакет с конкретным списком.
2. **Редирект проверяется на каждом переходе.** Переход на хост, не покрытый правом, не
   выполняется: возвращается `denied` с указанием целевого хоста. Иначе право на один хост
   превращалось бы в право на любой.
3. **TLS обязателен по умолчанию.** Обращение по `http://` требует отдельной пометки в
   манифесте с обоснованием; исключение существует для устройств в локальной сети, у
   которых нет сертификата.
4. **Metered-политика применяется драйвером.** В metered-сети объёмные загрузки фоновых
   компонентов откладываются или переносятся на другую ноду; UI-инициированный запрос не
   откладывается никогда. Приложение видит это как задержку или `unavailable`, а не как
   молчаливую потерю запроса.
5. **Запрос делегируем.** Если у ноды нет доступа в интернет, запрос может быть выполнен
   другой нодой профиля — типично облачной, работающей шлюзом. Делегирование не является
   автоматическим: оно требует права `remote.delegate` и согласия целевой ноды, и добавляет
   к ответу ошибки `unreachable` и `result-unknown`.
6. **Тело — поток.** Ответ не материализуется целиком в памяти; загрузка файла идёт
   в VFS через `byte-reader` без промежуточной копии.

### Локальная сеть и приватность

Обращение к устройству в локальной сети (`net.http:192.168.1.50`) отличается от обращения в
интернет: оно не покидает дом, но раскрывает приложению состав локальной сети. Поэтому
права на приватные диапазоны адресов относятся к отдельному классу и не выдаются
автоматически вместе с правом на публичный хост.

## HTTP server

Здесь система принимает решение, которого нет в обычных прикладных средах, и которое
определяет всю модель «приложение экспортирует API».

### Два разных механизма под одним словом «сервер»

| Механизм | Кто клиент | Транспорт | Право |
|---|---|---|---|
| **Экспорт API** | ноды профиля, связанные пользователи, другие приложения | сессии сети пользователя, реального порта нет | `api.export` |
| **Слушающий сокет** | произвольный клиент в локальной сети или интернете | настоящий TCP-порт хоста | `net.listen:<port>` |

Первый механизм — основной и рекомендуемый. Именно он имеется в виду, когда говорится, что
можно обратиться напрямую к конкретному устройству и вызвать API приложений и сервисов,
которые его экспортировали.

### Экспорт API приложением

```text
Приложение на ноде A                       Приложение или UI на ноде B
        │                                            │
        │ export("library", handler)                 │ call(node=A, "library", req)
        ▼                                            ▼
   api-registry ◀────── сессия сети пользователя ──── rpc-service
        │                                    (аутентифицирована, зашифрована)
        ▼
   активация компонента, проверка прав вызывающего
```

Свойства:

- **Порт не открывается.** Вызов идёт по уже установленной аутентифицированной сессии между
  нодами, поэтому экспорт работает за NAT, в сотовой сети и на Android, где прослушивание
  сокета ограничено платформой.
- **Идентичность вызывающего известна.** Она выводится из сессии ноды и delegation-токена,
  а не из содержимого запроса. Обработчик получает `caller` с profile, node, package и не
  может быть обманут подделкой заголовка.
- **Экспорт объявляется в манифесте.** Набор методов, их схемы, требуемые права вызывающего
  и допустимая область — свои ноды, связанные пользователи, другие пакеты на этой ноде.
- **Обработчик активируется по вызову.** Постоянно работающий процесс не требуется: вызов
  является событием активации worker, что согласуется с
  [отказом от пользовательских daemons](../03-apps/01-app-model.md).
- **Доступ проверяется дважды.** У вызывающего должно быть право обращаться к этому API,
  у принимающей ноды — собственное правило, разрешающее этому пакету обслуживать вызовы
  отсюда.

Контракт:

```wit
interface api-export {
  record exported-method {
    name: string,
    request-schema: string,
    response-schema: string,
    audience: audience,          // profile-nodes | linked-users | local-packages
  }
  record call-context {
    caller: caller,              // profile, node, package, component
    audience: audience,
    deadline-ms: duration-ms,
  }
  export: func(service: string, methods: list<exported-method>) -> result<_, error>;
  unexport: func(service: string) -> result<_, error>;
}

interface api-call {
  call: func(target: node-id, service: string, method: string,
             payload: list<u8>, deadline-ms: duration-ms) -> result<list<u8>, error>;
  call-profile: func(service: string, method: string,
                     payload: list<u8>, deadline-ms: duration-ms) -> result<list<u8>, error>;
}
```

`call-profile` адресует не ноду, а профиль: систему просят найти любую ноду, где этот
сервис доступен. Это форма, которой пользуется большинство приложений; адресация к
конкретной ноде нужна, когда важен именно ресурс этого устройства — оборудование, локальные
файлы, экран.

### Слушающий сокет

Отдельная возможность для сценариев, где клиентом является внешняя программа, не знающая о
K-OS: локальное веб-приложение, устройство умного дома, инструмент разработчика.

```text
capability net.listen:<port>       право занять порт на этой ноде
        ↓
http-server-driver                 приём соединений, лимиты, маршрутизация
        ↓
http protocol engine
        ↓
SocketAdapter::listen
```

Решения:

1. **Право привязано к ноде, а не к профилю.** Порт — ресурс конкретного устройства.
   Grant выдаётся на ноде, где приложение действительно должен слушать.
2. **Привилегированные порты недоступны.** Диапазон ниже 1024 не выдаётся приложениям.
3. **Область прослушивания объявляется явно**: только петлевой интерфейс, локальная сеть
   или все интерфейсы. По умолчанию — петлевой; выход в локальную сеть требует отдельного
   подтверждения, потому что делает приложение доступным соседям по Wi-Fi.
4. **Соединения не переживают компонент.** Сокет принадлежит execution; при остановке
   компонента слушатель закрывается. Долгоживущий приём — свойство системного сервиса, а не
   пользовательского кода.
5. **На Android возможность ограничена платформой** и возвращает `unavailable` в фоне. Это
   нормальное состояние, приложение обязано его обрабатывать.
6. **Публикация наружу не входит в возможность.** Открыть порт в интернет через
   маршрутизатор система приложению не даёт; выход наружу — решение пользователя на уровне
   сети, см. [NAT и достижимость](../06-network/10-nat-and-reachability.md).

## WebSocket client

```text
capability net.ws:<host>
        ↓
ws-client-driver                 кадрирование, ping/pong, лимиты сообщений
        ↓
http protocol engine             upgrade-запрос
        ↓
network-broker → SocketAdapter + TlsAdapter
```

Ключевое ограничение уже зафиксировано в каталоге: **соединение принадлежит вызвавшему
execution**. Worker, завершившийся после обработки события, теряет соединение. Это прямое
следствие модели жизненного цикла: система не обещает пользовательскому коду постоянно
живущий процесс.

Отсюда следует разделение сценариев:

| Сценарий | Механизм |
|---|---|
| UI открыт, нужен поток обновлений | `net.ws` из Web UI, соединение живёт вместе с view |
| нужна подписка, переживающая закрытие UI | системный брокер: `mqtt` или durable-подписка, активирующая worker |
| нужен обмен внутри сети пользователя | экспорт API и события, а не WebSocket |

Приложение, пытающееся удержать WebSocket ради фоновой подписки, работает против модели;
документ фиксирует это явно, чтобы такая попытка не считалась дефектом системы.

## WebSocket server

Симметрично HTTP-серверу, различаются те же два механизма.

**Внутри сети пользователя** постоянный двусторонний обмен выражается не WebSocket, а
подпиской на события и realtime-каналом: сессия между нодами уже существует, мультиплексирует
потоки и переживает смену транспорта, поэтому заворачивать в неё ещё один WebSocket
бессмысленно. См. [события](../03-apps/10-events-and-push.md) и
[realtime](../03-apps/09-realtime.md).

**Для внешних клиентов** WebSocket-сервер существует как надстройка над слушающим сокетом:

```wit
interface ws-server {
  resource session {
    send:    func(msg: message) -> result<_, error>;
    receive: func() -> result<option<message>, error>;
    close:   func(code: u16) -> result<_, error>;
    peer:    func() -> peer-info;
  }
  resource acceptor {
    accept: func() -> result<option<session>, error>;
    close:  func();
  }
  listen: func(port: u16, path: string, opts: listen-opts) -> result<acceptor, error>;
}
```

Правила: право `net.listen:<port>` то же самое, число одновременных сессий квотируется,
сессии закрываются вместе с execution, аутентификация внешнего клиента — задача приложения,
и система не считает такого клиента доверенным ни в каком смысле.

## Файловая система

Файлы — единственная из трёх базовых возможностей, где приложение работает не с внешним
миром, а с реплицируемым состоянием профиля. Поэтому вертикаль устроена иначе.

```text
capability files.app.* / files.user.* / files.external.<mount>.*
        ↓
vfs-service                 единое дерево профиля, идентичность файла, состояния
        ├── storage-driver  атомарная публикация, дескрипторы, квоты, watch
        │        ↓ FileSystemAdapter          приватный каталог ноды
        ├── blob-driver     чанки, дедупликация, вытеснение, сборка мусора
        │        ↓ FileSystemAdapter
        └── external-mount-driver
                 ↓ ExternalStorageAdapter    внешние каталоги, отзываемый доступ
        ↕
sync-service                репликация метаданных, передача содержимого
```

### Три разных пространства

| Пространство | Путь | Кто владеет | Реплицируется |
|---|---|---|---|
| файлы приложения | `/data/<pkg>/files/` | приложение | да |
| пользовательские файлы | `/user/` | пользователь, доступ по праву | да |
| внешние монтирования | `/mnt/<mount-id>/` | хостовая ОС | нет, только факт монтирования |

Приложение по умолчанию видит только своё поддерево. Доступ к `/user/` выдаётся правом,
доступ к внешнему каталогу — только через явное действие пользователя в системном picker,
и только тому приложению, которое этот доступ запросило.

### Решения

1. **Метаданные и содержимое разделены.** Дерево видно на всех нодах, содержимое
   материализуется по политике. Состояние файла (`materialized`, `metadata-only`,
   `fetching`, `evicted`, `unavailable`, …) — часть публичного API, а не деталь реализации.
2. **Идентичность файла не зависит от пути.** Переименование и перемещение — операции над
   метаданными; открытые handles остаются валидными.
3. **Публикация атомарна.** `commit` опирается на `sync_data` и атомарное переименование
   платформы; частично записанный файл не наблюдаем ни локально, ни в репликации.
4. **Ожидание всегда ограничено.** Режим `auto` материализует содержимое в пределах
   deadline; скрытая блокирующая загрузка без deadline не допускается ни в одном режиме.
5. **Конфликт не разрешается потерей данных.** Параллельная запись сохраняет обе версии;
   выбор делает приложение или пользователь.
6. **Отзыв доступа платформой — нормальное состояние.** Внешнее монтирование может
   исчезнуть в любой момент, что выражается `revoked`, а не `io`.

Подробности контракта — в [VFS](../05-storage/03-vfs.md) и
[blob store](../05-storage/04-blobs-and-materialization.md).

## Сводка прав базового стека

| Возможность | Право | Область | Делегируемо |
|---|---|---|---|
| HTTP-запрос | `net.http:<host>` | хост | да |
| WebSocket-клиент | `net.ws:<host>` | хост | нет |
| Экспорт API приложения | `api.export` | сервис и аудитория | — |
| Вызов API другой ноды | `api.call:<service>` | сервис | по определению удалённое |
| Слушающий сокет | `net.listen:<port>` | порт на конкретной ноде | нет |
| Файлы приложения | `files.app.read-write` | своё поддерево | да |
| Пользовательские файлы | `files.user.read`, `files.user.write` | `/user/` | да |
| Внешний каталог | `files.external.<mount>.read|write` | монтирование | да |

## Правила для новых стеков

Любая возможность, добавляемая позже, обязана следовать образцу:

1. Сначала типизированный контракт в каталоге, потом вопрос о реализации.
2. Протокол реализуется переносимо; платформенным остаётся только примитив под ним.
3. Право имеет область: хост, порт, монтирование, устройство. Право без области — исключение,
   требующее обоснования.
4. Ресурс принадлежит execution и освобождается вместе с ним.
5. Долгоживущее состояние принадлежит системному сервису, а не пользовательскому коду.
6. Недоступность выражается явно и сопровождается списком нод, где возможность есть.
7. Всё, что обращается наружу, делегируемо — либо в контракте объявлено, почему нет.
