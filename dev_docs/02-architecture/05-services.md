# Системные services

Статус: готов  
Назначение: разделить control plane и feature services, зафиксировать каталог сервисов,
правила их запуска, зависимостей и взаимодействия с компонентами приложений.

Связанные документы: [слои системы](./01-layers.md), [drivers](./04-drivers.md),
[загрузка системы](./07-boot.md), [базовый стек](./06-base-stack.md).

## Роль слоя

Service — системная функция, построенная поверх drivers и других services. Если driver
отвечает на вопрос «как безопасно владеть ресурсом», то service — на вопрос «какую
системную функцию предоставить»: хранилище, синхронизацию, планирование, уведомления,
маршрутизацию вызовов.

Отличие от driver, определяющее принадлежность кода:

| Признак | Driver | Service |
|---|---|---|
| предмет | конкретный ресурс платформы | прикладная функция |
| состояние | только время жизни процесса | durable, переживает перезапуск |
| знание о профиле | нет | да: ноды, пакеты, права |
| знание о сети | нет | да, там где функция распределённая |

Правило проверки: если компонент обязан восстанавливать состояние после перезапуска ноды,
это service, а не driver.

## Control plane и feature services

Services делятся на две группы с разными правилами запуска и зависимостей.

**Control plane** — то, от чего зависит сама проверка прав. Эти компоненты не могут быть
capability-gated и не вызывают feature services:

| Компонент | Ответственность |
|---|---|
| node identity | ключ ноды, его использование, привязка к устройству |
| key storage | эпохи ключей данных, доступ к платформенному хранилищу |
| profile control log | состав профиля, роли нод, grants, установленные пакеты |
| capability registry | известные capabilities, их версии и доступность здесь |
| permission evaluation | решение о выдаче права конкретному execution |
| package registry | какие пакеты и версии установлены в профиле |
| logging и crash reporting | журнал, доступный до подъёма остальной системы |

**Feature services** — системные функции, доступные компонентам через capability API:

| Service | Ответственность |
|---|---|
| `vfs-service` | единое дерево файлов профиля, состояния и материализация |
| `storage-service` | namespaces приложений, реплицируемые типы, подписки на изменения |
| `blob-service` | содержимое файлов, чанки, дедупликация, вытеснение |
| `sync-service` | репликация состояния и передача содержимого между нодами |
| `net-service` | сессии между нодами, маршрутизация, выбор транспорта |
| `rpc-service` | вызовы между нодами, делегирование, экспортированные API приложений |
| `event-service` | шина событий профиля, подписки, дедупликация доставки |
| `notification-service` | уведомления пользователю и выбор устройства показа |
| `scheduler-service` | активация компонентов, расписания, фоновые leases |
| `app-runtime` | жизненный цикл компонентов, изоляция, capability bridge |
| `package-manager` | установка, материализация, обновление, откат |
| `device-service` | реестр подключённых устройств и маршрутизация обращений к ним |
| `secrets-service` | секреты приложений и профиля |
| `media-service` | разбор и преобразование медиа, выбор backend |
| `tools-service` | внешние инструменты: Git и подобные |
| `telemetry-service` | метрики и диагностика, доступные пользователю |

Различие между группами существенно не формально: попытка проверить право на запись в
журнал через сервис, который сам пишет журнал, даёт цикл. Порядок запуска в
[документе о загрузке](./07-boot.md) следует из этого разделения.

## Правила

1. **Control plane не вызывает feature services.** Обратное разрешено.
2. **Циклические зависимости запрещены** и разрываются событиями либо отложенной
   активацией, а не взаимными ссылками.
3. **Service не обращается к host adapter напрямую**, минуя driver. Исключение — сервисы
   control plane, которым нужны `ClockAdapter`, `RandomAdapter` и `SecureKeyStoreAdapter`
   до подъёма слоя драйверов.
4. **Service объявляет свой контракт версионированно.** Компоненты находят сервисы через
   реестр по контракту, а не по конкретному типу реализации.
5. **Service не зависит от наличия UI.** Ядро собирается и работает headless; отсутствие
   системной оболочки — штатное состояние, а не деградация.
6. **Долговечное состояние сервиса принадлежит ему**, а не драйверу и не приложению, и
   восстанавливается при старте ноды.

## Взаимодействие с компонентами

Компоненты приложения не получают ссылку на сервис. Они обращаются к capability API, за
которым системный gateway восстанавливает идентичность вызывающего, проверяет право и
направляет вызов нужному сервису.

```rust
let media = ctx.services().require::<MediaService>(">=1.2")?;   // внутри ядра
let result = media.transcode(request).await?;
```

Контракт не должен зависеть от нестабильного Rust ABI. Для разных границ используются:
WIT и Component Model — для workers, сериализуемые versioned messages — для IPC и RPC,
генерируемый TypeScript API — для Web UI.

Локальный и удалённый вызовы могут иметь одинаковые типы запроса и ответа, но API обязан
сохранять сетевую семантику: deadline, отмену, недоступность узла, повтор и идемпотентность.

## Сервисы и распределённость

Часть сервисов работает только локально, часть по определению распределена:

| Класс | Сервисы | Свойство |
|---|---|---|
| локальные | `app-runtime`, `blob-service`, `media-service`, `secrets-service` | состояние ноды, работают офлайн полностью |
| распределённые | `sync-service`, `rpc-service`, `event-service`, `scheduler-service` | учитывают состав профиля и доступность нод |
| смешанные | `vfs-service`, `storage-service`, `device-service`, `notification-service` | локальный доступ всегда, полнота — по доступности сети |

Смешанный класс — источник большинства ошибок проектирования: приложение видит локальный
ответ, но полнота ответа зависит от того, какие ноды сейчас на связи. Поэтому такие сервисы
обязаны возвращать признак полноты и давность сведений, а не молчаливо отдавать частичный
результат как окончательный.

## Наблюдаемость

Метрики собираются на том слое, который владеет соответствующим знанием, и не дублируются
между слоями:

| Слой | Что измеряет |
|---|---|
| driver | технические метрики ресурса, см. [drivers](./04-drivers.md) |
| service | метрики операций: количество, задержка, доля ошибок |
| application runtime | метрики жизненного цикла компонентов |

Приложению доступна только разрешённая ему часть диагностических данных. Требования к самим
контрактам — типизированные ошибки, deadline, отмена, backpressure, trace ID и журналирование
без утечки секретов — общие для всей системы и зафиксированы в
[правилах каталога](../04-capabilities/02-catalog/00-index.md); сервис не вправе предлагать
контракт слабее.

## Отличие от компонентов приложения

Service — runtime-роль системы, а не единица установки для пользователя. Пользовательский
backend входит в пакет приложения как worker и не становится системным сервисом из-за того,
что работает в фоне: он не получает системных прав, не участвует в загрузке ядра и
подчиняется квотам и активации.

Обратное тоже верно: системный сервис не устанавливается и не удаляется пользователем.
Расширение системы новым оборудованием происходит на слое adapters, а не добавлением
сервиса, см. [расширяемость](./08-extensibility.md).
