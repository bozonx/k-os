# Критерии корректности архитектуры

Статус: перенесено из прежних документов, требует ревизии.  
Назначение: перечислить проверяемые условия, которым обязано удовлетворять архитектурное решение, и краткое распределение ответственности между слоями.

Связанные документы: [принципы](../01-overview/03-principles.md), [тестируемость](../12-testing/01-determinism-and-simulation.md).


Архитектурное решение считается совместимым с этим документом, если:

- приложение не может обойти capability API;
- package может быть установлен в profile без требования исполнять каждый component на каждом node;
- несовместимый или недоступный component получает явное placement state;
- UI можно закрыть без обязательной остановки разрешённой фоновой задачи;
- worker можно остановить и позже возобновить из checkpoint;
- host adapter можно заменить другой платформенной реализацией без изменения service API;
- один ресурс можно безопасно разделить между несколькими приложениями через driver;
- данные явно относятся к local, replicated, derived или secret классу;
- выполнение имеет явный scope относительно устройств пользователя;
- обновление package не расширяет права без подтверждения;
- приложение без собственного backend может полноценно работать через стандартное API;
- добавление backend не требует отдельной установки service пользователем;
- ядро собирается и проходит тесты без `tauri` и без системной оболочки;
- любое обращение к внешнему миру проходит через host adapter, имеющий mock-реализацию;
- несколько экземпляров ядра запускаются в одном процессе и синхронизируются через симулированную сеть;
- отсутствие capability на устройстве выражается явным `unavailable`, а не деградацией поведения;
- внешний инструмент вызывается через типизированный контракт, не зависящий от способа его исполнения;
- файл имеет стабильную идентичность, не зависящую от пути;
- нематериализованное содержимое файла является нормальным состоянием, обрабатываемым API.


## Краткое распределение ответственности


```text
Host adapter       — как выполнить платформенную операцию.
Driver             — как безопасно владеть и делить ресурс.
Control plane      — кто входит в профиль и что кому разрешено.
Service            — какую системную функцию предоставить.
Package            — что устанавливает пользователь.
Web UI             — что работает во view внутри единственного окна.
Worker             — backend приложения, активируемый runtime.
Capability API     — единственный путь к защищённым возможностям.
Storage namespace  — семантическое место хранения состояния.
VFS                — единое имя данных на всех устройствах профиля.
Placement          — где допустимо и предпочтительно исполнять component.
Node role          — что устройство вообще способно и обязано делать.
```

Главное следствие этой модели: frontend и backend могут принадлежать одному приложению, но имеют независимый жизненный цикл. Backend оформляется как worker внутри package, а не как отдельно устанавливаемый пользовательский service. Системные services остаются частью доверенной платформы K-OS.
