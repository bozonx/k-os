# Профиль, ноды и их роли

Статус: готов  
Назначение: определить профиль пользователя, ноду, роли нод, состояния установки и размещения компонентов.

Связанные документы: [сеть пользователя](../06-network/01-overview.md), [подключение нод](../06-network/09-network-lifecycle.md), [облачная нода](../09-clients/04-cloud-node.md), [устройства и IoT](../08-devices/01-model.md), [VFS](../05-storage/03-vfs.md), [размещение и исполнение](../03-apps/08-placement-and-execution.md).


`Profile` представляет персональную среду пользователя: набор установленных packages, grants, replicated namespaces и доверенных устройств.

`Node` — конкретная установка K-OS на устройстве. Node имеет собственную криптографическую identity, роль, набор доступных capabilities, platform constraints, локальное состояние и статус доступности. Роли нод перечислены ниже.

`Package installation` — desired state профиля: пользователь считает package установленным в своей среде. Это не означает, что все его артефакты обязаны быть загружены и все components способны исполняться на каждом node.

`Placement` — решение о том, где может и должен исполняться component. Для component различаются состояния:

```text
available     package известен профилю
materialized  необходимые артефакты присутствуют на node
compatible    node удовлетворяет требованиям component
placed        runtime выбрал node для исполнения
running       существует конкретный execution
```

UI приложения может быть доступен на Android и desktop, а hardware worker — только на Linux node с требуемым устройством. Runtime обязан представлять такую ситуацию явно, а не имитировать локальную доступность компонента.


## Роли нод

Профиль состоит из нод разных ролей. Роль объявляется при enrollment и записывается в control log.

**Роль отвечает на один вопрос: владеет ли нода ключами данных профиля и что ей позволено
исполнять.** Сколько состояния нода хранит — это не роль, а [политика хранения](#политика-хранения):
две настройки, которые нельзя смешивать, потому что первая определяется физической
защищённостью устройства и меняется только переподключением, а вторая — объёмом диска и
меняется галочкой.

| Роль | Ключи профиля | UI приложений | Исполнение workers | Владеет оборудованием | Назначение |
|---|---|---|---|---|---|
| `device` | да | да | да | да | ноутбук, десктоп, телефон |
| `cloud` | да | нет | да | нет | всегда доступное хранилище, синхронизация, фоновые сервисы |
| `appliance` | нет | нет | только собственные драйверы | да | физически доступное устройство с подключённым оборудованием |
| `relay` | нет | нет | нет | нет | шифрованный транзит и хранение непрозрачных данных |

### Device node

Полноценный узел с системным UI. Может быть офлайн, приостановлен, выключен. Не предполагается, что device node доступен в произвольный момент.

### Cloud node

Headless-нода без Tauri, WebView и системного UI: полноправный доверенный член профиля,
хранящий полную реплику состояния и исполняющий фоновые компоненты. Она намеренно **не
запускает UI приложений**: удалённый доступ к интерфейсу не нужен, потому что приложение и
его состояние реплицированы и запускаются локально на том устройстве, которое пользователь
взял в руки. Подробно — в [документе об облачной ноде](../09-clients/04-cloud-node.md).

### Appliance node

Узел, назначение которого — подключённое оборудование, а не данные: одноплатный компьютер с
датчиками и реле, контроллер в щитке, устройство в гараже или на даче.

Ключевое свойство: **appliance не владеет ключами данных профиля.** Он участвует в
[реестре устройств](../08-devices/01-model.md) и принимает команды к своему оборудованию
через отдельный узкий канал с собственной парой ключей, но не может прочитать ни файлы, ни
базы приложений, ни control log целиком.

Причина введения роли: до неё выбор был двоичным и оба варианта неверны для этого случая.
Полноправная нода в незапертом помещении означает, что кража железки отдаёт все данные
профиля. Relay не имеет ключей, но и не исполняет ничего — управлять реле он не может.
`appliance` закрывает ровно этот разрыв: последствие компрометации ограничено оборудованием.

Свойства:

- получает не control log, а **подтверждение членства с ограниченным сроком** — тот же
  механизм, что у relay, см. [control log](../06-network/03-control-log.md);
- публикует дескриптор своих устройств и их состояние; состояние устройств не является
  данными профиля и передаётся по каналу управления устройствами;
- исполняет только драйверы своего оборудования и объявленные для него системные сервисы.
  Воркеры приложений на нём не размещаются: приложение, которому нужно оборудование,
  обращается к устройству по идентификатору с любой ноды;
- не хранит реплику состояния профиля, поэтому политика хранения к нему неприменима;
- отзывается так же, как любая нода: записью в control log, после чего подтверждения
  членства перестают выдаваться.

Полноправная нода с оборудованием остаётся допустимой и остаётся ролью `device`: домашний
сервер в запертой квартире не требует понижения прав. Выбор между `device` и `appliance` —
это ответ на вопрос «что случится, если устройство унесут», и он задаётся при подключении.

### Relay node

Узел без ключей профиля. Видит только зашифрованные op log records и blobs и метаданные маршрутизации: profile ID в псевдонимизированной форме, размеры, тайминги.

Relay:

- ретранслирует сессии между nodes за NAT;
- может хранить зашифрованные blobs и op log для доставки офлайн-узлам;
- не может исполнять workers, читать данные и участвовать в координации;
- обязан проверять членство обращающейся ноды, чтобы отозванный node не мог продолжать выкачивать данные. Сам control log relay не получает: нода предъявляет ему подтверждение членства с ограниченным сроком, см. [control log](../06-network/03-control-log.md).

## Политика хранения

Ортогональна роли и настраивается пользователем в любой момент. Применима только к нодам с
ключами данных, то есть к `device` и `cloud`.

| Политика | Реплицируемые данные | Содержимое файлов | Типичный носитель |
|---|---|---|---|
| `full-mirror` | всё | полное зеркало | десктоп, облачная нода, домашний сервер |
| `working-set` | всё | по квоте, вытеснение по давности | телефон, планшет, ноутбук с малым диском |
| `system-only` | состояние профиля и коллекции размещённых здесь компонентов | ничего, кроме затребованного | headless-нода в шкафу, узкоспециальное устройство |

Смысл разделения: вопрос «сколько места нода тратит» пересматривается по мере заполнения
диска и решается галочкой, а вопрос «может ли нода читать данные» — решение о доверии,
принимаемое один раз при подключении и меняемое только переподключением. Слияние их в одну
настройку приводит к тому, что освобождение места на устройстве незаметно меняет модель
безопасности.

`system-only` опирается на [частичную репликацию](../05-storage/02-database.md): нода
подписана на коллекции, объявленные компонентами, которые на ней размещены, и на состояние
профиля, без которого невозможны проверка прав и маршрутизация. Дом пользователя такая нода
не хранит и в режиме `members-only` может не хранить даже его индекс.

Инвариант [минимума реплик](../05-storage/03-vfs.md) действует поверх политики: набор
политик, при котором содержимое остаётся в одном экземпляре, допустим, но показывается
пользователю как незакрытый риск.

### Node capability descriptor

Каждый node публикует в replicated state описание своих возможностей: платформа, архитектура, роль, политика хранения, доступные capabilities, наличие оборудования, класс питания, метрика сети, объём хранилища, background-гарантии.

Дескриптор является входом для [placement](../03-apps/08-placement-and-execution.md) и обновляется при изменении состояния устройства. Он реплицируется как обычное replicated state, поэтому placement можно вычислить и на офлайн-узле по последнему известному состоянию — с явной пометкой staleness.
