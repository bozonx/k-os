# Drivers и resource brokers

## Роль слоя

Driver, или resource broker, превращает host adapter в управляемый системный ресурс.
Adapter отвечает на вопрос «как выполнить операцию платформы», driver — на вопрос «как
безопасно владеть ресурсом и делить его между потребителями».

```text
Приложение ──запрос──▶ capability gateway ──▶ driver ──▶ host adapter ──▶ ОС
                          ▲                     │
                    проверка прав          владение, очередь,
                    и выдача handle        квоты, retry, метрики
```

Driver — **не устанавливаемый компонент**. Драйверы интегрированы в систему и поставляются
вместе с ядром. Это осознанное ограничение: от корректности мультиплексирования, отзыва
handles и учёта квот зависит изоляция всех приложений, поэтому в этом слое не появляется
внешний код. Расширять систему новым оборудованием можно на слое adapters через
[платформенное расширение](./08-extensibility.md); политику владения ресурсом при этом
по-прежнему применяет системный driver.

## Обязанности

Driver отвечает за:

- создание, переиспользование и освобождение ресурсов;
- владение платформенным дескриптором и его единственность;
- мультиплексирование между потребителями и справедливость доступа;
- очереди, backpressure, rate limits и admission control;
- reconnect, retry, timeout и circuit breaking;
- учёт квот и их применение;
- выдачу capability handles и проверку их валидности, scope и владельца;
- сбор технических метрик ресурса;
- корректное поведение при исчезновении adapter или изменении его доступности.

Driver **не** отвечает за: интерпретацию манифеста пакета, решение о выдаче права,
семантику прикладного протокола и синхронизацию пользовательского состояния.

## Разделение с capability service

Решение о выдаче права принимает централизованный capability service на входе в системный
API. Driver не читает манифест и не интерпретирует пользовательские grants.

При этом driver обязан повторно проверять ограничения выданного handle: владельца, scope,
срок жизни, признак отзыва. Это defense-in-depth и защита конкретного ресурса на случай
дефекта на верхнем уровне:

```text
gateway  → «этому execution разрешено net.http:api.example.com»  → выдаёт handle
driver   → «этот handle принадлежит этому execution, не отозван,
            запрошенный хост входит в scope»                     → выполняет операцию
```

Односторонней проверки недостаточно: gateway защищает от отсутствия права, driver — от
использования чужого или устаревшего handle.

## Модель handle

Приложение никогда не получает прямую ссылку на driver. Оно получает непрозрачный handle:

```rust
let connection = ctx.capabilities().http().connect(options).await?;
```

Handle связан с: profile ID, node ID, package ID, component ID, execution ID, набором
выданных операций, scope и временем жизни владельца.

| Событие | Что происходит с handle |
|---|---|
| завершение execution-владельца | закрывается, ресурс возвращается в pool |
| перезагрузка или навигация Web UI | вся сессия и её handles отзываются |
| отзыв grant пользователем | handle переходит в `revoked` немедленно |
| обновление пакета с изменением прав | handles предыдущей версии отзываются |
| исчезновение adapter | `revoked` с причиной, а не бесконечное ожидание |
| превышение квоты | операции возвращают `quota-exceeded`, handle остаётся валидным |

Свойства: непрозрачность для приложения, идемпотентное освобождение, невозможность передачи
другому пакету иначе как через явный системный механизм, ошибка `revoked` при использовании
после отзыва. Handle не является ёмкостью для хранения состояния приложения: перезапуск
компонента означает получение нового handle, и код обязан это допускать.

## Мультиплексирование и справедливость

Один физический ресурс обслуживает нескольких потребителей. Правила:

1. **Изоляция по потребителю.** Очередь, лимиты и учёт ведутся по паре
   (package, component), а не суммарно по ресурсу. Одно приложение не может исчерпать
   очередь другого.
2. **Ограниченные очереди.** Очередь имеет предел; при его достижении новые запросы получают
   `quota-exceeded` с `retry-after`, а не встают в неограниченный список. Неограниченная
   очередь — способ превратить нехватку ресурса в исчерпание памяти.
3. **Backpressure вместо буферизации.** Запись возвращает число принятых байт; driver не
   буферизует неограниченно.
4. **Приоритеты объявлены явно.** Системные операции control plane (репликация control log,
   enrollment) имеют приоритет над прикладными; в пределах прикладного класса действует
   справедливое распределение. Приложение не может повысить свой приоритет.
5. **Отмена освобождает место в очереди немедленно.** Отменённый запрос не удерживает слот
   до истечения deadline.

## Квоты

Права определяют доступ, квоты — объём использования уже выданного права. Оба механизма
применяет runtime, и они не заменяют друг друга.

| Ресурс | Единица квоты |
|---|---|
| соединения | число одновременных, частота установки |
| трафик | исходящий и входящий объём за окно, отдельно для metered-сетей |
| файлы | число открытых дескрипторов, объём записи, объём хранилища namespace |
| handles | число одновременно удерживаемых, суммарно и по виду |
| процессы | число одновременных, суммарное время CPU |
| активации | частота пробуждения фоновых компонентов |

Превышение возвращает `quota-exceeded` с указанием ресурса и времени восстановления.
Квота не является правом и не объявляется в манифесте: она задаётся политикой ноды и
зависит от класса устройства и режима питания.

## Устойчивость

- **Retry** выполняется только для операций, объявленных идемпотентными, и только в пределах
  объявленного бюджета. Retry никогда не выполняется автоматически для запросов с
  побочными эффектами без ключа идемпотентности.
- **Reconnect** относится к соединению, а не к операции: восстановление канала не означает
  повторной отправки прикладного запроса.
- **Circuit breaking**: после серии отказов одного назначения driver перестаёт занимать
  ресурс и возвращает `unavailable` сразу, экономя батарею и трафик. Состояние размыкателя
  наблюдаемо в метриках.
- **Deadline имеет приоритет над retry**: суммарное время с учётом повторов не превышает
  deadline вызывающего.
- **Исчезновение adapter** переводит выданные handles в `revoked` и не приводит к
  бесконечному ожиданию.

## Каталог драйверов

| Driver | Поверх adapters | Что делает |
|---|---|---|
| `network-broker` | `SocketAdapter`, `TlsAdapter`, `NetworkInfoAdapter` | сокеты, пул соединений, DNS, TLS, учёт трафика, metered-политика |
| `http-client-driver` | `network-broker` | HTTP-семантика, пул keep-alive, редиректы под проверкой прав |
| `http-server-driver` | `network-broker` | прослушивание портов, маршрутизация к экспортированным API |
| `ws-client-driver` | `network-broker` | WebSocket-соединение, кадрирование, ping/pong |
| `ws-server-driver` | `http-server-driver` | приём upgrade-запросов, пул сессий, лимит соединений |
| `mqtt-driver` | `network-broker` | удержание подписок вне жизни worker, durable-доставка |
| `storage-driver` | `FileSystemAdapter` | атомарная публикация, дескрипторы, квоты записи, watch |
| `external-mount-driver` | `ExternalStorageAdapter` | монтирования, отзыв доступа платформой, изоляция по mount-id |
| `blob-driver` | `FileSystemAdapter` | чанки, дедупликация, вытеснение, сборка мусора |
| `key-driver` | `SecureKeyStoreAdapter` | владение ключами, ограничение операций, аудит подписей |
| `process-driver` | `ProcessAdapter` | группы процессов, потоки ввода-вывода, обязательный timeout |
| `media-driver` | `MediaCaptureAdapter` и внешние backends | очередь задач транскодирования, выбор backend, лимит нагрузки |
| `ble-driver` | `BluetoothLeAdapter` | сессии BLE, разделение сканирования между потребителями |
| `gpio-driver` | `GpioAdapter` | единственный владелец линии, режимы, прерывания |
| `serial-driver` | `SerialAdapter` | эксклюзивный доступ к порту, скорость, буферы |
| `notification-driver` | `NotificationAdapter` | дедупликация, частота, группировка |
| `input-driver` | `InputAdapter` | синтез ввода только для управляющих сценариев, аудит |

Драйверы могут зависеть друг от друга: `ws-server-driver` работает поверх
`http-server-driver`, тот — поверх `network-broker`. Запрещены только обратные зависимости
и обращение driver к services.

### Различие эксклюзивных и разделяемых ресурсов

| Класс | Примеры | Модель владения |
|---|---|---|
| разделяемый | сокеты, файлы, HTTP-соединения | одновременный доступ, изоляция по потребителю |
| эксклюзивный | линия GPIO, последовательный порт, камера | один владелец, остальным `unavailable` с указанием владельца |
| арендуемый | линия GPIO под управлением фоновой задачи | владение через lease с fencing token |

Для эксклюзивных ресурсов driver обязан сообщать, кто владелец, чтобы UI мог показать
пользователю причину отказа, а не абстрактную ошибку. Освобождение эксклюзивного ресурса
при аварийном завершении владельца обязательно и проверяется тестом.

## Жизненный цикл driver

```text
1. Инициализация   получает ссылки на adapters и политику ноды
2. Готовность      объявляет предоставляемые capabilities и их состояние
3. Работа          выдаёт handles, обслуживает операции, ведёт учёт
4. Деградация      adapter стал unavailable → новые запросы отклоняются,
                   выданные handles отзываются с причиной
5. Остановка       закрытие в порядке, обратном инициализации;
                   ожидание завершения операций в пределах grace-периода
```

Driver не переживает перезапуск процесса: все handles после старта ноды новые. Долговечное
состояние (durable-подписки, незавершённые задачи) принадлежит services, а не драйверам, и
восстанавливается из хранилища.

## Метрики и наблюдаемость

Driver собирает технические метрики ресурса: число открытых соединений и handles, длина
очереди, задержка обслуживания, число отказов по квоте, состояние circuit breaker, объём
переданных данных с разделением на metered и unmetered.

Метрики размечаются по (package, component), что делает наблюдаемым приложение,
злоупотребляющее выданными правами в пределах квот. Приложению доступна только та часть
диагностики, которая относится к нему самому; сводная картина по ноде — системному UI.

## Проверяемые критерии

- один ресурс безопасно разделяется между несколькими приложениями;
- завершение владельца всегда освобождает ресурс, включая аварийное;
- отзыв grant делает выданный handle непригодным немедленно;
- ни один driver не читает манифест и не принимает решение о выдаче права;
- очередь любого driver ограничена, и переполнение выражается `quota-exceeded`;
- исчезновение adapter не приводит к зависанию операции;
- эксклюзивный ресурс не может быть захвачен двумя владельцами одновременно;
- метрики позволяют отнести потребление ресурса к конкретному пакету.
