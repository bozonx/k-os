# Мобильный клиент

Статус: готов  
Назначение: определить формы поставки K-OS на мобильных платформах, режим launcher и
ограничения фонового исполнения, которые из них следуют.

Связанные документы: [платформы](./01-platforms.md),
[системная оболочка](./05-system-shell.md), [десктопный клиент](./02-desktop.md),
[события и push](../03-apps/10-events-and-push.md),
[размещение и исполнение](../03-apps/08-placement-and-execution.md).

## Поддерживаемые платформы

Поддерживаются **Android** и **мобильные Linux-системы**. Apple-платформы в обозримый объём
работ не входят и не влияют на решения.

Мобильные Linux-системы (postmarketOS, Mobian и подобные) с точки зрения ядра являются
десктопным Linux с другим форм-фактором: те же host adapters, тот же демон, те же ярлыки
`.desktop`. Отличия сводятся к оформлению оболочки под сенсорный ввод и к более жёсткому
энергосбережению. Поэтому основная специфика этого документа относится к Android.

## Две формы поставки

| Вариант | Что видит пользователь | Статус |
|---|---|---|
| Единое приложение | одно приложение K-OS, внутри которого работают все приложения среды | базовый, входит в первую версию |
| Launcher | K-OS установлен домашним экраном, приложения запускаются по отдельности | дополнительный режим |

### Единое приложение

Одна активность, внутри неё представление оболочки и представление приложения — та же
композиция, что и в режиме единого окна на десктопе. Навигация: launcher оболочки,
системная кнопка «назад» обрабатывается сначала приложением, затем оболочкой.

### Launcher

K-OS регистрируется как домашний экран и показывает установленные в профиле приложения
наравне с приложениями Android. Это возможно в рамках платформы, но с существенными
уточнениями:

1. **Каждое приложение K-OS — не отдельное приложение Android.** Значок на домашнем экране
   и в списке — это ярлык, открывающий ту же активность K-OS с указанием пакета. Установка
   приложения в профиль не порождает установку APK и не требует подтверждений системы.
2. **Изоляция сохраняется**, потому что она обеспечивается origin и capability gateway, а
   не разделением процессов Android. Запуск приложения ярлыком и запуск из launcher
   оболочки — один и тот же путь.
3. **Правило «одна нода — один процесс ядра» соблюдается**: активности являются
   представлениями одного сервиса, а не отдельными нодами.
4. **Режим не является обязательным.** Пользователь, не сделавший K-OS домашним экраном,
   получает ровно ту же среду в варианте единого приложения; отличается только точка входа.
5. **Ограничения платформы принимаются как есть.** Если версия Android не даёт нужного
   поведения ярлыков, режим объявляется недоступным на этой версии, а не имитируется.

Оболочка в режиме launcher дополнительно отвечает за то, что обычно делает домашний экран:
показ приложений Android, виджеты платформы не поддерживаются, уведомления остаются
системными.

## Фоновое исполнение

Главное отличие мобильного клиента от десктопного: **платформа не гарантирует фоновую
работу**, и модель системы обязана это выражать, а не обходить.

| Задача | Механизм на Android | Что обещано |
|---|---|---|
| синхронизация при открытом приложении | обычная работа сервиса | полная |
| синхронизация при свёрнутом приложении | ограниченное окно, затем остановка | ничего не обещано |
| длительная синхронизация по желанию пользователя | foreground service с постоянным уведомлением | пока пользователь не остановит |
| периодические задачи | планировщик платформы | срабатывание не в точное время |
| реакция на входящее событие | пробуждение по сети или push | зависит от режима энергосбережения |

Отсюда правила:

- `BackgroundSchedulerAdapter` отображает платформенные возможности в общую модель
  планировщика, а не имитирует непрерывное исполнение;
- lease на фоновую работу выражает разрешение и запрошенный бюджет, но не обещание
  запуска в точное время;
- планировщик профиля предпочитает размещать фоновые компоненты на нодах с питанием от
  сети: телефон — последний кандидат для тяжёлой работы, а не первый;
- приложение, спроектированное в предположении «мой воркер работает всегда», сломается на
  мобильном устройстве, и документация приложения обязана это учитывать.

## Уведомления и push

Событие может прийти в момент, когда процесс выгружен. Решение о доставке принимает
выбранный обработчик событий профиля, см.
[события и push](../03-apps/10-events-and-push.md).

**Базовая поставка не зависит от проприетарных push-сервисов.** Причина: зависимость от
внешнего сервиса противоречит обещанию работы без интернета и без чужого сервера. Вместо
этого используются:

- удержание соединения, пока приложение активно или выдан foreground-lease;
- пробуждение по локальной сети, когда телефон и другая нода в одной сети;
- периодическая проверка планировщиком платформы;
- доставка при следующем открытии приложения.

Поддержка платформенного push-сервиса возможна как **необязательный модуль сборки** для
тех, кому нужна мгновенная доставка при выгруженном процессе. Он не входит в базовую
поставку и его отсутствие не ломает ни один сценарий, а лишь увеличивает задержку.

## Хранилище и файлы

- приватное хранилище приложения используется для данных ноды и материализованного
  содержимого; квоты жёстче, чем на десктопе, поэтому selective sync по умолчанию
  агрессивнее вытесняет;
- доступ к пользовательским каталогам выражается идентификаторами SAF и может быть отозван
  платформой в любой момент; adapter представляет это явно, не имитируя POSIX-семантику;
- телефон по умолчанию не является полной репликой содержимого файлов: дерево видно
  целиком, содержимое подтягивается по требованию.

## Сеть и энергия

- выбор канала учитывает metered-статус: объёмная передача в сотовой сети откладывается,
  если пользователь не запросил её явно;
- локальная сеть предпочтительна: синхронизация с домашними устройствами по Wi-Fi дешевле
  и быстрее, чем через облачную ноду;
- BLE используется для обнаружения и подключения устройств, но не для передачи содержимого;
- входящие соединения в сотовой сети недоступны, поэтому телефон обращается наружу сам, а
  экспортированные API приложений работают через сессии сети профиля, а не через
  слушающий сокет.

## Что недоступно

| Возможность | Состояние на Android |
|---|---|
| `process.exec`, `process.shell` | `unavailable` |
| `net.listen` в фоне | `unavailable`, на переднем плане — ограниченно |
| `gpio.line`, `serial.port` | `unavailable` |
| `system.power` | `unavailable` |
| управление вводом и захват экрана другой ноды | доступно как инициатор, недоступно как цель |

Недоступность — нормальное состояние: приложение получает `unavailable` со списком нод, где
возможность есть, и предлагает выполнить операцию там.

## Проверяемые критерии

- среда одинаково работает в варианте единого приложения и в режиме launcher;
- изоляция приложений не зависит от выбранного варианта поставки;
- ни один сценарий базовой поставки не требует проприетарного push-сервиса;
- фоновые обещания API совпадают с тем, что платформа действительно даёт;
- телефон может участвовать в профиле, не будучи полной репликой содержимого файлов;
- отсутствующие возможности выражаются `unavailable` и списком альтернативных нод.

## Открытые вопросы

- насколько режим launcher устойчив к изменениям политики Android между версиями;
- совпадает ли способ размещения контейнера приложения с десктопным решением — проверяется
  спайком, см. [открытые вопросы](../01-overview/05-open-questions.md);
- какой минимальный набор фоновых гарантий стоит объявлять в API, чтобы он выполнялся на
  всех поддерживаемых версиях Android.
