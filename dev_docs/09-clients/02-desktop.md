# Десктопный клиент

Статус: готов  
Назначение: определить формы запуска K-OS на настольных системах, роль демона, интеграцию
приложений в рабочий стол и связанные с этим уточнения модели окон.

Связанные документы: [системная оболочка](./05-system-shell.md),
[frontend приложения](../03-apps/04-frontend.md), [платформы](./01-platforms.md),
[изоляция](../10-security/01-isolation.md), [мобильный клиент](./03-mobile.md).

## Нода, процесс и окна

Уточнение модели, из которого следует всё остальное в этом документе:

> **Одна нода — один процесс ядра и один сеанс оболочки. Окна являются представлениями
> этого сеанса, а не отдельными нодами.**

Прежняя формулировка «одно окно на устройство» описывала не то ограничение, которое
действительно нужно. Существенно, что на устройстве работает единственное ядро, владеющее
ключами, соединениями, синхронизацией и планировщиком; сколько окон оно показывает — вопрос
формы поставки. Изоляция обеспечивается origin и capability gateway, а не количеством окон,
поэтому несколько окон её не ослабляют.

```text
Нода
└── процесс ядра (демон): ключи, сеть, синхронизация, планировщик, драйверы
    └── сеанс оболочки
        ├── окно 1: shell view + app view
        ├── окно 2: app view приложения, запущенного ярлыком
        └── трей: индикатор состояния, launcher, уведомления
```

## Два способа запуска

| Способ | Что видит пользователь | Что требуется |
|---|---|---|
| Единое окно | системная панель и приложение в одном окне | приложение K-OS |
| Интеграция в рабочий стол | каждое приложение — как отдельная программа системы | демон, ярлыки, приложение настроек |

**Способы совместимы и включаются независимо.** Это настройка ноды, а не взаимное
исключение: пользователь может держать основное окно K-OS и одновременно иметь ярлыки
часто используемых приложений. Оба способа обслуживает один демон, поэтому состояние,
синхронизация и фоновые задачи у них общие.

### Единое окно

Основной режим, совпадающий по модели с мобильным клиентом: окно содержит представление
оболочки и представление активного приложения. Переключение приложений — через launcher
оболочки.

Режим самодостаточен: демон при этом всё равно существует, но живёт как процесс,
запущенный вместе с окном, и может завершаться вместе с ним, если пользователь не
разрешил фоновую работу.

### Интеграция в рабочий стол

При установке приложения в профиль на каждой десктопной ноде создаётся ярлык:

| Платформа | Форма | Размещение |
|---|---|---|
| Linux | `.desktop`-файл | `~/.local/share/applications/` |
| Windows | ярлык | меню «Пуск» в профиле пользователя |

Ярлык запускает не самостоятельную программу, а окно приложения поверх работающего демона:

```text
Пользователь открывает ярлык
        ↓
kos-launch --app com.example.music
        ↓
демон работает? ── нет ──▶ запустить демон, дождаться готовности control plane
        │ да
        ▼
демон создаёт окно с app view нужного пакета
        ↓
если окно этого приложения уже открыто — сфокусировать его
```

Правила:

1. **Ярлыки создаются на конкретной ноде.** Установка пакета — операция над профилем, а
   создание ярлыка — локальное следствие: приложение, несовместимое с этой нодой, ярлыка
   здесь не получает.
2. **Ярлыки создаются в профиле пользователя** и не требуют прав администратора.
3. **Удаление пакета удаляет ярлыки**, переименование и смена иконки их обновляют.
   Расхождение между реестром пакетов и набором ярлыков проверяется при старте демона.
4. **Ярлык не является точкой доверия.** Он передаёт демону идентификатор пакета, а демон
   проверяет, что такой пакет установлен и совместим; подделанный ярлык не даёт ничего,
   чего не даёт launcher.
5. **По умолчанию одно окно на приложение.** Повторный запуск фокусирует существующее окно.
   Приложение может объявить в манифесте поддержку нескольких представлений — тогда
   открывается новое окно, а сессии остаются независимыми.
6. **Оболочка присутствует и здесь**: окно приложения содержит узкую доверенную полосу с
   индикатором системы и точкой входа в launcher, а системные диалоги рисуются над окном.
   Приложение по-прежнему не может нарисовать системный запрос.

Дополнительно регистрируется обработчик схемы `kos://` для ссылок вида
`kos://app/<package-id>/<path>`, что даёт открытие приложения по ссылке из внешних программ.

## Демон

Демон — процесс ядра ноды. Он существует в обоих режимах и отвечает за всё, что не должно
зависеть от открытого окна: синхронизацию, сессии с другими нодами, фоновые задачи,
экспортированные API приложений, обслуживание подключённого оборудования.

| Вопрос | Решение |
|---|---|
| автозапуск | включается пользователем при первой настройке; Linux — пользовательский юнит systemd или autostart-файл, Windows — задача в планировщике от имени пользователя |
| закрытие всех окон | демон продолжает работу, если есть разрешённые фоновые задачи или роль в сети; иначе завершается по таймауту простоя |
| остановка пользователем | явное действие; синхронизация и фоновые задачи прекращаются, о чём оболочка предупреждает |
| единственность | на пользователя приходится один демон; повторный запуск обнаруживает существующий и передаёт ему команду |
| выход из системы | демон завершается вместе с сеансом; фоновые задачи сохраняют checkpoints |
| несколько пользователей ОС | каждому соответствует своя нода со своим ключом; общего состояния между ними нет |

Остановленный демон означает остановленную ноду: устройство перестаёт быть доступным в сети
профиля, и на других устройствах оно отображается как офлайн. Это честное поведение, а не
сбой.

## Обновление при открытом окне

Артефакты пакетов неизменяемы, поэтому обновление не ломает работающее представление:
открытое окно продолжает работать на прежней версии, новая версия активируется при следующем
запуске. Оболочка показывает, что доступна новая версия. Если обновление расширяет права,
пакет переходит в `pending-grant` и не запускается ни на одной ноде до подтверждения.

## Платформенные особенности

### Linux

- сеансы X11 и Wayland различаются по возможностям синтеза ввода и захвата экрана: на
  Wayland часть операций [управления нодой](../08-devices/02-node-control.md) недоступна
  или требует портала; это выражается дескриптором adapter, а не обходными путями;
- индикатор в трее реализуется через StatusNotifier там, где он поддерживается окружением;
  отсутствие трея не должно лишать пользователя доступа к оболочке;
- headless-сборка на том же дистрибутиве — это [облачная нода](./04-cloud-node.md), а не
  десктопный клиент без окна.

### Windows

- ярлыки и автозапуск создаются в профиле пользователя, без записи в общесистемные разделы;
- регистрация обработчика `kos://` выполняется для текущего пользователя;
- единственность демона обеспечивается именованным объектом синхронизации.

## Блокировка и защита в состоянии покоя

Профиль может требовать разблокировки при старте демона: ключи данных остаются
запечатанными в платформенном хранилище до подтверждения пользователем. Автоблокировка по
бездействию блокирует представления, но не обязана останавливать фоновую синхронизацию —
это выбор пользователя, и он объявляется явно, потому что определяет, что увидит человек,
получивший доступ к включённому компьютеру.

## Проверяемые критерии

- оба режима запуска обслуживаются одним процессом ядра;
- закрытие окна не останавливает разрешённую фоновую задачу;
- остановка демона переводит ноду в офлайн явно и наблюдаемо для других устройств;
- набор ярлыков соответствует набору установленных и совместимых пакетов;
- ярлык не даёт прав, которых не даёт launcher оболочки;
- обновление пакета не прерывает работу открытого представления;
- ни в одном режиме приложение не может нарисовать системный диалог.
