## На стророне клиента
Обычный стейт в памяти
- плоское дерево сторов
- в каждом сторе свойсвто и методы - геттеры и сеттеры, причем они могут работать даже с другими сторами
- все это реактивное

Стэк для доступа к апи
- через билдер создаешь конфиг для стора апи
- в конфиге указыаешь базовый  URL и методы генерируются сами
- если rest api не стандартный то можно под каждый метод подправить path
- librnet api подключается бесшовно - сразу готово к использованию
- можно добавлять сторонние эндпоинты и отключать некоторые методы
- считывается схема бд и zod и валидация работает сразу
- валидация сразу работает на полях формы
- когдда работаешь со списком то в сторе отдельный элемент списка и каждый метод должен его обнолять
- когда заправшиаешь элементы то они хранятся отдельно по их id
- когда только запросил элемент то сразу отдается реактиный стеейт с  pending и в процессе загрузки будет либо result либо error
- ошибки сразу поднимает в тостере. в дев режиме более расширенные
- компонент запрашивает через composable который наешениется на  onMoutn and onUnmount и если на отдеьном запросе больше нет компонентов то его данные удаляются
- стор на конкретном эндпоинте можно подключить для атоматического обновления. в librnet это делается по умолчанию, а для других запросов нужно настроить обновление: либо полинг либо вебсокет 
- если на строне серера разработчик пишет свои обработчики апи то они сразу доступны на клиенте

## Серверная часть апи
- для локального доступа для UI пользователь сразу подставляется на перого в базе и сразу формируется сессия и полный доступ к своим личным данным, для этого даже не нужно писать проверки
- еси юзер впускает другого пользователя то его данные хранятся  в его сети, а они могут запрашиввать друг у друга данные
- чтобы добавлять нового пользователя сразу будут готовая система прав и ролей и просто назначаеь роли на определенные апи
- для пользователя который заходит с расшаренного приложения то его данные хранятся у ввас и так же даешь ему роли и права
